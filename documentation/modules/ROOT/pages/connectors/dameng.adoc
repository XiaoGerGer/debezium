= Debezium 达梦 Connector 使用手册
:page-aliases: connectors/dameng-database-setup.adoc, connectors/dameng-support-matrix.adoc
:toc:
:toclevels: 3

== 概览

本手册适用于 `3.6-xinchuang` 分支、版本 `3.6.4-xingchuang-kafka2.0`，内容核对日期为 2026-10-21。
数据库准备、兼容矩阵、采集机制、事件格式、类型映射、部署、参数、监控和故障处理均集中在本文件。
代码测试和历史调研报告作为工程证据保留，日常部署和运维不需要按报告逐篇查找使用方法。

Connector 使用 JDBC 获取表结构和快照数据，通过达梦 `DBMS_LOGMNR` 挖掘归档 REDO，向 Kafka 发布行级变更。
支持采集可写单机、主备环境中的当前主库，以及显式配置的物理备库；备库采集要求目标数据库构建支持该接口，信号写入仍连接主库，详见 <<dameng-standby-capture,备库采集与主库信号写入>>。
只创建一个 Task，`tasks.max` 大于 `1` 会报错。
默认 `snapshot.mode=no_data`，首次启动只建立结构和 LSN 基线，不扫描存量行；需要存量数据时显式使用 `initial`，或稍后触发增量快照。
已有 offset 时正常恢复原位置，`no_data` 不表示每次重启都从最新位置开始。

交付语义为至少一次，重启后可能重发尚未确认 offset 的事件；当前不声明 Kafka Connect Source Exactly-once 支持。
数据库的一个事务可以包含很多条行级变更，一条更新 100 行的 SQL 通常产生 100 个更新事件，另可能有事务元数据事件。
事件只在事务提交后发布；回滚内容不应发布。Kafka 跨 Topic、跨分区的消费顺序和原子可见性仍需由下游设计。

== 工作原理

[source,text]
----
Kafka Connect Worker
  -> DamengConnector：插件发现、配置、创建唯一 Task
  -> DamengConnectorTask：JDBC、offset、schema history、队列和服务
  -> ChangeEventSourceCoordinator：协调快照、持续采集和信号处理
       -> 初始快照：共享锁 -> 选择 LSN -> 结构/可选数据 -> 释放锁
       -> 持续采集：归档检查 -> LogMiner 窗口 -> 事务缓存/回滚重建
                    -> 历史结构解码 -> EventDispatcher -> 事件队列
       -> 增量快照：主键分块读取 + 信号水位 + CDC 去重
  -> Task.poll() -> Worker Converter/SMT/Producer -> Kafka 业务 Topic
  -> Worker 确认进度 -> Kafka Connect offset 存储
----

Worker 管理插件、Task 生命周期、REST API、序列化和 Kafka 发送；Broker 存储 Kafka 消息。
协调器不等于新的 Worker 或 Broker，它在 Task 内组织快照、streaming 和信号流程。
增量快照使用独立 JDBC 连接，但不因此变成多个 Task 或多表并行快照。

=== 分区、offset 和历史结构

Connector 的 source partition 是逻辑来源标识 `{"server":"<topic.prefix>"}`，不是 Kafka Topic 分区。
Worker 按 Connector 名称和 source partition 找回 offset；不要在恢复时随意改变 Connector 名称、`topic.prefix` 或 history Topic。
offset 记录安全重放 LSN、变更 LSN、提交 LSN、事务内记录序号、事务身份、数据库身份和结构解释签名。
这些值用于历史重放，不是可以任意编辑的“从这里继续”的游标。

数据库当前 JDBC 表结构可能晚于待处理日志。
Connector 先从 schema history 恢复日志位置对应的表定义，再按 REDO 中的 `OBJ#` 和 `COL n` 解码；不能拿当前列顺序解释旧日志。
快照记录对象编号与结构，后续受支持的 DDL 更新历史模型。映射按不可变表定义缓存，DDL 更新时失效，避免重复解析同一结构。
原生模式、词法、标识符和大小写设置进入 `compatibility_signature`；过滤范围进入 `capture_scope`。
旧 offset 缺失签名或兼容条件不一致时拒绝普通恢复。支持的表过滤范围调整通过独立的范围变更记录恢复，详见 <<dameng-capture-scope-changes,调整采集表范围>>和 <<dameng-recovery,恢复与升级>>。

=== 适用范围

本实现不提供 Oracle XStream、OpenLogReplicator、RAC/PDB、Oracle Flashback、Infinispan/Ehcache 事务缓存或在线字典采集模式切换。
JNI/C Logmnr 曾用于性能探测，当前产品路径仍为 JDBC 系统包。
并行初始快照、阻塞快照、自定义 snapshotter、主动丢弃事务信号，以及手工注入结构修复历史 DDL 的流程均未作为达梦已验证能力提供。
通用配置字段出现在 REST 配置元数据中，不意味着相应流程已在达梦实现或验收。

== 兼容模式、版本和部署支持矩阵

本节适用于 `3.6-xinchuang` 分支的 `3.6.4-xingchuang-kafka2.0`，核对日期为 2026-10-21。
矩阵描述当前 Connector 的实现边界和已有测试结果，不代表达梦数据库产品本身的完整能力。
部署时需要同时满足数据库构建、JDBC 驱动、兼容模式、相关参数和部署模式的条件；三张矩阵不能任意交叉组合成已经验证的环境。

“已验证”仅指记录中的场景通过测试；“组件探测”仅指直接调用 JDBC、LogMiner 或解析器；“未验证”不等于已经证明不可用。
数据库能执行 SQL、Connector 允许启动、端到端 CDC 数据一致性通过，是三个不同的判断。
字段精度、LOB 和 DDL 等限制仍以 <<dameng-connector,Connector 使用说明>>为准。

[cols="2,2,4",options="header"]
|===
|参数 |当前接受值 |验证范围

主备成员应保持一致，并在整个需重放的日志区间内保持不变；改模式后沿用旧 offset 不属于受支持的升级路径。

因此无版本 WARN 不等于完整环境通过验收；版本读取失败也只 WARN。
升级数据库或驱动后，应重新核对实际存储值、snapshot 和 streaming 的一致性，并执行历史 DDL、事务回滚、重启恢复及目标部署模式的测试。

官方社区线索见 https://eco.dameng.com/community/article/2b327cc00893e4f86a3c400afd60bd76[达梦日志挖掘 LOGMNR 功能介绍]。
文章示例与项目测试是不同证据，数据库具备备库接口也不等于 Connector 已完成备库适配。

本表描述数据库拓扑和实际采集节点，不是 Kafka Connect Worker 的部署方式。
当前生产采集接口为 JDBC `DBMS_LOGMNR`，不是 JNI/C Logmnr；后者的专项性能探测不表示存在可用的 Connector 适配器。

[cols="2,2,2,5",options="header"]
|===
|数据库部署与采集位置 |角色条件 |支持状态 |配置、测试与边界

|主备使用 VIP、代理或自动故障切换管理系统 |切换后仍须唯一 `PRIMARY` / `OPEN` |不是已验证的部署组合 |现有验收限于成员地址列表与人工角色切换。需要额外验证路由、连接失效、隔离旧主和历史连续性；Connector 不执行升主或脑裂仲裁。

`MOUNT`、`SUSPEND` 等非 `OPEN` 状态不是可采集状态；配置成员列表时也不接受 `NORMAL` 代替 `PRIMARY`。
服务器返回的角色和状态只是必要条件，不能替代归档范围、数据库家族、来源链和已应用 LSN 的校验。
主备恢复的配置与操作说明见 <<dameng-primary-standby-recovery,无 VIP 主备恢复>>。

备库失败的结论限定于上表的数据库构建与 JDBC 系统包调用，不应表述为“达梦所有版本的备库都不能挖掘日志”。
备库采集由主库负责创建和写入信号表、写入增量快照开启/关闭水位；备库负责 LogMiner，以及初始快照和增量快照所需的 JDBC 查询。
读写连接、备库回放屏障、来源身份校验及切换后的角色路由见 <<dameng-standby-capture,备库采集>>。数据库版本、归档保留和可用备库仍须满足该章节的条件。

=== 测试依据与更新规则

模式注册与检查依据为 `DamengCompatibilityRegistry`、`DamengNativeCompatibilityProfile`、`DamengDatabaseVersion` 和 `DamengConnection` 的当前实现。
数据库测试记录在仓库的 `debezium-connector-dameng/src/test/testing.adoc`；当前字段、兼容模式和备库支持边界以本手册相应章节为准。
主备 Connector 恢复用例为 `DamengPrimaryStandbyIT`，读写分离的备库采集用例为 `DamengStandbyIT`。
`DamengStandbyLogMinerProbeIT` 是接口诊断用例，在旧构建验证失败边界，在新构建验证直接 JDBC 挖掘；接口诊断不能代替 Connector 的快照、CDC 和切换回归。

后续更新矩阵时，应同时记录测试日期、Connector 版本、服务器完整构建、JDBC 数据库及驱动版本、字符集、参数、部署拓扑和具体通过或失败的场景。
不能用单元测试覆盖率、能启动、组件探测成功或其他版本的社区示例替代目标组合的端到端验收。

== 快照与信号

=== 初始快照和 no_data

[cols="2,4,4",options="header"]
|===
|snapshot.mode |没有可恢复 offset 时 |已有已完成快照的 offset 时
|`no_data`（默认） |读取结构、选择当前 LSN，再持续采集；不发存量行 |恢复旧位置，仍要求所需归档存在。
|`initial` |读取结构和存量行，再持续采集 |恢复旧位置，不自动再次全量。
|`initial_only` |读取结构和存量行后结束快照执行，不进入 CDC |不提供持续采集；Task 状态不应当作数据仍在变化的证明。
|`never` |`no_data` 的旧别名，仍需结构基线 |与 `no_data` 相同。
|===

未完成的初始快照可能在恢复时重新执行并重发已经输出的行。
Connector 先发现并锁住捕获表，选择 `V$RLOG.CUR_LSN`，读取结构，按模式决定是否扫描行。
选择 LSN 后再次检查匹配过滤器的新表；如发现新表，补锁并重新选择 LSN，再检查一次。最终检查之后的新表通过 DDL 流处理。
整个快照事务结束并成功 rollback 后才释放共享表锁。此处 rollback 用于结束只读快照事务，不是回滚业务事务。
普通查询不使用 Oracle `AS OF SCN`；一致性依赖这些锁，因此 `no_data` 建立结构基线也会短暂锁表。

`snapshot.max.duration.ms` 默认 10 分钟，覆盖锁等待、结构/数据读取和队列阻塞。
超时中断快照并请求 JDBC abort，Task 失败，不会通过跳过表继续；实际断开会话及释放锁依赖驱动和数据库。
主备模式在完成标记之前再次核对主库身份；切换打断初始快照后在新主库重新快照。
当前仅允许 `snapshot.locking.mode=shared`、`snapshot.max.threads=1`。
`snapshot.lock.timeout.ms` 的继承字段没有接入达梦锁语句，实际应结合 `database.query.timeout.ms` 和总快照预算设置超时。

=== 快照范围与采集范围

`schema.include.list`、`table.include.list` 等决定总体采集范围；表过滤针对完整 `schema.table`，列过滤针对 `schema.table.column`，不是 `database.schema.table`。
规则是正则表达式，需要字面点号时在 JSON 中写 `APP\\.CUSTOMERS`。
include 和 exclude 对应项不能同时配置。
`snapshot.include.collection.list` 只减少初始快照输出行的表，不缩小这些已捕获表的结构 history，也不改变 streaming 或增量快照的选择范围。
`snapshot.select.statement.overrides` 和每表 SQL 只过滤初始快照行，不能过滤之后的 CDC。

结构发现完成时，日志打印结构采集表和数据快照表。
每个没有匹配任何可见表的 `table.include.list` 表达式会 WARN，但不会因此停止，因为规则可能针对未来新表。
应检查表名大小写、其他过滤规则、元数据可见性和 SELECT 权限；WARN 本身不能证明是哪一种原因。
普通重启直接恢复 streaming 时不会重新执行完整快照发现检查。

初始 history 当前只包含采集过滤器选中的表，`schema.history.internal.store.only.captured.tables.ddl=false` 不会扩展为所有库表结构。
已捕获表被 rename 到范围外后仍保留后续 DDL，以支持之后改回名称；从未拥有历史定义的表不能仅靠 rename 进入捕获范围。
在过滤器不变时，运行中或停机期间创建、删除后重建的匹配表，可以通过仍保留的 DDL 采集。
已有完整 offset 和 history 时，可以修改表过滤范围后重启，具体边界和限制见 <<dameng-capture-scope-changes,调整采集表范围>>。不能直接用当前 JDBC 结构解释新增表的旧日志。

[id="dameng-capture-scope-changes"]
=== 调整采集表范围

在初始快照已完成且保留完整 offset、schema history 和所需归档的条件下，可以 PUT 完整 Connector 配置，修改 schema/table include/exclude 过滤规则后重启。
原有表继续使用原来的恢复位置；扩表不会把整个 Connector 推到数据库最新 LSN，也不会重新执行所有表的初始快照。
`initial` 和 `no_data` 在已有已完成 offset 时遵循相同的范围调整流程。`initial` 只控制首次初始化，不表示每次新增表都自动扫描存量行。

每次允许的过滤规则变更都会选定并持久化当前启动 LSN `S`，包括纯缩表、正则变化但没有当前可见新增表的情况。这些没有新增表的调整不获取业务表共享锁。
对于此前未捕获且 JDBC 当前可见的已有表，Connector 只保护本次新增表，等待其已有写事务结束，选定启动 LSN，获取当前结构和对象编号，并在释放共享锁前持久化范围变更与结构基线。
主备部署在主库保护新增表并选择边界，等备库重放到该边界后读取结构；不能用尚未追平的备库结构建立基线。
对于本次由“不匹配旧过滤器”变为“匹配新过滤器”的表，`LSN <= S` 的历史行变更和 DDL 始终过滤；这个边界不局限于建立了 JDBC 基线的表名清单。
因此扩大正则后，当前已删除或不可见表的旧 `CREATE TABLE` 不会被误认为本次新增表。以后在 `S` 之后创建且匹配新规则的表，仍可由受支持的 `CREATE TABLE` DDL 建立结构并进入采集。
已有完整基线的新增表在边界之后正常进入 CDC。等待旧表追赶积压期间，新表的结构基线保持待启用，挖掘跨过边界时才安装。
重启复用已持久化的边界，不通过重新选择更晚的 LSN 丢弃停机期间的变化。

如果 schema history 已知某张本次新加入的表，但 JDBC 当前看不到该表，范围调整会明确失败，不能沿用它的旧结构继续 CDC。应先确认表是否存在、同一 CDC 账号的元数据与 SELECT 权限，再恢复可见性并重新提交配置。
每条 `table.include.list` 规则如果没有匹配任何 JDBC 可见表，也会记录 WARN，提示检查表名、大小写、过滤范围和元数据/SELECT 权限。WARN 只能指出规则当前没有选中可见表，不能证明表不存在还是权限不足；如果一条正则同时匹配其他可见表，Connector 无法从无字典 redo 中推断被隐藏的表名。扩表前应使用采集账号验证新增表的元数据与 SELECT 可见性。
如果新增表的对象编号与另一个历史表名相同，可能是旧配置尚未处理完重命名日志，范围调整也会拒绝。先用原过滤配置追平重命名，再修改范围；不能让两个表名同时绑定同一物理对象。

扩表默认不补已有存量。确认新表启用后，可以按需发送该表的增量快照信号，要求信号表已配置且目标表满足增量快照条件。
增量快照补的是当前仍存在的行，不能补回启动边界之前已经删除的行、中间更新或历史事务。
扩表只保证新表在边界之后的采集，不补齐此前被排除的跨表事务。

缩表从新配置生效后停止输出被移除表，未发送的历史积压也不再补采；已经进入发送流程或已写入 Kafka 的记录不会撤回。
同一事务中仍保留表的变更继续输出，事务提交、回滚、全局恢复位置和原始事件序号不因过滤其他表而被跳过或重新编号。
被移除表的增量快照待处理列表、当前窗口和游标同时清理，其他保留表的快照继续恢复。
缩表保留历史结构记录；以后重新加入该表时按新的启动边界处理，不重放被排除期间的变化。下游保留的旧数据如需清理，应另行对账或重建。
缩表减少事件处理与发送量，但事务识别和日志挖掘仍有公共成本，数据库挖掘负载不一定同比下降。

以下变更不作为普通扩缩表处理，仍会拒绝：

* 初始快照尚未完成时修改范围，应等待快照完成后再调整。
* 改变数据库选择、`table.ignore.builtin` 或 `signal.data.collection`。
* 从过滤规则中移除已配置的信号表。信号表承担快照命令和水位，不是可以任意缩减的业务表。
* 缺失旧范围描述、兼容签名、offset 或 history，无法证明原来的结构与恢复条件。

旧版本 offset 如果没有 `capture_scope_manifest`，必须先使用原过滤配置运行，等待新版本保存带范围描述的 offset，再修改过滤规则。不能同时升级并直接更换过滤范围，也不要手工填造 manifest。

不要使用 `recovery.restart.nonce` 代替普通扩表。nonce 用于明确放弃整个 Connector 的历史积压，范围调整只为新增表建立边界。

=== 增量快照机制

增量快照按主键范围分块，默认每块最多 1024 行。
每个块通过源信号表的开启/关闭水位与 CDC 交错：读取块内行，观察水位之间的日志变更，移除被更新或删除的旧快照行，再输出剩余 `op=r` 记录。
进度随 offset 保存，重启后可恢复。日志追赶慢会延长块完成时间，未观察到关闭水位时不能把缓存行提前当成最终结果发布。
它不持有初始快照那种贯穿全流程的共享表锁，也不保证所有表处于同一个全库时刻。
当前验收以声明主键的表为基础；普通无主键 CDC 支持不等于无主键增量快照支持。
执行期间须保持表结构稳定，`incremental.snapshot.allow.schema.changes` 必须为 `false`。

=== 信号表配置、创建和触发

设置 `signal.data.collection=APP.DBZ_SIGNAL`，将信号表纳入捕获规则，并确保其产生逻辑日志。
每个独立 Connector 使用独立信号表，避免多个实例读取相同命令或互相消费水位。
已有 offset 时不能直接添加或改名信号表绕过 capture_scope 检查，建议首次创建 Connector 时就配置。

Task 在校验配置和 offset 后、发现快照表前检查信号表，不存在则自动创建；schema 必须已存在。
自动创建需要相应 CREATE TABLE 权限。现有表不改结构、不清空记录，但必须可读，恰好具有按顺序排列的 `ID`、`TYPE`、`DATA` 三个 VARCHAR/NVARCHAR 列。
创建或结构校验失败会阻止启动。Connector 还需插入水位的权限，`insert_delete` 策略需要 DELETE 权限。
不授予 DDL 权限时可由 DBA 预创建：

[source,sql]
----
CREATE TABLE APP.DBZ_SIGNAL (
    ID VARCHAR(64) PRIMARY KEY,
    TYPE VARCHAR(64) NOT NULL,
    DATA VARCHAR(2000)
);
GRANT SELECT, INSERT, DELETE ON APP.DBZ_SIGNAL TO CDC_USER;
----

使用有写权限的账号提交一次性、唯一 ID 的命令：

[source,sql]
----
INSERT INTO APP.DBZ_SIGNAL VALUES (
    'customers-snapshot-001',
    'execute-snapshot',
    '{"type":"incremental","data-collections":["APP.CUSTOMERS"]}'
);
COMMIT;
----

检查 Task 日志、快照通知/指标和业务 Topic 的 `op=r`，不要仅凭 INSERT 成功认定快照完成。
停止整个运行中的增量快照可使用公共信号动作：

[source,sql]
----
INSERT INTO APP.DBZ_SIGNAL VALUES (
    'customers-stop-001', 'stop-snapshot', '{"type":"incremental"}'
);
COMMIT;
----

停止动作不撤回已经发布的行。`pause-snapshot`、`resume-snapshot`、`additional-conditions` 和 Kafka/JMX/file 信号通道来自公共框架，但尚无本模块与源表基本流程同等范围的端到端验收，应先在目标环境验证。
即使使用其他触发通道，当前达梦增量快照仍需要源信号表协调水位，不能只配 Kafka 信号 Topic 就省略它。

== 日志挖掘、事务缓存与性能

=== 挖掘窗口和保存点

Connector 读取已归档的日志，未归档尾部造成的延迟不能靠扩大窗口消除。
每轮检查身份、兼容环境和所需归档，启动 LogMiner、读取窗口、处理事务并分发；不是严格每 poll.interval.ms 完成一次。
新配置默认使用 archive_bytes：按完整归档文件 LEN 的 64 MiB 软预算选择前向窗口，LSN 跨度随文件边界变化。
也可显式选择 fixed 固定 LSN 窗口。LSN 跨度是位置差，不是行数、SQL 数或字节数。

未完成事务跨窗口保留，普通窗口只读新增范围。
早先窗口的事务遇到 COMMIT、XA COMMIT 或 operation 36 时，在发布该窗口事务之前按完整安全范围重建缓存，替换包括落盘内容在内的临时行像，排除后来确认回滚的 DML。
重建从所有待处理事务的最老安全位置开始，不只从触发事务开始；同窗口多个边界合并重建，不同窗口仍可能重复读历史。

当前支持 SAVEPOINT 的有效结果恢复。测试版本的 operation 36 同时用于用户保存点、普通 UPDATE/DELETE 内部标记及回滚相关操作，不能仅凭该码拒绝 SAVEPOINT。
ROLL_BACK 表示这条记录已被回滚，不表示它本身是一条回滚命令。早期保存点回滚也可能标记 START，因此 START 的回滚标记不足以认定整个事务终止。
测试版本的完整回滚需结合已回滚 START、没有幸存行、terminal operation 36 的 ROLL_BACK=1 / RS_ID=-1；结果不明确的事务继续保留历史。
事务按提交顺序发布。长事务即使已落盘，仍会固定安全重放起点，数据库必须保留该范围的归档。

=== LogMiner 记录完整性与诊断

`V$LOGMNR_CONTENTS.SCN` 表示达梦日志的 LSN。
读取时显式检查必需数值字段 `SCN`、`OPERATION_CODE`、`ROLL_BACK`、`SSN`、`CSF` 的 SQL NULL，避免 JDBC 将缺失值解释为 0。
`ROLL_BACK` 和 `CSF` 只接受 0、1。DML 首片必须具有有效 `DATA_OBJ#`；事务标记的对象 ID 可以为空。
窗口从事务中途开始时 `START_SCN` 可为空；未提交或已回滚记录的 `COMMIT_SCN` 可为空，不据此误判事务已完成。

长 SQL 按 `SCN`、`XID`、`OPERATION_CODE`、`RS_ID` 组装。
已验证的 DM 8.1.2.128 构建中，首片 `SSN=0`，后续片逐片加 1，末片 `CSF=0`。
同版本不同测试实例分别观察到 2000、4000 字符的分片长度，不能把 `SQL_REDO VARCHAR(4000)` 的列宽当成固定分片大小；组装不依赖固定长度。
连接器检查该序列，并拒绝缺片、重复片、乱序片、缺失 SQL 文本或冲突的对象身份、对象版本、回滚标记；后续片可以省略对象元数据，组装结果保留首片元数据。
升级数据库后应复跑长 SQL 和元数据回归，确认分片规则未变。
读取校验失败时，该挖掘窗口不会发布事务或推进安全重放位置。

已知历史表通过 `DATA_OBJ#` 索引查找，索引随快照、历史恢复和 DDL 更新失效，避免逐行扫描全部表。
普通 DML 的未知对象可属于未捕获表，保持原有过滤行为。
遇到未实现操作（包括 255）时，历史身份明确且已排除的表可过滤；捕获表或无法确定所属表的异常操作停止任务，不静默跳过。
诊断包含 LSN、XID、RS_ID、SSN、`DATA_OBJ#`、`DATA_OBJV#`、`RBASQN`、`RBABLK`、`RBABYTE`；这些字段随事务临时落盘保留，不附带 SQL 内容。
可空诊断数值以 -1 表示缺失；0 是合法对象版本和日志位置，不能用作缺失标记。

`DATA_OBJV#` 目前仅用于诊断和同一 SQL 分片之间的一致性检查，不用来推算表结构。
2026-10-20 在 DM 8.1.2.128 上实测：CREATE/ALTER/DROP 的版本字段可为空，首次 DML 版本为 0，改列名后由 0 变为 2，TRUNCATE 后版本不变，删除重建后重新从 0 开始；重复挖掘同一区间的结果一致。
因此不能假定每条 DDL 将版本增加 1，也不能用它替代 schema history。

官方将 `STATUS`、`INFO`、`SAFE_RESUME_SCN` 定义为保留且为空的字段，连接器不套用 Oracle 的 STATUS 错误码规则。
查询只增加本地测试版本已具备的经典字段，不依赖较新手册中的 `SUBTAB_ID`、`SRC_RAFT_ID`。
字段定义参见 https://eco.dameng.com/document/dm/zh-cn/pm/dm8-admin-manual-appendix2.html[达梦官方动态视图文档]；挖掘接口参见 https://eco.dameng.com/document/dm/zh-cn/pm/dbms_logmnr-package.html[DBMS_LOGMNR 文档]。

=== 内存与临时文件

所有事务共享默认 64 MiB 的估算缓存阈值，超出时将最大的驻留事务写入临时文件，后续行追加。
事务身份和起点等元数据始终留在内存，包含已提交待分发事务，计入内存阈值和默认 1000000 条事务限制；元数据耗尽仍会失败。
提交时顺序读取文件，不要求整个大事务重新装入内存。文件带帧长度和校验，损坏、截断、权限或 I/O 错误均停止任务。
默认每次运行临时文件上限 1 GiB，文件位于独立 `dameng-tx-*` 目录；日志记录事务 ID、起点、路径，不打印 SQL 内容。
分发、确认完整回滚、重建和正常/错误清理会删除对应文件。强制 kill 可能遗留目录，只能在确认对应运行已结束后清理。
配额不包含其他 Task、其他进程或遗留目录，因此还需监控文件系统剩余容量；文件含源数据，应限制访问。

临时文件不是持久恢复状态。新 Task 忽略旧文件，从已保存 offset 重放归档；不能因落盘成功就提前删除旧归档。
单条 SQL_REDO 的连续片段必须先在内存拼接，默认 payload 上限 16 MiB，按 UTF-16 计数，拼接前校验；单条无连续片段的 SQL 也受限制。
JDBC 输入、StringBuilder、最终 String 和临时副本还占用额外堆。编解码复用的每个字节/字符缓冲各最多保留 64 KiB，大记录使用临时数组。
事务阈值不包括事件队列、JDBC 和转换开销，不应等于整个 JVM 的 Xmx。
旧 `log.mining.buffer.max.bytes`、`log.mining.buffer.max.records` 已废弃并忽略；累计挖掘工作量不再是停止条件。

=== 文件预算窗口与调优

`log.mining.window.strategy=archive_bytes` 从下一条待扫描 LSN 所在文件开始，按顺序累加 `V$ARCH_FILE.LEN`，达到 `log.mining.window.max.bytes` 后停止扩展结束位置。
结束位置还受到本轮归档上界限制；备库同时受 SLSN 和 RPKG_LSN 的安全回放上界限制。到尾部立即处理可读部分，不等文件写满、不等凑齐预算。
这是固定文件字节预算，窗口随文件范围变化；没有通过耗时或吞吐试探自动增减字节预算。

官网将 LEN 定义为日志长度，单位字节；FREE 为写日志偏移。
8.1.3.162 实测已关闭小文件 LEN=32768、FREE=32768，活动归档 LEN=67108864、FREE=49152，说明活动文件可能预分配。
预算使用整个 LEN，包含已扫描部分和预分配空间，不代表实际读取字节、缓存内存或本轮 DML 数据量。
单文件超过预算仍读取其安全范围；最后一个文件及共享 inclusive 边界所需文件也可能让总长度超过预算。
选中文件 LEN 缺失或非正值时停止，提示核查 V$ARCH_FILE 或显式选择 fixed；不以 LSN 差伪造字节数。
归档缺口、身份或主备历史异常仍按现有安全检查停止。
跨文件数值不连续时，只允许下一文件的正 PREV_LSN 精确等于请求起点减一来证明连续；若重启请求包含缺失的前驱记录本身，仍拒绝继续。

正常扫描从 scannedThrough 继续，不因长事务固定 replayLsn 而反复读旧范围，也不因文件名未变而自动扩预算。
需要事务重建时，仍完整读取 replayLsn 到本轮结束位置，允许超出前向预算。
整轮扫描与必要重建结束后才分发，因此扩大预算可能提高吞吐，也可能增加消息延迟与临时磁盘占用。
JMX 暴露预算、所选文件总 LEN 和文件数；启动 INFO 打印策略及配置，DEBUG 打印每轮范围、文件数和总长度。

[source,json]
----
"log.mining.window.strategy": "archive_bytes",
"log.mining.window.max.bytes": "67108864"
----

回退对照可显式设置 `log.mining.window.strategy=fixed`、`log.mining.batch.size=10000`。
旧耗时反馈 adaptive 模式已删除，strategy 只接受 archive_bytes 或 fixed，未指定时默认 archive_bytes。
升级前删除 `log.mining.window.adaptive.enabled`（无论 true/false）、`log.mining.batch.size.min`、`log.mining.batch.size.max` 和 `log.mining.window.target.ms`。
这些旧参数不再注册为配置项；残留任意一项都会在配置校验或任务启动时明确报错并提示迁移，即使已指定新的 strategy 也必须删除。
原来使用 adaptive.enabled=false 的任务若要保持固定窗口，改为 `log.mining.window.strategy=fixed` 并保留 `log.mining.batch.size`。

==== 文件预算与固定 10000 的本地对照（2026-10-21）

==== 吞吐与下游调优

先比较普通挖掘、重建、分发和队列等待，定位慢在哪一段。
增加缓存和磁盘只能降低落盘压力或承接突发，不能修复持续低于源端生成速度的下游吞吐。
生产者 buffer wait 高、每请求约一条记录且请求延迟低时，可评估增大 producer.batch.size；请求本身慢时检查 Broker 磁盘、网络和限流。
已有本地 221 列、65400 事件对比中，16 KiB 改为 64 KiB producer batch 曾将耗时从 32.2 秒降至 17.9 秒，buffer wait 从 22.1 秒降至 0；这是该次负载结果，不是所有环境的默认建议。
压缩需要权衡 CPU 和带宽，linger.ms 受延迟预算约束。调优保持确认和顺序保证，并复核吞吐、延迟、重试、内存和数据一致性。

== DDL、结构演进与支持边界

DDL 流程分为词法识别、语句影响范围分析和历史表模型解析。
词法保留原始位置和字面值，识别双引号转义、N 字符串、Q 引用、`--`、`//`、`/* ... */` 注释和 hint；删注释不合并两侧单词。
`NESTED_C_STYLE_COMMENT=0` 在第一个结束标记结束，=1 迭代平衡嵌套层数。
旧 8.1.2.128 原生构建在 BACKSLASH_ESCAPE 的两种值下都保留普通/N/Q 字符串反斜杠，现有实现据此不进行 MySQL 式转义。
8.1.3.162 在 BACKSLASH_ESCAPE=1 时语义已有变化，例如普通字面量 `'A\0B'` 返回 `A0B`；该组合尚未完成适配，应使用 0。
未加引号名转大写；引用名在 IDENTIFIER_MODE=0 或旧库缺失该参数时保留大小写，=1 按已实现规则转大写，但显式模式仍需目标版本验收。

先验证完整输入再应用捕获过滤，不能让前面的 GRANT、索引或过程掩盖后面的表 DDL。
已知索引、序列、视图、同义词、权限、COMMENT 和可识别的平衡 BEGIN/END 程序体可按不改变行结构处理；未知语句或残余语法不静默忽略。
MySQL 可执行注释拒绝，PostgreSQL dollar string 和 MySQL # 注释不作为原生语法处理。
受支持的 CREATE/ALTER/DROP/TRUNCATE/RENAME 在历史模型副本上先验证，成功后通过 history 管道应用；失败不应用该语句、不越过该位置。
错误提供 LSN、对象身份及可用的字符/行/列位置。捕获 DDL 缺失或使用非正 DATA_OBJ# 会失败。

[cols="3,5",options="header"]
|===
|类别 |当前边界
|普通表结构变化 |支持解析器已实现的列、主键和约束变化；未知子句失败。快照保存命名主键、UNIQUE、外键、CHECK 元数据供后续 DROP CONSTRAINT 历史重放。
|物理选项 |逐项识别常见 STORAGE、TABLESPACE、USING LONG ROW，以及单层 HASH/RANGE/LIST 分区声明；不任意丢弃未知 SQL 尾部。
|CTAS / LIKE |从历史位置的已知源表推导结构。CTAS 支持单源、星号/列投影、别名、CAST(column AS type) AS name 和简单过滤。实测两者复制行均产生 INSERT 日志。
|CTAS 限制 |拒绝 JOIN、子查询、聚合、算术类型推断和显式列定义列表；源表必须已在 history。复制列不继承主键、默认值、identity 或注释，直接投影保留来源可空性。
|多表复合 DDL |单条 LogMiner DDL 最多一个受支持表语句。CREATE SCHEMA、DROP SCHEMA/USER 及 CASCADE 未支持，不能保留陈旧结构假装成功。
|特殊表与列 |临时、HUGE、外部表及虚拟/生成列不支持；快照和捕获 CREATE 都有校验。实测部分特殊表不产出所需行日志、虚拟列 redo 值为 NULL，不能靠快照可查判断支持。
|分区维护 |不支持子分区、interval partitioning 和任意分区维护操作，创建分区根表支持不代表这些操作支持。
|DEFAULT ON NULL |解析器有支持和单测，但基线旧数据库拒绝该语法，尚非目标数据库端到端验收结论。
|===

常量默认值按历史列类型转换；复合默认表达式不在 Connector 中执行。
存入默认表达式前，将已识别注释替换为空格，保留其他字面内容；原始 DDL 仍保存在结构记录中。
流式 COMMENT 不更新事件 schema 的注释描述。
没有用当前 JDBC 表结构或 Flashback 自动兜底的生产路径。解析失败后的 restart 会再次遇到同一位置，处理方法见故障章节。
词法依据为 https://eco.dameng.com/document/dm/zh-cn/pm/dm_sql-introduction.html[SQL 介绍]、https://eco.dameng.com/document/dm/zh-cn/sql-dev/practice-strings.html[字符串]和 https://eco.dameng.com/document/dm/zh-cn/pm/definition-statement.html[DDL 文档]。

== Topic 与消息用途

默认 Topic 命名保留实际 schema/table 名称大小写。原生模式未加引号的标识符通常为大写，例如 `dameng.APP.CUSTOMERS`。
以下以 `topic.prefix=dameng` 为例；自定义 TopicNamingStrategy 或 SMT 会改变相应业务 Topic 路由。

[cols="2,3,4",options="header"]
|===
|用途 |默认名称或配置 |内容与要求
|业务变更 |`dameng.APP.CUSTOMERS` |每表一个 Topic；包含该表快照和 CDC 事件。
|结构变更事件 |`dameng` |供消费者读取的结构通知，默认 `include.schema.changes=true`。关闭不会停止内部历史记录。
|内部 schema history |`schema.history.internal.kafka.topic` 指定 |恢复历史结构和紧急恢复基线。每个 Connector 独占，单分区、完整保留，不配置 compaction。
|事务元数据 |`dameng.transaction` |启用 `provide.transaction.metadata=true` 后发布 BEGIN/END。
|心跳 |`__debezium-heartbeat.dameng` |启用心跳后发布；帮助提交安全 offset，不代表业务表发生变化。
|Worker 内部配置、offset、状态 |Worker 的 `config.storage.topic`、`offset.storage.topic`、`status.storage.topic` |由 Kafka Connect 管理，可由同一 Worker 集群的多个 Connector 共享。不能与 schema history 混用。
|通知 |`notification.sink.topic.name` |启用 sink 通知通道时使用；不是业务 CDC 或 schema history。
|===

schema history 的分区数和保留规则关系到恢复正确性。业务 Topic 的分区数不增加达梦 Task 数；多分区也不提供表级全局顺序。
字段名调整改变事件 schema，不会重命名数据库列。Topic 路由 SMT 只作用于发出的记录，不替代内部 history 配置。

== 数据变更事件

下面展示默认 envelope 的 JSON 形态，省略部分可选字段。示例数值仅用于说明，不是实测 LSN。
`JsonConverter` 的 `schemas.enable=false` 时直接得到下面的业务对象；设为 `true` 时外层包含 `schema` 和 `payload`。
Connect 的字段类型与最终 JSON、Avro 或其他序列化形式需要分开理解。

=== Key、Value 与 source

假设 `APP.CUSTOMERS(ID INT PRIMARY KEY, NAME VARCHAR(100))` 新增一行。
Key 为：

[source,json]
----
{"ID": 1}
----

Value 为：

[source,json]
----
{
  "before": null,
  "after": {"ID": 1, "NAME": "Alice"},
  "source": {
    "version": "3.6.4-xingchuang-kafka2.0",
    "connector": "dameng",
    "name": "dameng",
    "ts_ms": 1792368000000,
    "snapshot": "false",
    "db": "DAMENG",
    "schema": "APP",
    "table": "CUSTOMERS",
    "lsn": 1000,
    "change_lsn": 1100,
    "commit_lsn": 1200,
    "event_serial_no": 0,
    "transaction_id": "example-transaction"
  },
  "op": "c",
  "ts_ms": 1792368000100,
  "transaction": null
}
----

[cols="2,5",options="header"]
|===
|字段 |含义
|`before` / `after` |行级变更前后镜像；NULL 行镜像与某列值为 NULL 不同。行外 LOB 可能使用不可用占位值。
|`op` |`r` 快照读取、`c` 插入、`u` 更新、`d` 删除、`t` 清空表。
|`source.name` / `source.db` |逻辑来源 `topic.prefix` / 配置的 `database.dbname`。后者不是 PDB、schema 或 JDBC URL 的路由参数。
|`source.schema` / `source.table` |历史位置对应的逻辑表标识。
|`source.lsn` |安全重放起点，可能被长事务固定；不是已经挖到的最大 LSN。
|`source.change_lsn` |这条变更对应的日志位置。
|`source.commit_lsn` |事务提交位置；同事务的多条变更可能相同。
|`source.event_serial_no` |事务内记录序号，从零开始，可因过滤而不连续；不是 Kafka offset，也不等同于 transaction.total_order。
|`source.transaction_id` |达梦日志事务标识。不能假设跨数据库重建或所有恢复世代永久唯一。
|`source.snapshot` |是否来自快照；可能为 `true`、`last`、`incremental` 或 `false`，按实际快照阶段解释。
|`source.ts_ms` / 顶层 `ts_ms` |来源时间 / Connector 构造事件的时间；公共 envelope 还可提供 `ts_us`、`ts_ns`。它们不是 Kafka 消费确认时间，时钟差和来源时间粒度影响延迟计算。
|`transaction` |启用事务元数据时的事务 ID 和事件顺序；默认未启用。
|===

复合主键的 Key 包含全部主键列。唯一索引或 UNIQUE 约束不会自动当作主键。
无主键表支持普通 snapshot 和 CDC，默认 Key 为 null；用 `message.key.columns` 可以指定业务键，但必须自行保证非空、唯一和稳定。
这不会创建数据库主键，也不等于该表具备已验证的增量快照条件。

=== 操作类型和下游处理

[cols="1,3,3,4",options="header"]
|===
|op |before |after |说明
|`r` |null |当前行 |初始/增量快照读取，不表示数据库刚刚 INSERT。
|`c` |null |新增行 |INSERT 的提交结果。
|`u` |旧行 |新行 |更新的行级镜像；一条批量 SQL 可能产生多个事件。
|`d` |旧行 |null |删除事件，消费者应按 Key 删除其副本。
|`t` |null |null |TRUNCATE 表级事件，Key 为 null；默认 `skipped.operations=t` 不发布。需要时显式设置 `skipped.operations` 为空字符串。
|===

以下展示 update、delete 和 truncate 的 envelope 片段，实际消息还包含 source 和时间字段：

[source,json]
----
[
  {"before":{"ID":1,"NAME":"Alice"},"after":{"ID":1,"NAME":"Bob"},"op":"u"},
  {"before":{"ID":1,"NAME":"Bob"},"after":null,"op":"d"},
  {"before":null,"after":null,"op":"t"}
]
----

默认 `tombstones.on.delete=true`：有 Key 的 DELETE 后再发送相同 Key、Kafka value 为 null 的 tombstone，供 compacted Topic 清理旧值。
tombstone 不是 `{"after":null}`，也没有 envelope。无 Key 表无法依赖主键压缩清理。
主键更新产生旧 Key 的 delete、可选 tombstone、新 Key 的 create，公共发射器还提供新旧 Key 关联 header。
中途重启可能重发旧 Key 的 delete。下游应使用幂等写入/删除，不要只靠统计消息数推断数据库当前行数。
TRUNCATE 没有逐行 Key，多分区消费时不能假定其与所有分区内消息具有全局顺序。

=== 结构变更事件与内部 history

启用 `include.schema.changes` 时，结构变更 Topic 的 Key 包含 `databaseName`，Value 包含 `source`、`ts_ms`、`databaseName`、`schemaName`、`ddl` 和 `tableChanges`。
`tableChanges` 描述 CREATE、ALTER、DROP 等结构变化，包含列、主键和表标识等结构化信息；它不是一条业务行。
初始结构快照也会生成结构事件，DDL 文本可能为空。消费者应读取结构化定义，不能假定每条记录都有可执行 SQL。

[source,json]
----
{"databaseName":"DAMENG"}
----

单次加列事件的字段片段示意：

[source,json]
----
{
  "databaseName": "DAMENG",
  "schemaName": "APP",
  "ddl": "ALTER TABLE APP.CUSTOMERS ADD EMAIL VARCHAR(200)"
}
----

内部 history 保存恢复所需的完整结构、位置和达梦对象属性；结构变更 Topic 是面向消费者的通知，两者不可互相替代。
不要从业务结构事件手工拼出 history，也不要清空 history 后保留旧 offset 继续采集。

=== 事务元数据

设置 `provide.transaction.metadata=true` 后，事务 Topic 发布如下形式的边界消息，业务事件附带 transaction 字段：

[source,json]
----
[
  {"status":"BEGIN","id":"example-transaction","ts_ms":1792368000000,"event_count":null,"data_collections":null},
  {"status":"END","id":"example-transaction","ts_ms":1792368000100,"event_count":2,
   "data_collections":[{"data_collection":"APP.CUSTOMERS","event_count":2}]}
]
----

[source,json]
----
{"id":"example-transaction","total_order":1,"data_collection_order":1}
----

`total_order` 是已发出的事务数据事件顺序，`data_collection_order` 是该表在事务内的事件顺序，均从 1 开始。
计数反映捕获范围和事件处理路径，不等于数据库原始事务修改的所有行数，也不包含 tombstone 作为新的行变更。
达梦 BEGIN 的时间来自所处理的日志行，END 使用 Connector 处理时间；不能将两者差直接当作数据库事务执行时长。
事务元数据提供下游重组依据，但不会让多个业务 Topic 的消息自动原子可见。

[id="dameng-data-types"]
== 数据类型映射

以下为原生模式的默认映射。以实际 JDBC 物理类型和历史 DDL 为依据，不能只按另一数据库同名声明推断。
JSON 中 bytes 常呈 Base64；Decimal 的 JSON 表示还取决于 Converter 设置，不能把 Connect BYTES 直接理解为业务字符串。

[cols="3,2,5",options="header"]
|===
|达梦类型/物理类型 |Connect 类型 |逻辑含义与限制
|BOOLEAN、单比特 BIT |BOOLEAN |true/false；多比特声明须按实际物理映射验收。
|TINYINT、SMALLINT |INT8、INT16 |分别对应 8/16 位整型，输入边界以达梦实际接受范围为准。
|INT/INTEGER、BIGINT |INT32、INT64 |保持整型值；消费端不要用不能精确表示大整数的浮点类型接收 BIGINT。
|REAL / 物理 REAL 的 FLOAT(p) |FLOAT32 |日志文本可能损失精度，见下文。
|DOUBLE / 物理 DOUBLE 或 FLOAT |FLOAT64 |FLOAT(p) 声明在不同模式/参数下可能映射不同，不按名字固定为单精度。
|DECIMAL(p,s)、NUMERIC(p,s)、NUMBER(p,s) |BYTES |默认逻辑类型 `org.apache.kafka.connect.data.Decimal`，保留 scale；string/double 模式改为 STRING/FLOAT64。
|未限定精度的 NUMBER/NUMERIC/DECIMAL |STRUCT |物理 DECIMAL/NUMERIC 元数据长度非正时，precise 下为 `io.debezium.data.VariableScaleDecimal`，包含 scale 和非标度 value；不将不同 scale 强行统一。
|CHAR、NCHAR、VARCHAR、VARCHAR2、NVARCHAR 等字符列 |STRING |CHAR/NCHAR 保留定长空格；按历史字节长度和字符集补齐 LogMiner 省略的 padding。
|BINARY、VARBINARY、RAW |BYTES |或按 binary.handling.mode 输出 Base64、URL-safe Base64、hex 字符串。仅二进制列将日志 `'0x'` 解为空数组，文本列仍为文字。
|DATE |INT32 |adaptive 下 `io.debezium.time.Date`，距 1970-01-01 的天数；保留公元前年份语义。
|TIME(p)，p ≤ 3 |INT32 |`io.debezium.time.Time`，午夜起毫秒；原生 TIME 未声明精度时 p=0。
|TIME(p)，4 ≤ p ≤ 6 |INT64 |`io.debezium.time.MicroTime`，午夜起微秒。
|TIMESTAMP/DATETIME，p ≤ 3 |INT64 |`io.debezium.time.Timestamp`，以毫秒编码无时区日历时间，不代表已获知写入会话时区。
|TIMESTAMP/DATETIME，4 ≤ p ≤ 6 |INT64 |`io.debezium.time.MicroTimestamp`，微秒精度。
|TIMESTAMP，7 ≤ p ≤ 9 |INT64 |8.1.3.162 可接受声明，默认映射 `io.debezium.time.NanoTimestamp`。仅约 1677 至 2262 年可用 INT64 纳秒表示；0001/9999 年的 snapshot 和 streaming 实测告警后输出 null，不能宣称完整数据库时间范围无损。
|TIME WITH TIME ZONE |STRING |`io.debezium.time.ZonedTime`，归一到 UTC 时刻，跨午夜不附加日期；旧 8.1.2.128 小数秒受限，8.1.3.162 的 TIME(1..6) WITH TIME ZONE 严格矩阵已通过。
|TIMESTAMP WITH TIME ZONE |STRING |`io.debezium.time.ZonedTimestamp`，保留瞬时和小数秒，归一 UTC，不保留最初写入的偏移格式。
|INTERVAL |STRING |`io.debezium.time.Interval` version 1，保留年/月或日/时间单位及精确十进制秒。
|CLOB / BLOB |STRING / BYTES |快照可读取完整内容；流式行外值不完整时输出不可用占位值，非完整 LOB CDC。
|TIMESTAMP WITH LOCAL TIME ZONE |不支持 |JDBC 依赖读取时区、无字典日志缺失写入时区，不能安全统一解释。
|复杂对象、集合及无已验证映射的类型 |不支持 |明确报 schema 错误，不静默丢列。公共转换器中出现 XML/ROWID 等分支不代表达梦已完成其 CDC 验收。
|===

=== Decimal、时间和默认值

decimal.handling.mode=precise 保留固定 scale 或 VariableScaleDecimal；string 避免下游十进制类型限制；double 可能损失有效位。
`time.precision.mode=connect` 使用 Kafka Connect Date/Time/Timestamp，只保证毫秒；其他公共模式的单位见参数说明。
TIMESTAMP(7..9) 等高精度声明、超大 NUMBER 和中文 CHAR 长度边界在旧构建上存在声明或驱动/存储限制。
8.1.3.162 复测后，中文 CHAR 边界、ROWID 普通列用例及部分高精度时间通过；超大 NUMBER 和纳秒时间的极端年份仍失败。版本差异和具体用例见 <<dameng-regression-813162,新版本回归>>，不能把某些边界通过扩大为整个类型全范围无损。
日期按原始日历文本解析，避免旧 JDBC java.sql.Date/Timestamp 丢失 BCE 年代；接受日志中不补零的年份，不使用 JVM locale 猜测格式。
LogMiner TO_DATE/TO_TIMESTAMP/TO_TIMESTAMP_TZ 仅解析已支持的 ISO 格式，例如 YYYY-MM-DD、YYYY-MM-DD HH24:MI:SS.FF6 和带 TZH:TZM 的形式。
不支持表达式或格式会失败，CURRENT_TIMESTAMP 等表达式默认值不会在 Connector 中当场求值来伪造历史值。

INTERVAL 覆盖 13 种 year/month 和 day/time qualifier，leading precision 1～9、fractional seconds 0～6。
`INTERVAL '12-3' YEAR TO MONTH` 输出 `P12Y3M0DT0H0M0S`；负日时间可输出 `P0Y0M-2DT-3H-4M-5.123456S`。
保留零分量并去除秒小数末尾零，不将月近似换算成天，也不将完整范围挤入可能溢出的微秒整数。
列默认 leading precision 为 2，字面值默认 9；非法范围、子字段或精度拒绝，不悄悄舍入。

=== 已知一致性边界

81 项失败实例的分类、生产影响、处理条件及逐项索引见 <<dameng-datatype-failures-20261020,字段边界失败分析>>。

测试构建将 REAL/FLOAT/DOUBLE 的 SQL_REDO 输出为六位小数，小非零值可能变成零，相邻浮点值可能合并。
带时区 TIME 的日志可能只保留秒，即使 JDBC 快照有小数秒。在线字典 MINE_VALUE 也观察到相同损失；无字典接口不能按文档逻辑列名可靠读取替代值。
日志已缺失的信息无法从文本推回，也不能用当前表行修复旧更新或已删除行。
精确一致性要求涉及这些字段时，必须验证能保留原值的数据库构建和接口。

原始 Connect 浮点值保留负零；旧 8.1.2.128 可写入的 NaN 也有原始事件回归，但 8.1.3.162 配合当前 JDBC 驱动会在 NaN 写入时返回 Data overflow。
已验证的 Kafka 4.3.0 schema-enabled JsonConverter 在往返解码中可能丢失负零；旧版本 NaN 编成字符串后数值解码为零的问题，不能用新版拒绝写入来宣称修复。
这是序列化往返问题，不是原始 Connector 值相同；其他 Converter/Worker 版本须分别验收。
LOCAL TIME ZONE 不能通过“统一假设 UTC，再转换到用户时区”修复，因为 snapshot 与 redo 的原始时间基准不同且历史写入时区缺失。
排除现有列可以避免其值映射，但不保证声明该类型的历史 DDL 可以重放。

流式 `OUT_CLOB` / `OUT_BLOB` 或被省略的 LOB before-image 使用 unavailable.value.placeholder，BLOB 标记经过 UTF-8 和所选二进制模式编码。
显式 SQL NULL 保持 null；消费者应区分缺失值、NULL 和真实字段内容。

=== 自定义转换器

`converters` 扩展数据库类型到 Connect 值；Worker 的 key.converter/value.converter 把 Connect 记录序列化；SMT 在 Worker 流程中变换记录，三者用途不同。
达梦没有照搬 Oracle 的 NUMBER(1)→Boolean、NUMBER→Zero Scale、RAW→String 专用转换器。
需要时自行提供 SPI 实现，配置别名和 `<alias>.type`，验证 Key、schema、snapshot、streaming、默认值和历史恢复一致性。
转换器不能恢复数据库日志已经舍弃的浮点位或时区信息。

== 数据库端配置与权限

本文供数据库管理员在部署 {prodname} 达梦 Connector 前核查数据库。
以下要求针对初始快照和持续 LogMiner 采集，适用于单机或由管理员人工切换的主备部署。
部署前先核对 <<dameng-support-matrix,兼容模式、版本测试与部署模式矩阵>>，确认实际构建、驱动及采集节点是否在已验证范围内。
旧 DM8 `08134283904-20220804-166351-20005` 与新测试基线 `03134284194-20240621-232765-20108` 均使用 `DmJdbcDriver18` `8.1.3.140` 回归；通过范围和失败项见版本测试矩阵，不能将“执行过测试”等同于全部验收通过。
Connector 每次启动 Task 时，通过 JDBC 标准 `DatabaseMetaData` 接口读取并以 INFO 记录数据库产品名、版本字符串和主次版本。
两个测试构建分别返回 `DM DBMS` / `8.1.2.128` 和 `DM DBMS` / `8.1.3.162`，主版本均为 `8`、次版本均为 `1`；数据库版本与 JDBC 驱动版本不同。
未匹配代码中已测试版本名单，或无法读取版本元数据时，仅打印 WARN 并继续启动。
JDBC 版本匹配不能唯一识别数据库构建，也不代表所有数据一致性测试都已通过。
Connector 不会自动修改数据库参数或启用归档。

=== 必需参数和归档

|===
|数据库配置 |目标值 |用途和核查依据
|本地归档与 `ARCH_INI` |通常设 `ARCH_INI=1`；`V$DATABASE.ARCH_MODE` 必须显示已开启 |达梦 `DBMS_LOGMNR` 读取归档日志。官方 https://eco.dameng.com/document/dm/zh-cn/pm/logmnr-interface-instructions.html[LogMiner 说明]使用 `ARCH_INI=1`；Connector 校验实际归档模式，而非只读取 `ARCH_INI`。

`RLOG_APPEND_LOGIC` 与 `RLOG_LLOG_COMPRESS` 的 LogMiner 行为见 https://eco.dameng.com/document/dm/zh-cn/pm/dbms_logmnr-package.html[达梦 DBMS_LOGMNR 文档]。
`RLOG_IGNORE_TABLE_SET=0` 时，任务配置者必须在采集开始前按当前达梦版本的官方操作方法，为每张实际捕获的表开启表级逻辑日志；配置了信号表时，信号表及后续新增的采集表也必须分别处理。
Connector 只打印启动警告，不查询或验证各表的日志设置，也不会代替 DBA 开启日志。缺失表级日志时，任务可能继续运行却静默漏掉变更；事后启用日志无法补回之前未写入的变更。
使用自动创建信号表时，应在该表创建后、发送信号前启用其表级逻辑日志。
`COMPATIBLE_MODE` 和 `LENGTH_IN_CHAR` 的目标值仍是 Connector 的启动条件，见 <<dameng-connector,Connector 说明>>。
即使暂不采集 BLOB/CLOB，也要保留以上非 LOB 行像设置。
词法参数在主备节点上必须一致，并在需要重放的归档区间内保持不变。
当前参数不能证明旧 DDL 生成时的词法设置；修改这些设置前应另行规划历史衔接，不能仅重启任务后沿用旧 offset。
Connector 将这些实际设置保存为 offset 的 `compatibility_signature`，启动恢复 history 前和运行期间会核对，变化时停止。
旧版没有该签名的 offset 也会拒绝恢复；升级需规划新 Connector 身份、新 offset/history 和初始快照，不能手工给旧 offset 补一个当前签名。
检查不能恢复历史参数，也不能发现两次检查之间修改后又改回的情况，因此不能替代数据库侧的参数变更管理。
只有确认临时参数下没有生成受影响的历史，才能改回原值后继续旧 offset；否则应重新建立采集基线，不能仅凭当前签名重新相等判断安全。

测试容器使用 `SP_SET_PARA_VALUE(2, ...)` 设置 `RLOG_APPEND_LOGIC` 和 `RLOG_IGNORE_TABLE_SET`，且仅在数据库提供 `RLOG_LLOG_COMPRESS` 时将其设为 `0`，随后启用本地归档并重启数据库。
生产库应由 DBA 根据当前 DM8 版本的参数生效规则、维护窗口和既有归档配置实施；测试容器的归档路径、`FILE_SIZE=64` 和 `SPACE_LIMIT=1024` 不是生产容量建议。
设置或重启后，在每个可能成为主库的节点上检查*实际生效值*：

[source,sql]
----
SELECT PARA_NAME, PARA_VALUE
FROM V$DM_INI
WHERE UPPER(PARA_NAME) IN (
    'ARCH_INI',
    'RLOG_APPEND_LOGIC',
    'RLOG_IGNORE_TABLE_SET',
    'RLOG_LLOG_COMPRESS',
    'COMPATIBLE_MODE',
    'LENGTH_IN_CHAR',
    'BACKSLASH_ESCAPE',
    'NESTED_C_STYLE_COMMENT',
    'IDENTIFIER_MODE'
)
ORDER BY PARA_NAME;

SELECT ARCH_MODE FROM V$DATABASE;
SELECT SF_GET_CASE_SENSITIVE_FLAG();
SELECT MODE$, STATUS$ FROM V$INSTANCE;
SELECT PATH, ARCH_LSN, CLSN
FROM V$ARCH_FILE
WHERE PATH IS NOT NULL
ORDER BY ARCH_LSN;
----

`ARCH_MODE` 应为启用状态；当前 Connector 接受 `Y`、`1` 或 `ARCHIVE`。
核查 `V$ARCH_FILE` 中存在本地归档，对应文件仍在数据库服务器上，且需要恢复的 LSN 区间没有缺口。
当前 Connector 只读取归档文件，尚未归档的日志会增加变更事件延迟。
归档保留应覆盖最老未完成事务、Connector 积压、Kafka 或网络故障、人工切换与恢复所需时间。
本地归档达到空间上限时可能删除最旧文件；丢失所需文件后，Connector 会停止而不会跳过缺口。

=== CDC 账号

在上面注明的 DM8 版本中，以下权限已用于验证 JDBC 元数据读取、共享快照锁和 LogMiner。
先由 DBA 创建账号，再将示例中的用户、schema 和表名替换为实际值：

[source,sql]
----
GRANT SOI TO CDC_USER;
GRANT VTI TO CDC_USER;
GRANT EXECUTE ON DBMS_LOGMNR TO CDC_USER;
GRANT SELECT ON APP.CUSTOMERS TO CDC_USER;
GRANT SELECT ON APP.ORDERS TO CDC_USER;
----

若 `CREATE SESSION` 已被撤销，需补授连接权限。
每张新纳入采集的业务表也需授予 `SELECT`。
初始快照通过当前账号的 `ALL_TABLES` 发现表；不可见的表不会进入快照范围。
最终发现完成后，Connector 以 INFO 输出实际选择的结构采集表和数据快照表，并对没有选择到任何可见表的 `table.include.list` 规则打印 WARN。
该警告不会停止任务，也不能单独证明权限不足；请同时核对表是否存在、名称大小写及其他过滤条件。
如果使用源端信号表执行增量快照，账号还需对信号表写入信号和水位记录的权限。
这组权限无需 `DBA` 或 `SELECT ANY TABLE`，但 `SOI` 和 `VTI` 是较宽的系统目录读取角色；应在实际 DM 版本验证授权。
`SOI` 允许读取非安全、非审计系统表，包括对象与约束目录；`VTI` 允许读取系统动态视图，包括运行状态和 LogMiner 视图。
这是一组已经验证可用的权限，不是已证明不可再缩小的最小权限集。基线构建拒绝对 SYS.SYSOBJECTS、SYS.SYSCONS 直接进行对象级授权，不能用未经验证的单对象 GRANT 替代。

=== 主备与人工切换

对两个可能成为主库的成员分别执行上述参数、归档、权限和连接核查。
当前 Connector 只支持单实例成员（`N_EP=1`）和唯一可写主库；主备归档复制及切换由达梦 Data Guard 和 DBA 管理。
两端均需保有本地归档，实时归档通道应健康，且新主库要有覆盖 Connector 已确认位置的连续归档历史。
切换前确认备库已应用所需日志，切换时隔离旧主写入，切换后确认恰好一个成员在 `V$INSTANCE` 中报告 `PRIMARY`、`OPEN`。
Connector 通过 `database.failover.hosts` 配置两个 JDBC 地址，无需 VIP；它不会发起升主或修复丢失的归档。
详细的恢复边界和配置见 <<dameng-primary-standby-recovery,主备恢复说明>>，达梦复制与归档的管理要求见 https://eco.dameng.com/document/dm/zh-cn/pm/data-watch-overview.html[达梦 Data Guard 文档]。

完成配置后，先在测试表验证快照，再提交 INSERT、UPDATE 和 DELETE 并检查 Kafka 事件；随后重启 Connect worker，确认任务能够从已保存的 offset 继续采集。

=== 内置过滤和表存储类型

默认 table.ignore.builtin=true，代码内置排除 SYS、SYSTEM 和名称以 V$ 开头的 schema；这不是所有系统对象的完整清单。
SYSDBA 下某表或其他 schema 的系统用途表不一定被这一规则自动排除，生产应显式指定业务表过滤器并核对启动清单。
普通行表和已验证分区根表可以采集，临时/HUGE/外部表和生成列限制见 DDL 章节。
信号表自动创建及额外写权限见 <<dameng-signals,信号表>>。

=== 插件和运行时

将 assembly 产出的插件归档解压到 Worker 的 `plugin.path` 独立目录，保留依赖和 `DmJdbcDriver18`，然后重启所有可能调度到该 Task 的 Worker。
不要把打包时排除的 Kafka API JAR 随意塞回插件目录覆盖 Worker API。
默认 Dockerfile 在 Apache Kafka 3.9.1 镜像中安装本分支插件、驱动、环境变量配置脚本及 JMX Exporter 1.4.0；默认产物为 Linux amd64 / Java 21，启动时默认启用 `9404/metrics`。
镜像默认 JVM 堆参数为 `-Xms4G -Xmx4G`。可通过 `HEAP_OPTS` 或 `KAFKA_HEAP_OPTS` 覆盖；同时设置时 `HEAP_OPTS` 优先。
Oracle 模块的官方镜像配置来自统一镜像项目，本分支达梦的 Dockerfile 和脚本是自己的部署入口。

|===
|层次 |当前值 |含义
|Connector 项目版本 |`3.6.4-xingchuang-kafka2.0` |插件版本，不是 Broker 或客户端版本。
|Maven Kafka 依赖 |`4.3.0` |编译及默认独立测试进程使用的依赖；项目版本改名不会改变它。
|Kafka 2.0 部署镜像的 Worker |`3.9.1` |使用仍保留旧 Broker 协议的 Worker/client 运行插件；不是将 Broker 升到 3.9。

=== Kafka 2.0 的 Topic 准备

当前 history 客户端创建 Topic 时的请求与 Kafka 2.0 存在兼容限制，需提前创建 history Topic。
以下副本数 1 仅用于单 Broker 测试，生产根据 Broker 数量和可用性要求设置：

[source,shell]
----
kafka-topics --zookeeper ZOOKEEPER_HOST:2181 --create \
  --topic dameng-schema-history --partitions 1 --replication-factor 1 \
  --config cleanup.policy=delete --config retention.ms=-1 \
  --config retention.bytes=-1
----

history 不使用 compaction，其记录 Key 为 null；需要完整历史，并与任务配置的名称一致。
Worker 内部配置/offset/状态 Topic 则按 Kafka Connect 要求保留并启用 compaction，配置 Topic 单分区，不能套用 history 的策略。
Broker 关闭自动建 Topic 时还需预建业务、结构、心跳、事务等实际使用的 Topic。
Worker 保持 `exactly.once.source.support=disabled`。

=== Docker Compose 与环境变量

将下面服务加入现有 Kafka Compose，并接入与 Kafka 可互通的网络；`kafka:9092` 必须是容器可达的 Broker advertised.listeners 地址。
外部数据库地址也必须从容器内可达，`localhost` 指向容器本身。

[source,yaml]
----
services:
  dameng-connect:
    image: debezium-connect-dameng:3.6.4-xingchuang-kafka2.0
    restart: unless-stopped
    ports:
      - "8083:8083"
    environment:
      BOOTSTRAP_SERVERS: "kafka:9092"
      GROUP_ID: "dameng-connect"
      CONFIG_STORAGE_TOPIC: "dameng-connect-configs"
      OFFSET_STORAGE_TOPIC: "dameng-connect-offsets"
      STATUS_STORAGE_TOPIC: "dameng-connect-status"
      CONNECT_CONFIG_STORAGE_REPLICATION_FACTOR: "1"
      CONNECT_OFFSET_STORAGE_REPLICATION_FACTOR: "1"
      CONNECT_STATUS_STORAGE_REPLICATION_FACTOR: "1"
      CONNECT_EXACTLY_ONCE_SOURCE_SUPPORT: "disabled"
      HEAP_OPTS: "-Xms4G -Xmx4G"
    volumes:
      - /srv/dameng-connect-spill:/var/lib/dameng-spill
----

部署前创建并授权落盘目录给镜像运行用户，按全部 Task、遗留目录和其他进程预留磁盘空间；不要使用 tmpfs 代替磁盘。
4 GiB 堆不是容器总内存限制；容器内存还需覆盖 JVM 堆外、JDBC 和运行时开销。现有 Compose 中显式配置的堆参数会覆盖新镜像默认值。
需在 REST config 中设置 `log.mining.buffer.spill.path=/var/lib/dameng-spill`；只有 volume 不会改变 Connector 的默认临时目录。

[cols="3,4",options="header"]
|===
|环境变量 |Worker 属性或作用
|`BOOTSTRAP_SERVERS`、`GROUP_ID` |bootstrap.servers、group.id。
|`CONFIG_STORAGE_TOPIC`、`OFFSET_STORAGE_TOPIC`、`STATUS_STORAGE_TOPIC` |三个 Worker 内部 Topic。
|`CONNECT_<PROPERTY>` |去前缀、转小写、全部下划线转点，例如 CONNECT_OFFSET_FLUSH_INTERVAL_MS → offset.flush.interval.ms。
|`KEY_CONVERTER`、`VALUE_CONVERTER` |Worker Key/Value Converter 类。
|`REST_PORT`、`REST_HOST_NAME` |REST 端口/地址；未显式设置 CONNECT_LISTENERS 时脚本同步生成 listeners。
|`ADVERTISED_PORT`、`ADVERTISED_HOST_NAME` |REST 对外公布端口/主机。
|`OFFSET_FLUSH_INTERVAL_MS`、`OFFSET_FLUSH_TIMEOUT_MS` |offset.flush.interval.ms、offset.flush.timeout.ms。
|`SHUTDOWN_TIMEOUT` |task.shutdown.graceful.timeout.ms。
|`KAFKA_CONNECT_PLUGINS_DIR` |plugin.path，默认插件位于 /opt/kafka/plugins。
|`HEAP_OPTS`、`KAFKA_HEAP_OPTS` |Worker JVM 堆选项，镜像默认 -Xms4G -Xmx4G；HEAP_OPTS 优先于 KAFKA_HEAP_OPTS。
|`KAFKA_OPTS` |默认含内置 JMX Exporter 的 -javaagent 参数。显式设置会覆盖镜像默认值；增加其他 JVM 选项时需保留该参数。设为空字符串可关闭 Agent。
|===

显式短名称优先于对应 CONNECT_ 变量。可以只读挂载 `/etc/kafka/connect-distributed.properties` 作为基础文件，环境变量覆盖同名属性。
脚本生成的运行配置仅容器用户可读，启动时不输出敏感值。
默认镜像 JsonConverter 的 key/value schemas.enable 均为 false；若下游依赖逻辑类型元数据，显式配置并验证序列化契约。

=== 验证运行与重启

同时检查 Connector 和 Task 状态，Connector 显示 RUNNING 时其 Task 仍可能 FAILED。
观察启动版本、兼容参数、捕获表清单和 streaming 日志。在测试业务表提交 INSERT、UPDATE、DELETE，消费相应业务 Topic 检查 Key、before/after、op 和顺序。
默认 no_data 不会发启动前已有的行；未提交事务不会发；日志尚未归档时也可能暂时看不到事件。
验证一次 Worker 重启和离线期间 DDL/DML 的恢复，保留至少一次语义允许的重复。

[source,shell]
----
curl -fsS http://localhost:8083/connectors/dameng-cdc/status
curl -fsS -X PUT http://localhost:8083/connectors/dameng-cdc/pause
curl -fsS -X PUT http://localhost:8083/connectors/dameng-cdc/resume
curl -fsS -X POST http://localhost:8083/connectors/dameng-cdc/tasks/0/restart
----

pause 不是删任务或清 offset，也不应依赖它立即释放所有资源；需要停止时使用当前 Worker 支持的 stop API。
restart 不会修复缺档、不支持 DDL 或资源上限，先按故障章节解决原因。

== Connector 参数参考

参数写在 REST 请求的 `config` 中。下表默认值取自当前分支，容量单位为字节、时间单位以参数名为准。
空值或无默认值不等于必填；仅明确标为必填的项目必须配置。
Connector 参数、Worker 参数和数据库参数是三层不同配置，例如 `CONNECT_MAX_QUEUE_SIZE` 只生成 Worker 属性，不会替任务设置 `max.queue.size`。
本节覆盖当前公开配置描述中的字段，以及实际读取但由公共服务或 history/Topic 组件另外定义的配置；内部调试开关不作为受支持的生产接口。

=== 身份与数据库连接

[cols="3,2,5",options="header"]
|===
|参数 |默认值 |用途与限制
|`name` |无，必填 |POST 请求外层的 Connector 名称，必须唯一；PUT 使用 URL 中名称，不把外层对象放入 config。
|`connector.class` |无，必填 |固定 `io.debezium.connector.dameng.DamengConnector`，不要写简称 `dameng`。
|`tasks.max` |Worker 默认 `1` |达梦只允许一个 Task，大于 1 会报错。
|`topic.prefix` |无，必填 |来源分区与 Topic 命名空间；使用字母、数字、点、横线和下划线。恢复时保持不变。
|`database.hostname` |无 |单地址模式主机/IP；配置 failover.hosts 时可省略。
|`database.port` |`5236` |JDBC 监听端口。
|`database.user` |无，必填 |CDC 账号，所需权限见数据库配置章节。
|`database.password` |无 |CDC 账号密码；生产配置应使用 Worker 支持的外部配置提供器。

|`database.failover.hosts` |空 |同一主备数据库的 `host:port` 列表，IPv6 写 `[address]:port`；覆盖 hostname/port，仅选择 OPEN PRIMARY。
|`database.standby.hosts` |空 |备库采集的 `host:port` 列表；非空时 LogMiner、初始快照和增量快照读取仅连接 OPEN STANDBY，现有数据库地址用于主库信号写入和初始快照锁。可与 failover.hosts 使用相同的成员列表，驱动按角色选择。两条连接使用相同的数据库账号，须属于同一物理数据库家族。

|`database.query.timeout.ms` |`600000` |非负，正数向上取整为秒后应用 statement timeout；0 关闭语句超时，但不关闭网络和快照总时限。

[id="dameng-recovery"]
== 恢复、升级与主备切换

=== 普通重启

正常恢复保留 Connector 身份、offset、完整 schema history 和所需归档，从已确认位置重放。
`source.lsn` 可能小于最近发出的 `change_lsn`，因为未完成事务仍需要旧日志。
临时落盘缓存不能替代归档，进程重启不会将旧临时文件作为恢复状态。
所需归档已清理、history 缺失或身份不一致时停止；修改为 `no_data` 不会自动跳过错误位置。

升级前保存 REST 配置、读取 Worker 支持的 `GET /connectors/{name}/offsets`、保留旧镜像和存储。
缺失 `compatibility_signature` 或 `capture_scope` 的旧 offset 不能通过填入当前参数伪造历史解释条件。
通常使用新 Connector 名称、`topic.prefix` 和 history Topic，再显式 `snapshot.mode=initial` 重建；默认 no_data 不会补齐存量。
同一个逻辑来源不能同时由两个实例共享同一 history 并写入不同恢复状态。

=== 显式从当前 LSN 重建基线

故障处置允许主动丢弃旧积压时，在完整 REST 配置中设置新 nonce：

[source,json]
----
{
  "recovery.restart.nonce": "incident-20261019-01",
  "recovery.incremental.snapshot.auto.start": "false"
}
----

这会跳过旧位置到新基线之间的历史变化，包括中间更新、删除和旧主键，不是无损恢复。
默认只恢复 CDC，即使配置了 `snapshot.mode=initial` 也不扫描存量行。需要时由人工稍后发送增量快照信号。
设置 auto.start 为 true 才会在新基线创建时安排已捕获业务表的增量快照，要求信号表及全部目标表的主键；单独改该开关不会重新安排。
nonce 最多 128 个不含空白的可打印 ASCII 字符；同值、移除或空白均恢复当前世代，使用历史中较早的旧值会拒绝。
`initial_only` 不能与恢复 nonce 组合；Connector 名称、source partition 和业务 Topic 不因 nonce 改变。

恢复仍需共享锁、当前结构和对象编号，等待已写捕获表的事务结束后选择当前 LSN，持锁到基线持久化完成。
因此不扫描行也可能等待长事务，且受快照总时限约束。之前只写其他表的事务可以在解锁后写入捕获表，其基线之后的部分正常采集，回滚重建不越过新基线。
随后等待归档覆盖新 LSN，并保留新的安全重放范围。

新世代的 nonce、完整结构、baseline offset、兼容签名和可选补数计划先持久化在一条 history 记录中，随后才允许事件确认新位置。
Worker 尚未保存新业务 offset 就崩溃时，也从该 history 基线恢复，不重新选择更晚的起点；旧世代结构不会混入新世代。
完整基线必须放得进单条 Kafka 消息，受 producer、Topic 和 Broker 大小限制；写入失败不会开始新 CDC，失败快照通知也不能确认不存在的基线。
history 必须持久、完整、可读且由该 Connector 独占。数据库角色、身份和兼容检查继续生效。
日志记录请求和新旧位置，JMX 暴露 `RecoveryNonce`、`RecoveryBaselineLsn`；重置指标不清除基线。

增量快照只能补当前存在的行，无法发现跳过区间已经删除的行。下游仍可能保留陈旧行或旧主键，需对账或重建才能恢复精确副本。

[id="dameng-primary-standby-recovery"]
=== 无 VIP 主备恢复

成员必须属于同一数据库家族，单实例 `N_EP=1`，只允许一个可写主库，归档由 DM Data Guard 同步和管理。
用 `database.failover.hosts=dm-a.example.com:5236,dm-b.example.com:5236` 替代单地址；Connector 不升主、不修复复制、不隔离旧主，也不把 endpoint 列表当作脑裂检测。
官方架构依据为 https://eco.dameng.com/document/dm/zh-cn/pm/data-watch-overview.html[达梦数据守护说明]。

驱动使用服务组地址，并固定 `loginMode=1`、`loginStatus=4`、`rwSeparate=0`、`autoReconnect=0`、`switchTimes=1`、`switchInterval=200`。
这些参数在建连时选择 OPEN PRIMARY，重连由 Connector 按确认的 offset/history 管理。禁止冲突覆盖、透明切库、自动重连别名和读写分离。
连接失败或角色改变后，按 errors.max.retries 创建新会话并恢复，未确认事件可能重放。

计划 switchover 前确认备库已应用所需 redo、两地址可达；DBA 用 DM 工具切换，检查恰好一个 PRIMARY/OPEN，实时归档通道健康。
不改变地址列表、offset 或 history，观察 Task 和 OldestReplayLsn 恢复。
主库故障时先隔离旧主写入，在确认所需日志已应用后执行非强制 takeover。
没有可用主库时按重试策略等待；新主库落后、身份链缺失或归档分叉时停止，不能仅因其当前 LSN 较大就继续。

恢复校验 PERMANENT_MAGIC、与存储 database_magic 对应的 SYS.SYSOPENHISTORY 锚点、连续来源主库链，以及每次 open 的 applied LSN 是否覆盖已存 replay/change/commit 位置。
offset 还保存 permanent_magic、primary_open_guid。挖掘中刷新身份，发布前锚点改变则放弃该窗口。
DM open history 最多保留 128 条，锚点轮转丢失、时间戳排序歧义、应用 LSN 倒退或身份链不一致均拒绝恢复。
保持数据库时钟同步，监控切换频率及归档保留；强制有损切换不在已验证范围。

归档 DB_MAGIC 标识本地写入库，SRC_DB_MAGIC 标识 redo 来源，复制后两者可不同。
校验整个文件的身份和范围，不仅检查窗口内部分；允许共享包含式端点，但拒绝更大重叠、缺口或错误分支。
这些校验配合 DM 管理的归档，不认证人为混合的任意文件集合。
旧单地址 offset 缺少主备锚点，不能只增加 failover.hosts 升级；通常需新身份、新 history 和显式 initial，或按已声明的有损恢复流程建立新基线。

=== 备库采集与主库信号写入

使用支持备库 `DBMS_LOGMNR` 的数据库构建，在现有主库配置之外增加：

[source,json]
----
{
  "database.failover.hosts": "dm-a.example.com:5236,dm-b.example.com:5236",
  "database.standby.hosts": "dm-a.example.com:5236,dm-b.example.com:5236",
  "database.standby.replay.timeout.ms": "60000",
  "snapshot.mode": "no_data",
  "signal.data.collection": "CDC.DBZ_SIGNAL"
}
----

这是任务配置片段。两组成员地址可相同：主库连接使用 `loginMode=1`，备库连接使用 `loginMode=2`，均要求 `loginStatus=4`，关闭驱动自动重连和读写分离。
主库连接负责自动创建信号表、信号水位 INSERT/DELETE、配置的 heartbeat.action.query 以及初始快照的共享锁；LogMiner、表结构、对象编号和快照行数据从备库读取。
用户发出的 execute-snapshot 信号也应插入主库，不能对备库执行 INSERT。初始快照即使从备库读取，仍会在主库持有共享锁，因此不能理解为对主库写入完全无影响。
两条连接使用 database.user/password。账号在主库具有已说明的元数据、表 SELECT/锁及信号表写入权限，在备库具有动态视图、元数据、业务表读取与 LogMiner 权限；不允许写入任意其他数据库家族。

流水线的安全边界为 `min(归档上界, V$RAPPLY_SYS.SLSN, V$RAPPLY_PARALLEL_INFO.RPKG_LSN)`。
SLSN 表示确认允许重演的日志，RPKG_LSN 表示重演已经完成；备库刚收到但尚未确认或尚未重演的归档不能用于推进可发布位置。
挖掘前后校验角色、数据库身份和重演边界。offset 的 database_magic/primary_open_guid 保存来源主库历史，归档 DB_MAGIC 仍检查实际读取成员，SRC_DB_MAGIC 检查来源链。
来源主库变更时重启 Task，并从持久化 offset 重建事务缓存，不把旧主库未确认尾部带入新窗口。

初始快照先在主库锁住捕获表，再取主库 LSN，等待备库重演完成，随后从备库读取结构和数据，最后释放主库锁。
`no_data` 使用相同的结构边界但不扫描存量行；recovery.restart.nonce 的新基线也遵循该边界。
增量快照在主库提交低水位后，等待备库重演到该位置，结束备库之前的读事务，再读取分块，最后在主库提交高水位。
这样低水位之前的删除和更新已经对备库查询可见，避免因为备库落后而补回陈旧行；窗口内变更继续由原有去重逻辑处理。
两种 watermarking.strategy 均使用主库写连接。等待超时、连接中断或角色改变时，未完成的协调操作进入 Task 恢复，不把它当作成功完成的分块。
备库增量快照的分块读取失败也不会走公共实现的跳表路径，不会把失败表记为已跳过后继续确认位置。可重试的连接故障受 errors.max.retries 控制，权限、SQL 超时等错误仍须处理原因后恢复。

人工切换仍由 DBA 执行。列表包含两个成员时，Task 重建后分别选择新的主库和备库；只有固定单节点地址时需由运维更新对应配置。
已实测的切换瞬态包括 JDBC `6091`（无符合角色的成员）、`-6508 / 25000`（事务被 MOUNT 中断）及 `-510 / 22000`（查询时处于 MOUNT）；在启用主备身份检查的连接配置下，按既有重试预算重建会话。
没有可用 OPEN STANDBY 时不会偷偷转成主库采集。例如只有两个节点且主库宕机、备库升主之后，须等另一个成员重新成为可用备库才可恢复备库采集。
缺失的归档、丢失的历史锚点、强制有损切换和 DMDSC 仍按现有规则拒绝。服务需要读取本地的 RPKG_LSN，不能用主库中存在反馈延迟的 V$ARCH_APPLY_INFO 替代。

=== 快照共享锁指标与日志

当前锁指标为 `SnapshotLockWaiting`、`SnapshotLocksHeld`、`LockedTableCount`、`SnapshotLockWaitDurationMillis`、`SnapshotMaxLockWaitDurationMillis`、`SnapshotLockHoldDurationMillis`。
持锁时间从第一把共享锁成功开始，包含后续锁等待、结构/行读取、队列等待和 rollback 执行。获取耗时覆盖整个 LOCK TABLE JDBC 调用，不是纯数据库阻塞时间，两种耗时不能相加。
成功 rollback 后当前值立即归零，最近结果通过 `LastSnapshotLockStatisticsAvailable`、`LastSnapshotLockedTableCount`、`LastSnapshotLockWaitDurationMillis`、`LastSnapshotMaxLockWaitDurationMillis`、`LastSnapshotLockHoldDurationMillis` 保留五分钟或直到下次快照。
之后 availability=false、结果值归零；Grafana 应据 availability 显示“无近期结果”，不是“持锁耗时为零”。Prometheus 独立保留已采样历史。
reset 清除完成结果，但保留尚未释放事务的活动锁状态；重启会清除内存中的最近结果。

日志在每次加锁前 INFO 打印表名，成功后打印耗时，事务 rollback 成功后打印释放表数、累计/最大获取耗时及持锁时长。
获取失败和 rollback 失败会 WARN；rollback 失败明确标记释放未确认，不发布成功完成结果，清理前保留最后观察的状态。
增量快照不使用此类贯穿全表快照的共享锁，因此不能用这些指标度量增量查询全部数据库锁行为。

=== 增量快照进度与性能指标

增量快照使用 `context=snapshot` 下独立的 `IncrementalSnapshot*` 属性，不需要新增连接参数。
公共 `SnapshotRunning`、`RemainingTableCount` 等来自共用进度监听器，不能仅凭这些值区分初始和增量快照；共享表锁指标仅对应初始/结构快照持锁过程。
Grafana 的「Incremental Snapshot · 增量快照」区域独立展示当前表、阶段、剩余表数、读取与入队速度、Task 累计计数及每块耗时。

[cols="3,4,6",options="header"]
|===
|JMX 属性 |Prometheus 指标后缀 |定义与限制
|`IncrementalSnapshotRunning` |`running` |有未完成增量快照为 1，暂停时仍为 1；无未完成工作为 0。不是初始快照状态，也不是补数成功标志。
|`IncrementalSnapshotPaused` |`paused` |增量快照已暂停为 1；短暂停可能在抓取间隔之间发生。
|`IncrementalSnapshotPhase` |`phase{phase="..."}` |当前阶段的 info 风格样本，值为 1；阶段包括 idle、preparing、reading、waiting_close、emitting、paused、failed。阶段变化后旧标签在后续抓取中消失，不是永久累积的每阶段计数。
|`IncrementalSnapshotCurrentTable` |`current_table{table="schema.table"}` |当前表的 info 风格样本，值为 1；无当前表时不导出空表名。抓取可能漏过处理很快的小表。表标签不是每表累计行数；面板还按 running 过滤，失败后即使底层保留表名也会隐藏。
|`IncrementalSnapshotRemainingTableCount` |`remaining_tables` |尚未完成的增量快照表数，包含当前表；暂停保留，完成后为 0。不是剩余行数、完成百分比或 ETA。
|`IncrementalSnapshotRowsScanned` |`rows_scanned_total` |本 Task 生命周期内所有增量快照 JDBC 读到的累计行数，包括重读和随后被 CDC 去重的行。
|`IncrementalSnapshotRowsEnqueued` |`rows_enqueued_total` |本 Task 生命周期内增量快照行事件成功 dispatch 入队的累计条数；不含流式 DML，不代表 Kafka ack 或下游消费。
|`IncrementalSnapshotWindowsCompleted` |`windows_completed_total` |本 Task 生命周期内成功完成发送的窗口数；末块可不足 chunk.size，不能以块数乘块大小替代准确行数。
|`IncrementalSnapshotLastQueryDurationMillis` |`last_query_duration_seconds` |最近完成读块的耗时，含 JDBC 查询、取数、类型转换与构建去重缓存；进行中的查询不提前更新。
|`IncrementalSnapshotCurrentCloseWaitDurationMillis` |`current_close_wait_duration_seconds` |当前 CLOSE 写入提交返回后，等待对应 CLOSE 被处理的实时经过时间；只要已写 CLOSE 仍未处理就继续计时，暂停期间也可能增长；Grafana 仅在 waiting_close 显示是 UI 策略。
|`IncrementalSnapshotLastCloseWaitDurationMillis` |`last_close_wait_duration_seconds` |最近完成的 CLOSE 确认等待，含归档可见性、主备回放、挖掘与分发等待；不是纯 LogMiner 数据库耗时。
|`IncrementalSnapshotLastEmitDurationMillis` |`last_emit_duration_seconds` |最近完成本块缓存发送耗时，含转换、分发及队列等待；不含 Kafka 确认，进行中的发送不提前更新。
|===

表中 Prometheus 后缀均添加 `dameng_incremental_snapshot_` 前缀。
导出规则将毫秒换算为秒；字符串通过属性值生成 phase/table 标签，规则关闭 cache，避免阶段或表变化后仍沿用旧标签。
所有指标带 context 和 server，Prometheus 再附加 namespace、pod、job、instance 等抓取目标标签。
累计 counter 跨本 Task 的多次增量快照，Task 重启清零；不是本次快照或当前表的完成行数。
读取多于入队可能来自 CDC 去重、过滤或重新读取，不能直接把两者差值判定为丢数。

recording rules 新增 `dameng:incremental_snapshot_scan_rate_rows` 与 `dameng:incremental_snapshot_enqueue_rate_rows`，分别对读取和入队 counter 使用两分钟 rate，单位行/秒。
规则不合并 server 或 Worker，保留所有源和抓取标签；可见 counter reset 由 rate 处理，至少两个样本才有值。
块式更新和 rate 窗口会平滑或形成脉冲，暂停后短期仍可能显示先前两分钟的平均速度。
面板对运行期速度和最近耗时使用独立 running 标志过滤，任务完成后隐藏陈旧结果；最近耗时在活动任务中仍保留上一块结果，不能当成实时阶段计时。
累计卡片仍显示 Task 生命周期总量，Prometheus 中的历史曲线按其存储保留策略保留。
没有可靠总行数时不计算完成百分比或预计结束时间。

一次块处理按准备 OPEN、查询、写 CLOSE、等待 CLOSE 进入 CDC、发送缓存串行推进。
preparing 还可能包含写入 OPEN、主库提交、备库回放屏障以及读取前的准备，不完全包含在查询/CLOSE/发送三个最近耗时之内，三者不能当作完整阶段耗时占比。
当前阶段和当前表按抓取时刻采样，短阶段可能不可见。
定位慢速时按以下方向检查：

* reading 长：查主键/复合键索引、实际分块 SQL 与执行计划、JDBC 网络取数和类型转换；分别验证 snapshot.fetch.size 与 incremental.snapshot.chunk.size。
* waiting_close 长：查信号提交、归档可见性、备库安全回放边界、LogMiner 窗口扫描和分发。归档扫描积压为零不能排除此类等待，因为扫描上界不等于 CLOSE 已被处理。
* emitting 长：查事件队列满等待、Worker、序列化/SMT、Producer 请求延迟及 Broker；入队与 Producer 等待可能重叠，不能相加作为总耗时。
* preparing 长：检查 OPEN 写入权限/提交、主库连接及备库回放屏障日志，不要只盯着 LogMiner 积压。

更大的 chunk.size 可摊薄固定水位开销，同时增加去重缓存、单次查询/发送停顿和 CDC 延迟。用相同负载单参数对照，结合行宽和堆预算验证，不能保证按块大小等比例提速。
更新这一功能必须部署含新埋点的 Connector JAR 或镜像，同时更新 Exporter YAML、Prometheus rules 和 Grafana JSON。
只更新面板无法从旧 Connector 获取新属性；只更新 JAR 而不更新 Exporter 则不会导出对应 Prometheus series。
Kubernetes 使用 PodMonitor 时继续沿用原抓取端口与标签选择器，重新应用本目录的 PrometheusRule 即可加载两个新 recording rules；同一 Prometheus 只部署一份共享规则。

=== 配置 Prometheus Agent

监控资源位于仓库 `debezium-connector-dameng/docker/monitoring/`。Agent 1.4.0、Exporter YAML、recording rules、Grafana JSON 是可执行部署资源，使用说明集中在这里。
当前 Docker 镜像内置 `/opt/jmx/jmx_prometheus_javaagent-1.4.0.jar` 和 `/opt/jmx/jmx-exporter.yaml`，并通过默认 `KAFKA_OPTS` 启用 `9404/metrics`。
运行时无需挂载 Agent JAR 或默认配置。构建机准备 Agent 的命令如下；脚本校验官方发行 SHA-256，Docker 构建时也会再次校验：

[source,shell]
----
bash debezium-connector-dameng/docker/monitoring/fetch-agent.sh
----

使用内置默认配置时，Compose 只需发布监控端口。Prometheus 与 Connect 在同一 Docker 网络时，可以直接访问容器的 9404 端口，无需发布到宿主机：

[source,yaml]
----
services:
  dameng-connect:
    ports:
      - "9404:9404"
----

若 Compose 显式设置 `KAFKA_OPTS`，会覆盖镜像默认值；合并其他 JVM 参数时保留如下 Agent 参数，且只保留一份：

[source,yaml]
----
environment:
  KAFKA_OPTS: "-javaagent:/opt/jmx/jmx_prometheus_javaagent-1.4.0.jar=9404:/opt/jmx/jmx-exporter.yaml -Duser.timezone=UTC"
----

设置 `KAFKA_OPTS: ""` 可关闭 Agent。需要自定义指标规则时，可只读挂载自己的 YAML 覆盖 `/opt/jmx/jmx-exporter.yaml`；Grafana 面板和 Prometheus rules 仍分别交给 Grafana、Prometheus 加载。
从旧 Compose 迁移时，可以删除 Agent JAR 和默认 YAML 的两个 bind mount。保留旧挂载会覆盖镜像内置文件，宿主机文件路径仍必须存在；内网部署不应保留原开发机的绝对路径。
改变 javaagent 启动参数需要重建 Worker 容器；Connector 配置和 offset 依赖 Kafka 内部 Topic 保留，不存储在容器可写层。
Prometheus 与 Connect 同网络时可用下面抓取配置；不同网络时改为可达地址，不能照抄本机 localhost：

[source,yaml]
----
scrape_configs:
  - job_name: dameng-connect
    scrape_interval: 15s
    static_configs:
      - targets: ['dameng-connect:9404']
rule_files:
  - /etc/prometheus/dameng/prometheus-rules.yaml
----

挂载对应 rules 文件。Exporter 输出检查：

[source,shell]
----
curl -fsS http://localhost:9404/metrics
----

=== Kubernetes 与 Prometheus Operator

Kubernetes Worker 容器需要保留镜像中的 javaagent 启动参数，并在 Pod 模板声明指标端口：

[source,yaml]
----
ports:
  - name: metrics
    containerPort: 9404
    protocol: TCP
----

`docker/monitoring/kubernetes/pod-monitor.yaml` 提供 PodMonitor 样例，`prometheus-rule.yaml` 提供 Operator 的 PrometheusRule 样例。Pod 模板要有同名 `metrics` 容器端口，并让 PodMonitor 的 `spec.selector.matchLabels` 与 Pod 标签一致。将 PodMonitor 中的目标命名空间改为 Connect 所在命名空间后应用：

[source,shell]
----
kubectl apply -n debezium -f debezium-connector-dameng/docker/monitoring/kubernetes/pod-monitor.yaml
kubectl apply -n debezium -f debezium-connector-dameng/docker/monitoring/kubernetes/prometheus-rule.yaml
----

Prometheus Operator 的 Prometheus 资源必须通过 `podMonitorSelector` 选中 PodMonitor 标签，并通过 `podMonitorNamespaceSelector` 覆盖 PodMonitor 所在命名空间；PodMonitor 自身的 `spec.namespaceSelector` 决定要抓取哪些 Pod 命名空间。否则资源存在也不会产生 scrape target。还要让 `ruleSelector` 匹配 PrometheusRule 的 `app.kubernetes.io/name: dameng-connect` 标签，并让 `ruleNamespaceSelector` 覆盖其命名空间，否则 `dameng:scan_backlog_lsn` 等 recording rule 不会生成。按集群现有的标签约定修改样例，不要假设所有发行版都使用相同的 Helm release 标签。

检查当前 Prometheus 自定义资源实际使用的标签选择器：

[source,shell]
----
kubectl get prometheus -A -o json | jq -r '.items[] | [.metadata.namespace, .metadata.name, (.spec.podMonitorSelector|tostring), (.spec.ruleSelector|tostring), (.spec.podMonitorNamespaceSelector|tostring), (.spec.ruleNamespaceSelector|tostring)] | @tsv'
----

把选择器与 PodMonitor、PrometheusRule 的 `metadata.labels` 以及它们所在的 Namespace 对齐。比如 selector 按 `app.kubernetes.io/name: dameng-connect` 选择资源时，两个资源都必须有该标签；如果 chart 通过 `release: <release-name>` 选择资源，就要给两个资源加上对应的 release 标签，并确保 namespace selector 覆盖 Connect 命名空间。

Grafana 的积压、速率、重放跨度和队列占用面板使用 `dameng:scan_backlog_lsn` 等 recording rules。若 Prometheus 查得到原始 `dameng_latest_archived_lsn` 与 `dameng_scanned_upper_lsn`，但 recording rule 没有值，检查 Prometheus UI 的 **Status → Rules** 是否加载 `dameng-cdc` 组、Operator 是否选择了 PrometheusRule，以及 `rule_evaluation_failures_total`。若原始指标也没有，检查 Pod 的 9404 端口、PodMonitor selector、Prometheus target 的 scrape 状态及 `up`。面板有 cluster、namespace、job 和 Worker 筛选；Prometheus 没有 `cluster` 标签时选择 All。

一个 Prometheus 同时监控多个 Connect 实例时，部署一份共享的 `PrometheusRule` 即可。规则表达式会分别计算每个 scrape target 的指标，Prometheus 会保留 `cluster`、`namespace`、`pod`、`instance`、`job` 等目标标签，所以不同 Worker 的结果是不同 time series。不要在每个 Connect 命名空间都复制一份相同规则，同时又让同一个 Prometheus 选择这些规则；重复规则会重复计算，并可能对相同标签集写出重复记录。可把唯一的 PrometheusRule 放在统一的 monitoring 命名空间，并让 Prometheus 的 `ruleNamespaceSelector` 包含该命名空间；各 Connect 命名空间仍可分别部署 PodMonitor。

现有本机 Compose 路径为 `~/projects/dockerfiles/kafka-2.0-3node-compose.yaml`，支持 DAMENG_MONITORING_DIR、DAMENG_CONNECT_METRICS_PORT、DAMENG_CONNECT_METRICS_BIND；迁移时按真实路径和抓取地址修改。
YAML 规则更新可在 scrape 时重载；单文件 bind mount 注意替换 inode 可能让容器仍读旧文件。
检查 jmx_config_reload_success_total、jmx_scrape_error 和新 series。新增埋点还要求新版公共队列/Connector JAR，只有规则变化不能补齐旧镜像的指标。

=== Grafana 面板与判读

Grafana 面板统一在 Connector 目录的 `debezium-connector-dameng/docker/monitoring/dameng-cdc-dashboard.json` 中维护，配套自动加载配置为同目录的 `grafana-provider.yaml`。
导入该 JSON 并选择 Prometheus 数据源；或将 `grafana-provider.yaml` 放入容器的 `/etc/grafana/provisioning/dashboards` 目录，将 JSON 放入其配置的 `/etc/grafana/provisioning/dashboards/dameng` 目录。
面板 UID 为 `dameng-cdc-overview`，文件夹为 Dameng CDC，默认可访问 `http://localhost:3000/d/dameng-cdc-overview?theme=dark`。
筛选项包括数据源、Worker、source identifier 和 Connector 名称。Agent/JVM 无任务也可显示，达梦和业务 producer 指标需任务运行。事件吞吐、Worker CPU、挖掘阶段耗时和 JVM GC 面板使用固定 `rate(...[2m])`，避免 Grafana 数据源推算的 `$__rate_interval` 小于实际抓取间隔；与增量快照及 LSN 速率 recording rules 的窗口一致。每条时间序列在 2 分钟内仍须至少有两个成功抓取样本；实际抓取间隔接近或超过 2 分钟时，应先缩短抓取间隔，或相应增大面板及 recording rules 的窗口。
每个指标图表标题旁的帮助说明均包含含义与单位、统计口径、判读边界、排查与优化方向，以及对应的 Prometheus 指标名。
「源标识」是 `topic.prefix`，「Connect 任务」是 REST Connector 名称，两者目前独立筛选，应选中同一采集任务；JVM 指标始终属于整个 Worker。
多源选择时注意概览卡片的 `sum`、`max`、`min` 聚合口径，具体见各卡片帮助。空闲、采样不足、Task 重启或规则未加载引起的无数据，不能直接当作零值。
增量快照区新增独立运行/暂停、当前表/阶段、读取/入队速率与 Task 生命周期累计、完成块数及查询/CLOSE/发送耗时；每个图表的帮助说明统计边界和优化方向。
窗口帮助分别解释文件预算和固定 LSN 策略，并提供文件预算/总 LEN 与文件数面板。调优应比较实际扫描速度、积压趋势与资源压力，不能仅看单轮耗时。旧自适应专属的 WindowIncreases、WindowDecreases、WindowAdjustmentReason 指标及扩缩次数导出规则已删除。
Producer 帮助说明了约 8 KiB 记录与 16 KiB 批次的边界、64 KiB 批次和 `linger.ms` 的单参数对照方法，以及 Worker 的 `producer.*` 与任务级 `producer.override.*` 的区别。
本地 `~/projects/docker-prometheus-grafana/` 下的文件是部署副本，修改 Connector 目录中的源文件后需同步部署副本；也可以让 Grafana Compose 直接只读挂载源文件到上述容器路径。
通过 Grafana UI 修改面板后，需要导出 JSON 并更新 Connector 目录中的源文件；UI 修改不会写回 provisioning 文件，后续文件加载可能覆盖这些修改。
只更新帮助文案时，重新导入同一 UID 的面板 JSON 或同步 Grafana provisioning 文件即可，无需重建 Connect 镜像或重启 CDC Task。

归档上界减扫描上界是扫描积压；扫描上界减安全重放位置是 replay span，不是历史重读放大倍数。
LSN 速率使用两分钟斜率，窗口中出现初始零值或回退时抑制；LSN 是 gauge，不能直接当作事件 counter 使用 rate。
累计耗时使用 rate/increase；increase 在图表时间范围内估算并处理可见 reset，至少需要两个样本。
producer buffer wait 是分配缓冲区的等待比例/累计时间，不是缓冲占用。records-per-request、batch-size、record-size 是滚动统计，不是配置值；空闲时缺值/NaN 不等于零。
队列空可能是源空闲或挖掘慢，队列满常是下游压力。入队等待、producer wait 和 dispatch 有重叠，不能相加当总耗时。
本地曾设置 Prometheus 15 天保留，这是部署参数，不是 Connector 保留策略。

业务 producer 图表按 `connector-producer-<connector>-<task>` 选择客户端，不把内部 Topic 或 history producer 混入。
Exporter 对 Kafka 3.9 的 bufferpool-wait-time-total 和 bufferpool-wait-time-ns-total 别名只导出前者，避免重复统计。

[cols="4,6",options="header"]
|===
|Prometheus 指标 |解释
|`kafka_producer_buffer_wait_ratio` |Kafka 指标时间窗内分配缓冲区的等待时间比例，不是缓冲占用比例。
|`kafka_producer_buffer_wait_seconds_total` |bufferpool-wait-time-total 从纳秒换算的累计秒，producer 重建时归零。
|`kafka_producer_records_per_request` |每请求记录数滚动均值。
|`kafka_producer_batch_size_bytes` |实际每分区 batch 字节滚动均值，启用压缩时为压缩后大小，不是配置 batch.size。
|`kafka_producer_record_size_bytes` |当前镜像使用的 Kafka 3.9.1 客户端按每批最大记录的未压缩大小估算上界取滚动平均，含记录开销；不是全部消息大小的算术平均，也不只是 JSON Value。
|`dameng_queue_enqueue_wait_seconds_total` |Debezium 队列满等待累计秒，需新版公共队列和达梦 JAR；与 producer 等待分属不同阶段且可能重叠。
|===

== 常见问题与故障处理

[cols="3,4,5",options="header"]
|===
|现象 |优先核查 |处理原则
|插件列表没有达梦 |plugin.path、解压层级、驱动/依赖、所有 Worker 是否更新 |先让完整类名出现在 connector-plugins，再创建任务。
|Included connector type 不匹配 request type |validate URL 是否写了 dameng 简称；POST/PUT 对象层级 |使用完整类名，POST 包含 name/config，PUT config 只交配置对象。
|Task RUNNING 但没有已有数据 |snapshot.mode、是否已有 offset、是否观察正确 Topic |默认 no_data 不扫描存量；需要时显式 initial 或增量快照，不删除 offset 试错。
|include 中的表没消息 |启动表清单/WARN、账号可见性和 SELECT、正则及大小写、事务是否提交 |先用同一 CDC 账号查表及元数据。不可见表不会因写在 include 中就自动获得权限。
|ARCH_LSN 很大，source.lsn 不前进 |ScannedUpperLsn、OldestReplayLsn、OpenTransactions |长事务可能固定安全起点；分别判断扫描积压和恢复跨度，不把两个 LSN 直接当处理速度。
|数据库有变化但 LatestArchivedLsn 未变 |归档策略、实际归档文件、磁盘空间 |只有已归档日志可挖；心跳和扩大窗口不会强制保证归档完成。
|持续追不上归档 |前进/重建/dispatch 时间、入队等待、producer buffer wait |按瓶颈调窗口、fetch、batch/压缩/资源；不要只增加 max.queue.size。
|持锁久或快照超时 |加锁日志、持锁指标、活跃写事务、快照数据量、下游队列 |结束不必要的长事务或调整维护窗口/预算。no_data 仍有结构锁；增量快照避免全程共享锁但需先建立结构基线。
|旧 LSN 归档缺失 |最老 replay LSN 到当前的完整归档范围 |补回正确来源的归档后恢复，或采用新身份初始快照；接受历史损失时才显式 nonce。重复 restart 和 no_data 不会修复。
|不支持 DDL，重启后再次失败 |错误 LSN、对象编号、SQL 位置、原始语句、兼容参数 |需要支持该历史语句的修复或明确重建基线；skip.unparseable.ddl 不会放行达梦解析。不要拿当前表结构替换旧定义。
|capture_scope differs / 范围调整被拒绝 |旧范围描述、初始快照状态、数据库选择、信号表、table.ignore.builtin |普通表扩缩按范围调整机制处理；快照未完成或不支持的身份变更不能直接恢复。保留原配置排查，不填造签名或删除 history。
|compatibility_signature 不匹配/缺失 |旧插件 offset、模式/词法/大小写参数、主备参数一致性 |不要填造签名。只有确认临时设置期间没生成受影响历史，才可还原设置恢复，否则新基线。
|内存/事务数/单 SQL 上限或磁盘失败 |具体错误字段、SQL 连续片段、并发事务、落盘可用容量/权限 |调整对应资源或负载后重启；队列、事务缓存、单 SQL 是不同预算。不能跳过超限事务。
|主备切换后停止 |唯一 OPEN PRIMARY、身份锚点、应用 LSN、归档连续性 |由 DBA 修复主备状态并保留 history/offset；高当前 LSN 不足以证明旧确认数据已复制。
|备库 -710 |实际构建、STANDBY 角色及失败的 SQL |旧 8.1.2.128 构建的 JDBC LogMiner 注册归档受角色限制；8.1.3.162 备库采集需配置 database.standby.hosts，信号 DDL/DML 路由到主库。业务 SQL 或水位误写备库也会报此错误，不能通过放开任意备库写入解决。
|Kafka 2.0 history 创建失败 |history Topic 是否预建、单分区和保留策略 |按部署章节预创建，检查认证与权限；延长 timeout 不修复协议不兼容。
|Grafana 无数据 |Task 是否运行、Agent 是否加载、Exporter 是否有对应规则、新版 JAR、标签筛选 |先 curl metrics，再查 Prometheus target 和 Grafana；缺 series 不当成数值零。
|===

连接类 IOException、SQLState 08、可恢复连接错误及主备无可用主库的特定错误按 errors.max.retries 重试。
快照预算、SQL timeout、history 存储、落盘损坏、未知 DDL 和缺档等不是靠重连能修复的错误，应先处理原因。
首次排查保存版本、配置键名、脱敏日志、LSN 和失败语句；不要把凭据、业务行或 history 全文直接公开。

=== 新增表和多实例

过滤规则已覆盖且启动后新建的表可通过 DDL 进入采集，前提是其类型/DDL 支持、权限和日志完整。
原先排除的已有表通过 <<dameng-capture-scope-changes,范围调整>>建立独立启动边界和结构基线，原有表继续使用旧位置；不读取新增表边界之前的历史变化。
增量快照用于已启用表补当前行，扩表不会默认自动触发，也不能用它恢复被排除期间的删除和中间变化。
同一 Worker 集群有多个 Worker 只提高调度容错，不增加单个达梦 Connector 的 Task 数。多 Worker 重平衡和 Broker 故障不应从单 Worker 测试推断已全部验收。

=== 安全与升级

REST API 的网络访问、认证与代理策略由部署管理；凭据用配置提供器，临时文件、offset 和 history 按源数据敏感级别保护。
数据库参数由 DBA 配置，Connector 不自动开启归档。自动建信号表只影响显式配置的信号表，不修改业务表。
数据库驱动 TLS、Kafka SASL/SSL、配置提供器和运行平台变化都应独立验收，不能照搬 Oracle Wallet 配置。
回滚插件镜像也要考虑新插件写出的 offset/history 格式是否可被旧插件理解；保留镜像不等于可以无条件回滚状态。

[[dameng-case-sensitive]]
=== CASE_SENSITIVE=0 标识符适配

`CASE_SENSITIVE` 是建库属性，不是 Connector 参数，也不能通过修改正在运行的任务把数据库切换为模式 0。
Task 自动查询 `SF_GET_CASE_SENSITIVE_FLAG()`，结果仍进入 offset 的 compatibility_signature；重启不能把不同建库属性的历史位置混用。

8.1.3.162 实测：模式 0 的 JDBC 元数据保留不少原始拼写，例如 Dbz_Mixed、Id，而非引号关键词 VaLuE 被保存为 VALUE；LogMiner 的 DDL 保留提交语句的原始拼写。
因此模式 0 对 schema、表、列、主键列和约束统一使用大写作为 Connector 内部及消息中的标识符，历史 DDL 与 JDBC 使用同一规则。默认 Topic 中的 schema/table 部分和消息字段名也相应大写，topic.prefix 本身不变；`'AbC'` 等数据和默认值不改变大小写。
例如物理表 `"Dbz_App"."Dbz_Case"`、列 `"VaLuE"` 对应 `prefix.DBZ_APP.DBZ_CASE` 与字段 `VALUE`。

更换 Converter 也不能修复已经有损的原始 Connect 值；读取业务表当前行不能可靠还原历史 UPDATE 或已删除行。
可行方向是获取并验证无损的数据库版本/日志接口，或在业务允许时重新设计源字段类型；`decimal.handling.mode=precise` 不会让已有 FLOAT 日志变无损。
TIME(0) WITH TIME ZONE、无时区 TIME 与带时区 TIMESTAMP 必须分别看测试结果，不能把这 6 项概括成所有时间类型都不支持。

==== B：标准 JSON 解码的特殊值差异

5 项聚焦负零用例为 REAL、FLOAT(24)、FLOAT、FLOAT(53)、DOUBLE 的 `-0.0`；2 项 NaN 用例为 REAL 和 DOUBLE。
负零经过编码的 JSON 包含 `-0.0`，但标准 JsonConverter 解码后成为 `+0.0`；NaN 编码为字符串 `"NaN"`，同一转换器解码成数值 0。
原始 Connector 特殊浮点 CRUD 回归另有 8 项，当前 XML 中均通过。
`DamengJsonConverterCompatibilityTest` 独立验证标准转换器的现有行为；诊断测试通过不等于无损往返通过。

负零与正零虽然按通常数值比较相等，但符号位、倒数和部分科学计算语义不同；NaN 变成 0 会把“非数值”误作真实零值。
这是可以单独评估修复的转换/消费协议问题：在 Kafka 依赖版本保持不变的条件下，验证自定义 Converter 或下游显式解码协议，并检查 schema、存量消息和消费者兼容性。
本次未实现或验证替代 Converter，不能宣称换一种格式就已解决。

==== D：LOCAL TIME ZONE 的安全拒绝

本轮 CREATE/INSERT 已成功，失败发生在 `DamengValueConverters.schemaBuilder()`，通过 schema change 分发回传为 `Dameng connector failed`。
底层原因明确为 `Unsupported Dameng TIMESTAMP WITH LOCAL TIME ZONE`；并非等待消息超时或数据库不支持建列。
历史跨会话诊断发现：快照随读取会话时区变化，而日志文本没有携带足够的原始写入时区信息，无法唯一恢复 instant。
仅给 Task 设置一个默认 UTC 的参数，不能保证所有写入会话的历史时间都可以正确解释。

恢复支持需要先验证共同的时间基准或提供可恢复原始 instant 的接口，再覆盖不同写入会话、显式偏移、夏令时及重启回放。
暂时应按不支持能力管理，保留明确拒绝；排除已有列可避开值映射，但不保证历史 DDL 声明此类型时能重放。

==== E/F/G/H：数据库未接受测试声明或输入

E 的 18 项等于 3 种类型名称 × 3 种 decimal.handling.mode × 正负两个值。
配置仅影响 Connector 的表示方式，无法改变启动前的 INSERT 结果；本轮 SQL 科学计数值被拒绝，错误根因为 `Data overflow`。
历史分路径诊断还记录 JDBC setBigDecimal 拒绝同样数值，但本次没有重新执行该诊断。
不能把官网数值表达式的计算范围直接等同于该旧构建的列存储范围。

F 的 15 项等于每种精度下 4 个普通 TIMESTAMP 输入独立用例、1 个带时区用例，共 3 组。
四个输入含公元 1 年、1969 年末、闰日及 9999 年；这次全部在建表阶段失败，尚不能判断对应日期/小数秒转换的结果。
升级后即使接受声明，还要检查 Connector 纳秒时间戳的 INT64 可表示范围；当前测试用独立 BigInteger 期望值防止溢出被误判为通过。

G 的输入是 `梦` 重复 8 次、重复 7 次，以及 `😀` 重复 8 次。
报告中的 emoji `length=16` 来自 Java UTF-16 长度，实际是 8 个 Unicode 码点，不是写入了 16 个 emoji。
现有字符集和长度参数下 JDBC 报 `Param incompatible`；历史 SQL 字面量路径也记录列超长。
目前不能仅凭这些信息断言是驱动、服务器实现还是某个参数单独负责，应在升级后重测两条写入路径及显式 CHAR/BYTE 语义。

H 的建表语句使用 `VALUE ROWID`，与查询或日志 WHERE 中的 ROWID 行定位语义不同。
不能通过删除这项失败就把普通 ROWID 类型列标成支持，也不能据此否定无主键表采集。

37 项都尚未进入这些值的 CDC 验收。升级后需先确认原声明/输入被接受，再检查 snapshot、归档 CRUD、before/after、JSON 及相关重启/历史结构回放。
缩小输入、截短中文或把精度改成 6 会变成另一个用例，不能算修复原来的边界。

==== 后续处理顺序与验收口径

先处理 A/C 的流式值失真，因为它们可能正常发布消息却给出错误数值；确认业务是否使用相关字段，并优先验证升级构建或无损接口。
B 可以作为独立开发项评估，保持 Kafka 版本不变也能研究转换器/消费者解码，但需要实际往返验收。
