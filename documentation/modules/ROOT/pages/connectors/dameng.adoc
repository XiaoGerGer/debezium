= Debezium 达梦 Connector 使用手册
:page-aliases: connectors/dameng-database-setup.adoc, connectors/dameng-support-matrix.adoc
:toc:

== 概览

本手册适用于 `3.6-xingchuang` 分支、版本 `3.6.4-xingchuang-kafka2.0`，核对日期为 2026-11-05。
Connector 通过 JDBC 读取结构和快照，通过 `DBMS_LOGMNR` 挖掘归档 REDO，发布已提交的行级变更。

部署前先确认四点：

* 支持 `COMPATIBLE_MODE=0` 和 `7`，单个 Connector 只运行一个 Task。
* 默认 `snapshot.mode=no_data`，不扫描存量行；需要首次全量时设置 `initial`。
* 交付语义为至少一次，重启可能重发未确认的事件，下游需支持幂等处理。
* 浮点精度、行外 LOB 和 LOCAL TIME ZONE 有已知限制，见 <<dameng-data-types,类型映射>>。

首次部署按 <<dameng-database-setup,数据库准备>>、<<dameng-deployment,部署与验证>> 操作。
已有任务调整表范围见 <<dameng-capture-scope-changes,扩缩表>>，故障或升级见 <<dameng-recovery,恢复>>。

=== 采集与恢复位置

[source,text]
----
初始快照：共享表锁 → 选择 LSN → 读取结构和可选存量行 → 释放锁
持续采集：归档 REDO → LogMiner → 事务缓存 → 历史结构解码 → Kafka
增量快照：主键分块读取 + 源表信号水位 + CDC 去重
----

事件在事务提交后发布，回滚行不发布。跨 Topic、跨分区的顺序和原子可见性由下游处理。
source partition 为 `{"server":"<topic.prefix>"}`，Worker 结合 Connector 名称查找 offset。正常恢复须保留名称、`topic.prefix`、offset 和独占的 schema history。

schema history 保存日志位置对应的表定义与对象编号，避免用当前 JDBC 列顺序解释旧日志。
offset 中的 `compatibility_signature` 记录兼容和词法环境，`capture_scope` 记录过滤范围；缺失或不兼容时拒绝普通恢复，不应手工补造。

[id="dameng-support-matrix"]
== 支持范围

[id="dameng-compatible-mode-matrix"]
=== 兼容模式

支持服务器实际的 `COMPATIBLE_MODE=0`（达梦原生模式）和 `COMPATIBLE_MODE=7`（PostgreSQL 兼容模式），分别选择 `native-v1` 和 `postgres-v1`。
其他模式和未知模式均拒绝启动，不回退到原生规则。
`dameng.compatible.mode` 是测试属性；JDBC 的 `compatibleMode` 驱动选项也不能覆盖服务器检查。
数据库端的日志和词法参数要求见 <<dameng-database-setup,数据库准备>>。

模式 7 使用达梦 JDBC、归档日志和 `DBMS_LOGMNR`，沿用达梦物理类型映射，不使用 PostgreSQL 的复制协议。
未引用标识符转大写；引用标识符按 `CASE_SENSITIVE` 和 `IDENTIFIER_MODE` 处理，不按 PostgreSQL 规则转小写。
支持历史 DDL 中的 `TIME/TIMESTAMP ... WITHOUT TIME ZONE` 和 `E'...'` 字面量。
模式 7 要求 `BACKSLASH_ESCAPE=0`、`FLOAT_MODE=0`、`NUMBER_MODE=0`、`ORA_DATE_FMT=0`；这些参数会记录到兼容签名并在运行边界复核。
在该设置下，`E'a\n'` 的反斜杠保留为文字，不解释为换行。
模式 7 不代表数据库接受所有 PostgreSQL 类型：当前测试的 DM 8.1.3.162 不接受 `SERIAL`、`INT4`、`BYTEA`、`JSONB`、`UUID` 等声明。
模式 7 的定向回归使用当前默认的 DM 8.1.3.162 镜像、`DmJdbcDriver18 8.1.3.140` 和 GB18030 字符集，覆盖 `CASE_SENSITIVE=0/1`。
浮点精度、行外 LOB 和 LOCAL TIME ZONE 的限制同样适用于模式 7，见 <<dameng-data-types,类型映射>>。
切换兼容模式必须建立新的采集基线，不能复用另一模式的 offset 和 schema history。

本实现使用 JDBC LogMiner，不提供 JNI 生产适配器、XStream、OpenLogReplicator、Oracle RAC/PDB 或 Flashback。
并行初始快照、阻塞快照、自定义 snapshotter、主动丢弃事务和手工注入历史 DDL 未提供。

=== 部署拓扑

[cols="3,2,5",options="header"]
|===
|拓扑 |支持状态 |要求
|单机直连 |支持 |`NORMAL/OPEN`，配置 hostname/port。
|固定地址连接主库 |支持当前成员采集 |`PRIMARY/OPEN`；单地址 offset 不提供跨成员恢复保证。
|成员列表连接主库 |支持人工切换 |配置 `database.failover.hosts`，成员 `N_EP=1`；DBA 负责切换和隔离旧主。见 <<dameng-primary-standby-recovery,主备恢复>>。
|物理备库采集 |支持指定构建 |配置 `database.standby.hosts`；备库提供 LogMiner、SLSN、RPKG_LSN，主库负责信号写入和快照锁。见 <<dameng-standby-capture,备库采集>>。
|VIP、代理、自动故障切换 |未验收 |现有回归使用成员地址列表和人工切换。
|DMDSC、多可写主库、分布式多源 |不支持 |未实现多节点日志合并与恢复。
|===

只采集 `OPEN` 实例。主备成员须属于同一物理数据库家族，保持唯一可写主库、连续归档和一致的词法参数。
旧 8.1.2.128 在备库注册 LogMiner 归档时返回 `-710`；8.1.3.162 的备库采集已有回归。强制有损 takeover 和脑裂恢复不在支持范围。

[[dameng-case-sensitive]]
=== 标识符大小写

`CASE_SENSITIVE` 是建库属性，Connector 自动读取：

* `0`：schema、表、列和约束统一为大写；Topic 中的 schema/table 和消息字段名也使用大写，数据值不变。
* `1`：非引号名转大写，双引号名保留大小写。同表列名仅大小写不同仍拒绝。

过滤正则、列配置和增量快照表名须使用上述名称。`signal.data.collection` 自动规范化，并始终按 `schema.table` 解析。
例如模式 0 下的 `"Dbz_App"."Dbz_Case"`、列 `"VaLuE"` 对应 Topic `prefix.DBZ_APP.DBZ_CASE` 和字段 `VALUE`。

[id="dameng-database-setup"]
== 数据库准备

由 DBA 配置归档、日志参数和 CDC 账号；Connector 不自动修改这些设置。
先按 <<dameng-support-matrix,支持范围>> 核对构建、驱动及部署拓扑，再检查以下实际生效值。

=== 必需参数和归档

[cols="2,1,4",options="header"]
|===
|数据库配置 |目标值 |用途和核查依据
|本地归档与 `ARCH_INI` |通常设 `ARCH_INI=1`；`V$DATABASE.ARCH_MODE` 必须显示已开启 |达梦 `DBMS_LOGMNR` 读取归档日志。官方 https://eco.dameng.com/document/dm/zh-cn/pm/logmnr-interface-instructions.html[LogMiner 说明]使用 `ARCH_INI=1`；Connector 校验实际归档模式，而非只读取 `ARCH_INI`。
|`RLOG_APPEND_LOGIC` |`2` |UPDATE 和 DELETE 的逻辑日志包含完整的非 BLOB/CLOB 列值，供 Connector 还原行像。值为 `1` 时，有主键表的日志可能只包含主键和更新列。
|`RLOG_IGNORE_TABLE_SET` |`1` 或 `0` |`1` 维持全表逻辑日志行为；`0` 时由任务配置者手动为每张采集表开启表级逻辑日志，Connector 在启动时打印 WARN 并继续。其他值会使流式任务拒绝启动。
|`RLOG_LLOG_COMPRESS` |存在时为 `0` |压缩逻辑日志可能使 INSERT 的值无法完整挖取。旧版本没有该参数时，Connector 接受其缺失。
|`COMPATIBLE_MODE` |`0` 或 `7` |原生模式或 PostgreSQL 兼容模式，其他值或缺失时拒绝。
|`FLOAT_MODE`、`NUMBER_MODE`、`ORA_DATE_FMT` |模式 7 时均为 `0` |模式 7 校验并记录到兼容签名；其他值或缺失会被拒绝。
|`LENGTH_IN_CHAR` |`0` |使用已验证的字节长度语义。其他值或查询不到该参数都会被拒绝。
|`BACKSLASH_ESCAPE` |8.1.3.162 使用 `0` |值为 1 的新版本字面量语义尚未适配；模式 7 拒绝 1，原生模式代码范围检查仍接受 0、1。
|`NESTED_C_STYLE_COMMENT` |`0` 或 `1` |`0` 在第一个 `*/` 结束块注释；`1` 按嵌套层数匹配结束。其他值或缺失会被拒绝。
|`CASE_SENSITIVE` |`0` 或 `1` |通过 `SF_GET_CASE_SENSITIVE_FLAG()` 读取，命名规则见 <<dameng-case-sensitive,大小写>>。
|`IDENTIFIER_MODE` |缺失、`0` 或 `1` |缺失/0 保留引用名大小写，1 转大写；显式模式仅有解析单测，需目标库验证。
|===

`RLOG_APPEND_LOGIC` 与 `RLOG_LLOG_COMPRESS` 的 LogMiner 行为见 https://eco.dameng.com/document/dm/zh-cn/pm/dbms_logmnr-package.html[达梦 DBMS_LOGMNR 文档]。
`RLOG_IGNORE_TABLE_SET=0` 时，任务配置者必须在采集开始前按当前达梦版本的官方操作方法，为每张实际捕获的表开启表级逻辑日志；配置了信号表时，信号表及后续新增的采集表也必须分别处理。
达梦官方 https://eco.dameng.com/document/dm/zh-cn/pm/definition-statement.html[数据定义语句]列出了既有表的 `ALTER TABLE <模式>.<表> ADD LOGIC LOG`，以及 `CREATE TABLE` 定义末尾的可选 `ADD LOGIC LOG` 子句。例如：

[source,sql]
----
ALTER TABLE BIZ.ORDERS ADD LOGIC LOG;
----

Connector 不验证每张表是否启用逻辑日志，也不代为开启。缺失时可能运行正常却漏掉变更；事后启用不能补回旧变化。
自动创建的信号表也须在发送信号前启用表级逻辑日志。

词法和大小写设置写入 `compatibility_signature`，启动恢复及运行期间变化会停止任务。主备成员及需重放的日志区间必须保持一致。
两次检查间改动后又改回无法检测；若该期间生成过受影响日志，应重建基线，不能只靠当前签名相等继续恢复。

测试容器的归档路径、64 MiB 文件和 1 GiB 空间上限不适合作为生产容量建议。生产变更按目标 DM 版本的生效规则实施，并在每个采集或主备节点查询：

[source,sql]
----
SELECT PARA_NAME, PARA_VALUE
FROM V$DM_INI
WHERE UPPER(PARA_NAME) IN (
    'ARCH_INI',
    'RLOG_APPEND_LOGIC',
    'RLOG_IGNORE_TABLE_SET',
    'RLOG_LLOG_COMPRESS',
    'COMPATIBLE_MODE',
    'LENGTH_IN_CHAR',
    'BACKSLASH_ESCAPE',
    'NESTED_C_STYLE_COMMENT',
    'IDENTIFIER_MODE'
)
ORDER BY PARA_NAME;

SELECT ARCH_MODE FROM V$DATABASE;
SELECT SF_GET_CASE_SENSITIVE_FLAG();
SELECT MODE$, STATUS$ FROM V$INSTANCE;
SELECT PATH, ARCH_LSN, CLSN
FROM V$ARCH_FILE
WHERE PATH IS NOT NULL
ORDER BY ARCH_LSN;
----

`ARCH_MODE` 应为启用状态；当前 Connector 接受 `Y`、`1` 或 `ARCHIVE`。
核查 `V$ARCH_FILE` 中存在本地归档，对应文件仍在数据库服务器上，且需要恢复的 LSN 区间没有缺口。
当前 Connector 只读取归档文件，尚未归档的日志会增加变更事件延迟。
归档保留应覆盖最老未完成事务、Connector 积压、Kafka 或网络故障、人工切换与恢复所需时间。
本地归档达到空间上限时可能删除最旧文件；丢失所需文件后，Connector 会停止而不会跳过缺口。

=== CDC 账号

在上面注明的 DM8 版本中，以下权限已用于验证 JDBC 元数据读取、共享快照锁和 LogMiner。
先由 DBA 创建账号，再将示例中的用户、schema 和表名替换为实际值：

[source,sql]
----
GRANT SOI TO CDC_USER;
GRANT VTI TO CDC_USER;
GRANT EXECUTE ON DBMS_LOGMNR TO CDC_USER;
GRANT SELECT ON APP.CUSTOMERS TO CDC_USER;
GRANT SELECT ON APP.ORDERS TO CDC_USER;
----

若 `CREATE SESSION` 已被撤销，需补授连接权限。
每张新纳入采集的业务表也需授予 `SELECT`。
初始快照通过当前账号的 `ALL_TABLES` 发现表；不可见的表不会进入快照范围。
最终发现完成后，Connector 以 INFO 输出实际选择的结构采集表和数据快照表，并对没有选择到任何可见表的 `table.include.list` 规则打印 WARN。
该警告不会停止任务，也不能单独证明权限不足；请同时核对表是否存在、名称大小写及其他过滤条件。
如果使用源端信号表执行增量快照，账号还需对信号表写入信号和水位记录的权限。
这组权限无需 `DBA` 或 `SELECT ANY TABLE`，但 `SOI` 和 `VTI` 是较宽的系统目录读取角色；应在实际 DM 版本验证授权。
`SOI` 允许读取非安全、非审计系统表，包括对象与约束目录；`VTI` 允许读取系统动态视图，包括运行状态和 LogMiner 视图。
这是一组已经验证可用的权限，不是已证明不可再缩小的最小权限集。基线构建拒绝对 SYS.SYSOBJECTS、SYS.SYSCONS 直接进行对象级授权，不能用未经验证的单对象 GRANT 替代。

=== 主备准备

各成员均需满足参数、授权和本地归档要求，实时归档通道保持健康。
新主库须已应用所需 redo，并保有覆盖 Connector 已确认位置的连续历史。
DBA 负责升主和隔离旧主，Connector 只选择符合角色的节点并检查恢复连续性。操作见 <<dameng-primary-standby-recovery,主备恢复>>。

=== 内置过滤和表存储类型

默认 `table.ignore.builtin=true`，代码内置排除 SYS、SYSTEM 和名称以 V$ 开头的 schema，以及任意 schema 下名称以 `MTAB$_`、`MLOG$_` 开头的物化视图内部表和以 `BMJ$_` 开头的位图连接索引辅助表。内部表前缀比较不区分大小写，匹配 `table.include.list` 也不会覆盖默认内置排除。
内置过滤同时用于快照和增量处理。旧 history 中残留的这些内部表也不输出数据，其对象编号不参与业务表的历史身份匹配，避免已删除内部表的编号复用后干扰业务表。
`table.ignore.builtin=false` 关闭这组内置过滤，但不会启用内部表 CDC，也不补齐隐式辅助表结构历史。这些内部表不能作为 `signal.data.collection`。
SYSDBA 下某表或其他 schema 的系统用途表不一定被这一规则自动排除，生产应显式指定业务表过滤器并核对启动清单。
普通行表和已验证分区根表可以采集，临时/HUGE/外部表和生成列限制见 DDL 章节。
信号表自动创建及额外写权限见 <<dameng-signals,信号表>>。

[id="dameng-deployment"]
== 部署、REST 管理与验证

=== 插件和运行时

将 assembly 产出的插件归档解压到 Worker 的 `plugin.path` 独立目录，保留依赖和 `DmJdbcDriver18`，然后重启所有可能调度到该 Task 的 Worker。
不要把打包时排除的 Kafka API JAR 随意塞回插件目录覆盖 Worker API。
默认 Dockerfile 在 Apache Kafka 3.9.1 镜像中安装本分支插件、驱动、环境变量配置脚本及 JMX Exporter 1.4.0；默认产物为 Linux amd64 / Java 21，启动时默认启用 `9404/metrics`。
镜像默认 JVM 堆参数为 `-Xms4G -Xmx4G`。可通过 `HEAP_OPTS` 或 `KAFKA_HEAP_OPTS` 覆盖；同时设置时 `HEAP_OPTS` 优先。
Oracle 模块的官方镜像配置来自统一镜像项目，本分支达梦的 Dockerfile 和脚本是自己的部署入口。

[cols="2,3,5",options="header"]
|===
|层次 |当前值 |含义
|Connector 项目版本 |`3.6.4-xingchuang-kafka2.0` |插件版本，不是 Broker 或客户端版本。
|Maven Kafka 依赖 |`4.3.0` |编译及默认独立测试进程使用的依赖；项目版本改名不会改变它。
|Kafka 2.0 部署镜像的 Worker |`3.9.1` |使用仍保留旧 Broker 协议的 Worker/client 运行插件；不是将 Broker 升到 3.9。
|生产目标 Broker |`2.0` |需采用下述 history 预创建等要求，并验证目标安全配置、负载和恢复；Kafka 4.x 客户端不能直接作为此兼容方案。
|===

=== 构建、导出与内网导入

从仓库根目录使用根 POM 要求的构建 JDK 和 Maven Wrapper：

[source,shell]
----

./mvnw -pl debezium-connector-dameng,debezium-assembly-descriptors -am install -Passembly -DskipITs
bash debezium-connector-dameng/docker/monitoring/fetch-agent.sh
cd debezium-connector-dameng
docker build --build-arg KAFKA_BASE_IMAGE=apache/kafka:3.9.1 \
  --build-arg CONNECTOR_VERSION=3.6.4-xingchuang-kafka2.0 \
  -f docker/Dockerfile -t debezium-connect-dameng:3.6.4-xingchuang-kafka2.0 .
bash docker/test-env-config.sh debezium-connect-dameng:3.6.4-xingchuang-kafka2.0
docker tag debezium-connect-dameng:3.6.4-xingchuang-kafka2.0 debezium-connect-dameng:kafka2.0
docker save debezium-connect-dameng:3.6.4-xingchuang-kafka2.0 \
  debezium-connect-dameng:kafka2.0 | gzip -1 \
  > target/debezium-connect-dameng-3.6.4-xingchuang-kafka2.0-linux-amd64.tar.gz
cd target
sha256sum debezium-connect-dameng-3.6.4-xingchuang-kafka2.0-linux-amd64.tar.gz \
  > debezium-connect-dameng-3.6.4-xingchuang-kafka2.0-linux-amd64.tar.gz.sha256
----

构建命令跳过数据库集成测试，不代表发布验收完成。
Agent 下载脚本在联网构建机执行；已有已校验 JAR 时无需重复下载。Docker 构建会再次校验 Agent SHA-256，并将 JAR 和指标映射配置写入镜像，运行时无需下载或挂载它们。
离线机器同时复制归档和 SHA-256 文件，然后执行：

[source,shell]
----
sha256sum -c debezium-connect-dameng-3.6.4-xingchuang-kafka2.0-linux-amd64.tar.gz.sha256
docker load -i debezium-connect-dameng-3.6.4-xingchuang-kafka2.0-linux-amd64.tar.gz
----

版本标签标识插件版本，`kafka2.0` 是兼容旧 Compose 的别名。更新 tag 不会更新运行中的容器。
替换现有 Worker 前先按恢复章节核查 offset；不要删除 Kafka 数据卷来完成升级。

=== Kafka 2.0 的 Topic 准备

当前 history 客户端创建 Topic 时的请求与 Kafka 2.0 存在兼容限制，需提前创建 history Topic。
以下副本数 1 仅用于单 Broker 测试，生产根据 Broker 数量和可用性要求设置：

[source,shell]
----
kafka-topics --zookeeper ZOOKEEPER_HOST:2181 --create \
  --topic dameng-schema-history --partitions 1 --replication-factor 1 \
  --config cleanup.policy=delete --config retention.ms=-1 \
  --config retention.bytes=-1
----

history 不使用 compaction，其记录 Key 为 null；需要完整历史，并与任务配置的名称一致。
Worker 内部配置/offset/状态 Topic 则按 Kafka Connect 要求保留并启用 compaction，配置 Topic 单分区，不能套用 history 的策略。
Broker 关闭自动建 Topic 时还需预建业务、结构、心跳、事务等实际使用的 Topic。
Worker 保持 `exactly.once.source.support=disabled`。

      STATUS_STORAGE_TOPIC: "dameng-connect-status"

验证一次 Worker 重启和离线期间 DDL/DML 的恢复，保留至少一次语义允许的重复。

[source,shell]

[id="dameng-snapshots"]
== 快照与信号

=== 初始快照和 no_data

[cols="2,4,4",options="header"]
|===
|snapshot.mode |没有可恢复 offset 时 |已有已完成快照的 offset 时
|`no_data`（默认） |读取结构、选择当前 LSN，再持续采集；不发存量行 |恢复旧位置，仍要求所需归档存在。
|`initial` |读取结构和存量行，再持续采集 |恢复旧位置，不自动再次全量。
|`initial_only` |读取结构和存量行后结束快照执行，不进入 CDC |不提供持续采集；Task 状态不应当作数据仍在变化的证明。
|`never` |`no_data` 的旧别名，仍需结构基线 |与 `no_data` 相同。
|===

未完成的初始快照可能在恢复时重新执行并重发已经输出的行。
Connector 先发现并锁住捕获表，选择 `V$RLOG.CUR_LSN`，读取结构，按模式决定是否扫描行。
选择 LSN 后再次检查匹配过滤器的新表；如发现新表，补锁并重新选择 LSN，再检查一次。最终检查之后的新表通过 DDL 流处理。
整个快照事务结束并成功 rollback 后才释放共享表锁。此处 rollback 用于结束只读快照事务，不是回滚业务事务。
普通查询不使用 Oracle `AS OF SCN`；一致性依赖这些锁，因此 `no_data` 建立结构基线也会短暂锁表。

`snapshot.max.duration.ms` 默认 10 分钟，覆盖锁等待、结构/数据读取和队列阻塞。
超时中断快照并请求 JDBC abort，Task 失败，不会通过跳过表继续；实际断开会话及释放锁依赖驱动和数据库。
主备模式在完成标记之前再次核对主库身份；切换打断初始快照后在新主库重新快照。
当前仅允许 `snapshot.locking.mode=shared`、`snapshot.max.threads=1`。
`snapshot.lock.timeout.ms` 的继承字段没有接入达梦锁语句，实际应结合 `database.query.timeout.ms` 和总快照预算设置超时。

=== 快照范围与采集范围

`schema.include.list`、`table.include.list` 等决定总体采集范围；表过滤针对完整 `schema.table`，列过滤针对 `schema.table.column`，不是 `database.schema.table`。
规则是正则表达式，需要字面点号时在 JSON 中写 `APP\\.CUSTOMERS`。
include 和 exclude 对应项不能同时配置。
`snapshot.include.collection.list` 只减少初始快照输出行的表，不缩小这些已捕获表的结构 history，也不改变 streaming 或增量快照的选择范围。
`snapshot.select.statement.overrides` 和每表 SQL 只过滤初始快照行，不能过滤之后的 CDC。

结构发现完成时，日志打印结构采集表和数据快照表。
每个没有匹配任何可见表的 `table.include.list` 表达式会 WARN，但不会因此停止，因为规则可能针对未来新表。
应检查表名大小写、其他过滤规则、元数据可见性和 SELECT 权限；WARN 本身不能证明是哪一种原因。
普通重启直接恢复 streaming 时不会重新执行完整快照发现检查。

初始 history 当前只包含采集过滤器选中的表，`schema.history.internal.store.only.captured.tables.ddl=false` 不会扩展为所有库表结构。
已捕获表被 rename 到范围外后仍保留后续 DDL，以支持之后改回名称；从未拥有历史定义的表不能仅靠 rename 进入捕获范围。
在过滤器不变时，运行中或停机期间创建、删除后重建的匹配表，可以通过仍保留的 DDL 采集。
已有完整 offset 和 history 时，可以修改表过滤范围后重启，具体边界和限制见 <<dameng-capture-scope-changes,调整采集表范围>>。不能直接用当前 JDBC 结构解释新增表的旧日志。

[id="dameng-capture-scope-changes"]
=== 调整采集表范围

初始快照完成后，可 PUT 完整配置修改 schema/table include/exclude，再重启。须保留 offset、schema history 和所需归档。

[cols="2,5",options="header"]
|===
|变更 |行为
|新增已有表 |只锁新增表，建立当前结构和激活 LSN `S`。原有表继续原位置；新纳入范围的表不重放 `LSN <= S` 的 DML/DDL。
|新规则匹配未来新表 |`S` 之后受支持的 CREATE TABLE 可建立结构并进入采集；已删除或不可见表的旧 CREATE 不会被回放成新表。
|移除表 |停止输出该表，包括未发送的积压；清理其增量快照进度，保留其他表进度。已发消息不撤回。
|重新加入表 |建立新的激活边界，不补被排除期间的历史。
|===

边界和新增结构在释放锁前写入 history，重启复用，不重新选择更晚的位置。备库采集时在主库加锁并选择边界，等待备库追平后读取结构。
`initial` 不会在扩表时自动补存量；需要时发送该表的增量快照信号。补数只能读取当前仍存在的行，不能补回旧删除或中间变化。

扩表前用 CDC 账号确认元数据和 SELECT 可见性。历史已知的新纳入表在 JDBC 中不可见，或对象编号与另一历史表冲突时，调整会失败；先恢复权限或用原配置追平重命名日志。
未匹配任何可见表的 include 规则会 WARN，但不阻止未来建表。

以下情况拒绝普通范围调整：初始快照未完成，改变数据库选择、`table.ignore.builtin` 或信号表身份，从过滤器移除信号表，以及缺失旧范围描述或兼容签名。
旧 offset 没有 `capture_scope_manifest` 时，先用原过滤配置运行并保存新 offset，再调整范围。
`recovery.restart.nonce` 会放弃整个任务的积压，不能替代扩表。

=== 增量快照机制

增量快照按主键范围分块，默认每块最多 1024 行。
每个块通过源信号表的开启/关闭水位与 CDC 交错：读取块内行，观察水位之间的日志变更，移除被更新或删除的旧快照行，再输出剩余 `op=r` 记录。
进度随 offset 保存，重启后可恢复。日志追赶慢会延长块完成时间，未观察到关闭水位时不能把缓存行提前当成最终结果发布。
它不持有初始快照那种贯穿全流程的共享表锁，也不保证所有表处于同一个全库时刻。
当前验收以声明主键的表为基础；普通无主键 CDC 支持不等于无主键增量快照支持。
执行期间须保持表结构稳定，`incremental.snapshot.allow.schema.changes` 必须为 `false`。

[id="dameng-signals"]
=== 信号表配置、创建和触发

设置 `signal.data.collection=APP.DBZ_SIGNAL`，将信号表纳入捕获规则，并确保其产生逻辑日志。
每个独立 Connector 使用独立信号表，避免多个实例读取相同命令或互相消费水位。
已有 offset 时不能直接添加或改名信号表绕过 capture_scope 检查，建议首次创建 Connector 时就配置。

Task 在校验配置和 offset 后、发现快照表前检查信号表，不存在则自动创建；schema 必须已存在。
自动创建需要相应 CREATE TABLE 权限。现有表不改结构、不清空记录，但必须可读，恰好具有按顺序排列的 `ID`、`TYPE`、`DATA` 三个 VARCHAR/NVARCHAR 列。
创建或结构校验失败会阻止启动。Connector 还需插入水位的权限，`insert_delete` 策略需要 DELETE 权限。
不授予 DDL 权限时可由 DBA 预创建：

[source,sql]
----
CREATE TABLE APP.DBZ_SIGNAL (
    ID VARCHAR(64) PRIMARY KEY,
    TYPE VARCHAR(64) NOT NULL,
    DATA VARCHAR(2000)
);
GRANT SELECT, INSERT, DELETE ON APP.DBZ_SIGNAL TO CDC_USER;
----

使用有写权限的账号提交一次性、唯一 ID 的命令：

[source,sql]
----
INSERT INTO APP.DBZ_SIGNAL VALUES (
    'customers-snapshot-001',
    'execute-snapshot',
    '{"type":"incremental","data-collections":["APP.CUSTOMERS"]}'
);
COMMIT;
----

检查 Task 日志、快照通知/指标和业务 Topic 的 `op=r`，不要仅凭 INSERT 成功认定快照完成。
停止整个运行中的增量快照可使用公共信号动作：

[source,sql]
----
INSERT INTO APP.DBZ_SIGNAL VALUES (
    'customers-stop-001', 'stop-snapshot', '{"type":"incremental"}'
);
COMMIT;
----

停止动作不撤回已经发布的行。`pause-snapshot`、`resume-snapshot`、`additional-conditions` 和 Kafka/JMX/file 信号通道来自公共框架，但尚无本模块与源表基本流程同等范围的端到端验收，应先在目标环境验证。
即使使用其他触发通道，当前达梦增量快照仍需要源信号表协调水位，不能只配 Kafka 信号 Topic 就省略它。

[id="dameng-logminer"]
== 日志挖掘与资源调优

=== 窗口和事务

Connector 只读取归档 REDO，未归档尾部会增加延迟。LSN 是日志位置，跨度不等于行数或字节数。

[cols="2,3,5",options="header"]
|===
|策略 |配置 |行为
|`archive_bytes`（默认） |`log.mining.window.max.bytes=67108864` |按完整归档文件 `V$ARCH_FILE.LEN` 选择前向窗口，默认软预算 64 MiB。
|`fixed` |`log.mining.batch.size=1000` |按固定 LSN 跨度前进。
|===

文件预算包含已扫描部分和预分配空间，不等于实际 I/O 或堆占用。单文件、共享边界和事务重建可以超出预算；到归档尾部立即处理可读范围，不等凑满预算。
所选文件 LEN 缺失或非正值时停止，可核查归档视图或显式使用 fixed。归档缺口、混入其他来源或重叠异常同样停止。

未完成事务跨窗口保留，并固定安全重放起点。遇到跨窗口提交或回滚边界时，Connector 从最老安全位置重建事务，排除已回滚行，再按提交顺序发布。
支持 SAVEPOINT 的有效结果恢复。长事务落盘后仍依赖旧归档，必须保留到安全重放位置推进。

旧 adaptive 模式已删除。升级前移除 `log.mining.window.adaptive.enabled`、`log.mining.batch.size.min`、`log.mining.batch.size.max`、`log.mining.window.target.ms`，否则配置校验失败。
要保留固定窗口，显式设置 `log.mining.window.strategy=fixed`。

=== 内存与临时文件

[cols="3,2,5",options="header"]
|===
|预算 |默认值 |超限处理
|事务缓存估算内存 |64 MiB |将最大驻留事务写入临时文件；事务元数据不能落盘，耗尽时停止。
|保留事务元数据条数 |1000000 |包含已提交待分发事务，超限停止。
|单次运行的临时文件 |1 GiB |超限、I/O 失败或文件校验失败时停止。
|单条 SQL_REDO |16 MiB UTF-16 payload |包含所有连续片段，拼接前检查；不能边拼接边落盘。
|===

事务内存预算不包括事件队列、JDBC、SQL 拼接和转换开销，不能作为 JVM 堆上限。
`log.mining.buffer.spill.path` 应指向可写磁盘，运行中创建私有 `dameng-tx-*` 目录。临时文件含源数据；强制终止后，只清理已确认结束的运行目录。

临时文件不用于重启恢复。新 Task 从 offset 重放归档，不能因缓存已落盘就删除旧归档。
磁盘配额不包含其他 Task 或遗留文件，须另外监控剩余空间。
旧 `log.mining.buffer.max.bytes`、`log.mining.buffer.max.records` 已废弃，设置只会 WARN 并忽略。

=== 错误诊断

Connector 校验 LogMiner 必需字段、长 SQL 分片顺序、对象身份和回滚标记；缺片、乱序、SQL 缺失或冲突时不发布该窗口。
未支持操作仅在能够确定属于已排除表时过滤，否则停止。错误日志提供 LSN、XID、对象编号和归档位置。
DDL/DML 解析失败还会输出完整拼接后的 SQL_REDO 和堆栈，日志应按源数据权限保护。
`DATA_OBJV#` 仅用于诊断与分片一致性检查，不能代替历史表结构。

=== 调优顺序

先用 <<dameng-monitoring,阶段指标>> 定位瓶颈，再一次调整一个参数：

* 挖掘慢：比较文件预算与 fixed 窗口、fetch 大小和归档延迟。大窗口可能增加分发等待与临时磁盘占用。
* 重建多：检查长事务和回滚负载，保留足够归档。
* 分发或队列等待长：检查 Worker、Converter/SMT、Producer 和 Broker。
* Producer buffer wait 高且每请求记录少：评估 batch.size、linger.ms 和压缩；请求本身慢时先查 Broker、网络和限流。

增加缓存只能承接突发，无法弥补下游持续吞吐不足。有限性能对照见 `src/test/regression-history.adoc`，不作为生产吞吐承诺。

[id="dameng-ddl"]
== DDL 与结构演进

受支持的 DDL 更新 schema history，再按历史结构解码后续行。默认遇到未知语法或无法安全更新结构的语句时停止，重启会再次遇到该位置。

=== 支持的表操作

[cols="2,5,4",options="header"]
|===
|操作 |行为 |限制
|CREATE、ALTER、RENAME、DROP |维护列顺序、类型、默认值、约束名和对象编号；列重命名同步更新主键。支持条件建表/删表、条件增删列和分组加列。 |未知 TABLE 子句、虚拟/生成列、HUGE 和分布式表拒绝。
|主键与约束 |主键变化更新事件 Key。UNIQUE、外键、CHECK 保存名称供后续约束操作。 |UNIQUE 不自动作为事件主键；DISABLE 及启停约束的状态转换不支持。
|整表 TRUNCATE |保留列和约束，按 `op=t` 处理。 |默认 `skipped.operations=t` 不发布数据事件；TRUNCATE CASCADE 拒绝。
|行存储分区表 |支持 HASH/RANGE/LIST、interval、多级子分区和模板。DML 按根表采集。 |合并/拆分后的搬迁 INSERT/DELETE 仍发送，不去重；删除、清空和交换见下节。
|CTAS |读取目标表在线字典；无需源表 history，复制行按 INSERT 日志采集。 |首次消费时目标表须仍存在且保持创建时结构。对象编号核对无法检测所有后续 ALTER，存在结构超前风险；字典失败不受通用 DDL 跳过控制。
|LIKE |从 history 中的源表复制列及可空性。 |不继承主键、默认值、identity 或注释；源表必须已有历史定义。
|临时表、外部表 |只保存表类型、对象编号和生命周期，跳过数据快照、增量快照、行事件及 schema 通知。 |外部文件变化不是 CDC；外部表仅支持创建、删除及重命名历史处理，其他 ALTER、TRUNCATE 和从它推导列的 LIKE 拒绝。
|物化视图与辅助表 |识别普通物化视图/日志的创建、修改、刷新和删除；默认过滤内部表。 |不采集物化视图数据，`FOR ... ON PREBUILT TABLE` 拒绝；预建表须显式排除。
|===

DM 8.1.3.162 删除主键后，原主键列恢复可空；删除复合主键中的一列则移除整个主键，其余列保留非空，历史模型按此更新。
普通列定义支持裸 `ENCRYPT` 标记；算法、密钥和 MANUAL 等扩展选项未支持。加密列仍需目标环境 CDC 验证。
高级日志 `WITH/WITHOUT/TRUNCATE ADVANCED LOG` 不支持。

=== 非表 DDL

已识别且不改变行结构的索引、普通视图、序列、同义词、权限、COMMENT、用户/空 schema、目录、DOMAIN、PROFILE、CONTEXT、LIBRARY、STAT、LINK、OPERATOR、表空间和程序定义按 `NO_TABLE_CHANGE` 跳过。
程序内容和查询体不在 Connector 中执行，但会校验词法、括号和完整语句边界，不能把尾随表 DDL 一起跳过。

COMMENT 不刷新事件 schema 的注释。`REVOKE ... CASCADE` 回收权限，`DROP PROFILE ... CASCADE` 解除关联，`DROP TYPE BODY ... CASCADE` 删除实现，均不等于下节的对象级联删除。
类型定义可识别不代表对象列可采集；权限回收也可能使后续查询失败。
`CREATE SCHEMA` 内嵌对象、`DROP CLASS BODY ... CASCADE` 和单条 redo 中的复合表 DDL 不支持。

`RESTORE TABLE` 的数据替换可能没有逐行 DML redo，不能依赖 CDC 同步这类恢复结果。
多个 LOCAL 归档目的地可能造成重复注册并报 `-2848 cannot add duplicate logfile`，当前尚未支持。

=== 删除、清空与交换的专用策略

以下操作可能没有完整的逐行删除/插入日志，默认报错。三个开关均默认为 `false`，通用 `skip.unparseable.ddl` 不绕过它们。

[cols="3,4,5",options="header"]
|===
|参数 |可显式忽略的语句 |后果
|`partition.drop.ignore` |DROP/TRUNCATE PARTITION、SUBPARTITION，含 TRUNCATE TABLE ... PARTITION。 |忽略分区删除/清空，不补下游删除；见 <<dameng-ddl,专用 DDL 策略>>。
|`partition.exchange.ignore` |完整解析且两端身份可确认的 EXCHANGE PARTITION/SUBPARTITION。 |忽略身份可确认的分区交换，不补交换行；见 <<dameng-ddl,专用 DDL 策略>>。
|`cascade.drop.ignore` |DROP USER/SCHEMA/DOMAIN/TYPE/CLASS ... CASCADE。 |忽略五类对象级联删除，保留旧模型；见 <<dameng-ddl,专用 DDL 策略>>。
|===

EXCHANGE 两端都不在当前采集或历史维护范围时直接过滤；任意一端相关则使用专用策略。
`WITH TABLE` 未限定 schema 时，必须由对象 ID 和历史表名确认，不能用根表的 schema 猜测。无法确认任意一端时始终失败，建议显式限定两端 schema。

对象级联删除在表过滤前处理，因为依赖对象可能跨 schema。`cascade.drop.ignore` 不授权 `TRUNCATE CASCADE` 或 `DROP CLASS BODY ... CASCADE`；`DROP TABLE ... CASCADE CONSTRAINTS` 仍按普通删表处理。

开启忽略会 WARN 并继续，日志含操作、对象、LSN 和完整 SQL。offset 持久化越过后，关闭参数不会补发历史，也不会自动修复下游或结构，必要时重新对账并建立基线。

=== 通用 DDL 跳过

`schema.history.internal.skip.unparseable.ddl=true` 可跳过流式 DDL 分析或历史模型规划中的解析/不支持错误。
跳过时保留旧模型，不写该语句的 history，不读取当前 JDBC 结构兜底；WARN 记录 LSN、对象编号、SQL 和原因。

该参数不跳过 SQL 缺失、已识别捕获表 DDL 的无效对象编号、CTAS 字典失败、DML 解析、归档读取或身份校验错误。上述三个专用策略仍独立生效。

[WARNING]
====
跳过真实结构变化可能导致后续行解析失败，或按旧列位置/类型输出错误数据。只在确认语句影响并接受后果后启用；持久化越过后无法靠关闭参数自动恢复。
====

=== 词法和默认值

支持双引号转义、N/Q 字符串、行注释、块注释和 hint；嵌套块注释按 `NESTED_C_STYLE_COMMENT` 处理。
8.1.3.162 应使用 `BACKSLASH_ESCAPE=0`，值为 1 的字符串语义尚未适配。标识符规则见 <<dameng-case-sensitive,大小写>>。
MySQL 可执行注释、`#` 注释和 PostgreSQL dollar string 不作为原生语法处理。

常量默认值按历史列类型转换，表达式如 CURRENT_TIMESTAMP 不在 Connector 中求值。
`0x` 二进制常量支持奇数位左补零，定长 BINARY 在右侧补零；输出遵循 `binary.handling.mode`。
DDL 语法覆盖和实库可执行性分别记录在模块 `src/test/testing.adoc` 的官方 SQL 语料章节。

JSON 中 bytes 常呈 Base64；Decimal 的 JSON 表示还取决于 Converter 设置，不能把 Connect BYTES 直接理解为业务字符串。

|===
|达梦类型/物理类型 |Connect 类型 |逻辑含义与限制
|BOOLEAN、单比特 BIT |BOOLEAN |true/false；多比特声明须按实际物理映射验收。
|TINYINT、SMALLINT |INT8、INT16 |分别对应 8/16 位整型，输入边界以达梦实际接受范围为准。
|INT/INTEGER、BIGINT |INT32、INT64 |保持整型值；消费端不要用不能精确表示大整数的浮点类型接收 BIGINT。
|REAL / 物理 REAL 的 FLOAT(p) |FLOAT32 |日志文本可能损失精度，见下文。
|DOUBLE / 物理 DOUBLE 或 FLOAT |FLOAT64 |FLOAT(p) 声明在不同模式/参数下可能映射不同，不按名字固定为单精度。
|DECIMAL(p,s)、NUMERIC(p,s)、NUMBER(p,s) |BYTES |默认逻辑类型 `org.apache.kafka.connect.data.Decimal`，保留 scale；string/double 模式改为 STRING/FLOAT64。

|TIMESTAMP/DATETIME |STRING |默认无逻辑类型和时区，例如 `2026-09-24 12:34:56.123456`。isostring 使用 `io.debezium.time.IsoTimestamp`，其他模式见下节。

|INTERVAL |STRING |`io.debezium.time.Interval` version 1，保留年/月或日/时间单位及精确十进制秒。
|CLOB / BLOB |STRING / BYTES |快照可读取完整内容；流式行外值不完整时输出不可用占位值，非完整 LOB CDC。

=== Decimal、时间和默认值

`decimal.handling.mode=precise` 保留固定 scale 或 VariableScaleDecimal；string 输出十进制文本；double 可能损失有效位。

普通 DATE、TIME、TIMESTAMP 默认 `time.precision.mode=sqlstring`，输出无逻辑类型名称、无时区的 STRING。
需要旧 ISO 格式时显式配置 `isostring`。升级或修改此参数会改变字段 schema 和表示，下游须先适配。
在 adaptive、adaptive_time_microseconds 下，普通 `TIMESTAMP(7..9)` 固定输出 IsoTimestamp；显式 nanoseconds 仍受 INT64 纳秒范围限制，connect 只保留毫秒。

日期按原始日历文本解析。LogMiner 的 TO_DATE/TO_TIMESTAMP/TO_TIMESTAMP_TZ 只接受已实现的 ISO 格式，不支持的表达式或格式会失败。
INTERVAL 保留年/月与日/时间单位，不近似折算：例如 `INTERVAL '12-3' YEAR TO MONTH` 输出 `P12Y3M0DT0H0M0S`。
支持 13 种 qualifier、leading precision 1～9、fractional seconds 0～6；不合法范围拒绝，不悄悄舍入。

=== 一致性限制

[cols="2,5",options="header"]
|===
|类型或路径 |限制
|REAL/FLOAT/DOUBLE |已测构建的 LogMiner 文本可能舍入到六位小数，小非零值变零、相邻值合并。Converter 或 BigDecimal 无法还原日志已丢失的位。
|TIME WITH TIME ZONE |旧 8.1.2.128 丢失小数秒；已测 8.1.3.162 的 TIME(1..6) WITH TIME ZONE 严格矩阵通过。
|BLOB/CLOB |快照可读完整内容；流式 OUT_BLOB/OUT_CLOB 或省略的 before 值使用 `unavailable.value.placeholder`。显式 SQL NULL 仍为 null。
|浮点 JSON 往返 |Kafka 4.3.0 schema-enabled JsonConverter 解码会将负零变正零、NaN 变零。原始 Connect 值与数据库实际存储位严格比较；JSON 测试仅允许零符号不同。
|数据库输入边界 |声明精度、极大 NUMBER、多字节 CHAR 和 NaN 是否接受，取决于具体构建与驱动，应以实际存储值验收。
|===

[[dameng-local-time-zone-policy]]
=== TIMESTAMP WITH LOCAL TIME ZONE

此类型采用有损 UTC 假设：快照使用 UTC JDBC 会话，streaming 将 LogMiner 的本地时间文本直接标为 UTC。
LogMiner 未提供足够的原写入会话时区信息，因此带 `Z` 的输出不保证是真实时间点，也不保证与快照相同。

例如在 `+05:45` 会话写入 `2000-02-29 12:34:56.123456`，已测快照值为 `2000-02-29T06:49:56.123456Z`，流式值为 `2000-02-29T12:34:56.123456Z`。
需要真实 instant 或跨阶段时间去重时，应避免依赖此字段；外部固定时区也不能保证所有历史 UPDATE/DELETE 的 before 值可恢复。
该策略不适用于普通 TIMESTAMP 或 TIMESTAMP WITH TIME ZONE。

=== 自定义转换器

`converters` 扩展数据库类型到 Connect 值；Worker 的 key/value.converter 负责序列化；SMT 负责记录变换。
自定义实现需验证 Key、schema、默认值、快照和 streaming 的一致性，不能恢复 LogMiner 已丢失的精度或时区。

[id="dameng-topics"]
== Topic 与消息用途

默认 Topic 命名保留实际 schema/table 名称大小写。原生模式和 PostgreSQL 兼容模式未加引号的标识符通常为大写，例如 `dameng.APP.CUSTOMERS`。
以下以 `topic.prefix=dameng` 为例；自定义 TopicNamingStrategy 或 SMT 会改变相应业务 Topic 路由。

[cols="2,3,4",options="header"]
|===
|用途 |默认名称或配置 |内容与要求
|业务变更 |`dameng.APP.CUSTOMERS` |每表一个 Topic；包含该表快照和 CDC 事件。
|结构变更事件 |`dameng` |供消费者读取的结构通知，默认 `include.schema.changes=true`。关闭不会停止内部历史记录。
|内部 schema history |`schema.history.internal.kafka.topic` 指定 |恢复历史结构和紧急恢复基线。每个 Connector 独占，单分区、完整保留，不配置 compaction。
|事务元数据 |`dameng.transaction` |启用 `provide.transaction.metadata=true` 后发布 BEGIN/END。
|心跳 |`__debezium-heartbeat.dameng` |启用心跳后发布；帮助提交安全 offset，不代表业务表发生变化。
|Worker 内部配置、offset、状态 |Worker 的 `config.storage.topic`、`offset.storage.topic`、`status.storage.topic` |由 Kafka Connect 管理，可由同一 Worker 集群的多个 Connector 共享。不能与 schema history 混用。
|通知 |`notification.sink.topic.name` |启用 sink 通知通道时使用；不是业务 CDC 或 schema history。
|===

schema history 的分区数和保留规则关系到恢复正确性。业务 Topic 的分区数不增加达梦 Task 数；多分区也不提供表级全局顺序。
字段名调整改变事件 schema，不会重命名数据库列。Topic 路由 SMT 只作用于发出的记录，不替代内部 history 配置。

[id="dameng-events"]
== 数据变更事件

下面展示默认 envelope 的 JSON 形态，省略部分可选字段。示例数值仅用于说明，不是实测 LSN。
`JsonConverter` 的 `schemas.enable=false` 时直接得到下面的业务对象；设为 `true` 时外层包含 `schema` 和 `payload`。
Connect 的字段类型与最终 JSON、Avro 或其他序列化形式需要分开理解。

=== Key、Value 与 source

假设 `APP.CUSTOMERS(ID INT PRIMARY KEY, NAME VARCHAR(100))` 新增一行。
Key 为：

[source,json]
----
{"ID": 1}
----

Value 为：

[source,json]
----
{
  "before": null,
  "after": {"ID": 1, "NAME": "Alice"},
  "source": {
    "version": "3.6.4-xingchuang-kafka2.0",
    "connector": "dameng",
    "name": "dameng",
    "ts_ms": 1792368000000,
    "snapshot": "false",
    "db": "DAMENG",
    "schema": "APP",
    "table": "CUSTOMERS",
    "lsn": 1000,
    "change_lsn": 1100,
    "commit_lsn": 1200,
    "event_serial_no": 0,
    "transaction_id": "example-transaction"
  },
  "op": "c",
  "ts_ms": 1792368000100,
  "transaction": null
}
----

[cols="2,5",options="header"]
|===
|字段 |含义
|`before` / `after` |行级变更前后镜像；NULL 行镜像与某列值为 NULL 不同。行外 LOB 可能使用不可用占位值。
|`op` |`r` 快照读取、`c` 插入、`u` 更新、`d` 删除、`t` 清空表。
|`source.name` / `source.db` |逻辑来源 `topic.prefix` / 配置的 `database.dbname`。后者不是 PDB、schema 或 JDBC URL 的路由参数。
|`source.schema` / `source.table` |历史位置对应的逻辑表标识。
|`source.lsn` |安全重放起点，可能被长事务固定；不是已经挖到的最大 LSN。
|`source.change_lsn` |这条变更对应的日志位置。
|`source.commit_lsn` |事务提交位置；同事务的多条变更可能相同。
|`source.event_serial_no` |事务内记录序号，从零开始，可因过滤而不连续；不是 Kafka offset，也不等同于 transaction.total_order。
|`source.transaction_id` |达梦日志事务标识。不能假设跨数据库重建或所有恢复世代永久唯一。
|`source.snapshot` |是否来自快照；可能为 `true`、`last`、`incremental` 或 `false`，按实际快照阶段解释。
|`source.ts_ms` / 顶层 `ts_ms` |来源时间 / Connector 构造事件的时间；公共 envelope 还可提供 `ts_us`、`ts_ns`。它们不是 Kafka 消费确认时间，时钟差和来源时间粒度影响延迟计算。
|`transaction` |启用事务元数据时的事务 ID 和事件顺序；默认未启用。
|===

复合主键的 Key 包含全部主键列。唯一索引或 UNIQUE 约束不会自动当作主键。
无主键表支持普通 snapshot 和 CDC，默认 Key 为 null；用 `message.key.columns` 可以指定业务键，但必须自行保证非空、唯一和稳定。
这不会创建数据库主键，也不等于该表具备已验证的增量快照条件。

=== 操作类型和下游处理

[cols="1,3,3,4",options="header"]
|===
|op |before |after |说明
|`r` |null |当前行 |初始/增量快照读取，不表示数据库刚刚 INSERT。
|`c` |null |新增行 |INSERT 的提交结果。
|`u` |旧行 |新行 |更新的行级镜像；一条批量 SQL 可能产生多个事件。
|`d` |旧行 |null |删除事件，消费者应按 Key 删除其副本。
|`t` |null |null |TRUNCATE 表级事件，Key 为 null；默认 `skipped.operations=t` 不发布。需要时显式设置 `skipped.operations` 为空字符串。
|===

以下展示 update、delete 和 truncate 的 envelope 片段，实际消息还包含 source 和时间字段：

[source,json]
----
[
  {"before":{"ID":1,"NAME":"Alice"},"after":{"ID":1,"NAME":"Bob"},"op":"u"},
  {"before":{"ID":1,"NAME":"Bob"},"after":null,"op":"d"},
  {"before":null,"after":null,"op":"t"}
]
----

默认 `tombstones.on.delete=true`：有 Key 的 DELETE 后再发送相同 Key、Kafka value 为 null 的 tombstone，供 compacted Topic 清理旧值。
tombstone 不是 `{"after":null}`，也没有 envelope。无 Key 表无法依赖主键压缩清理。
主键更新产生旧 Key 的 delete、可选 tombstone、新 Key 的 create，公共发射器还提供新旧 Key 关联 header。
中途重启可能重发旧 Key 的 delete。下游应使用幂等写入/删除，不要只靠统计消息数推断数据库当前行数。
TRUNCATE 没有逐行 Key，多分区消费时不能假定其与所有分区内消息具有全局顺序。

=== 结构变更事件与内部 history

启用 `include.schema.changes` 时，结构变更 Topic 的 Key 包含 `databaseName`，Value 包含 `source`、`ts_ms`、`databaseName`、`schemaName`、`ddl` 和 `tableChanges`。
`tableChanges` 描述 CREATE、ALTER、DROP 等结构变化，包含列、主键和表标识等结构化信息；它不是一条业务行。
初始结构快照也会生成结构事件，DDL 文本可能为空。消费者应读取结构化定义，不能假定每条记录都有可执行 SQL。

[source,json]
----
{"databaseName":"DAMENG"}
----

单次加列事件的字段片段示意：

[source,json]
----
{
  "databaseName": "DAMENG",
  "schemaName": "APP",
  "ddl": "ALTER TABLE APP.CUSTOMERS ADD EMAIL VARCHAR(200)"
}
----

内部 history 保存恢复所需的完整结构、位置和达梦对象属性；结构变更 Topic 是面向消费者的通知，两者不可互相替代。
不要从业务结构事件手工拼出 history，也不要清空 history 后保留旧 offset 继续采集。

=== 事务元数据

设置 `provide.transaction.metadata=true` 后，事务 Topic 发布如下形式的边界消息，业务事件附带 transaction 字段：

[source,json]
----
[
  {"status":"BEGIN","id":"example-transaction","ts_ms":1792368000000,"event_count":null,"data_collections":null},
  {"status":"END","id":"example-transaction","ts_ms":1792368000100,"event_count":2,
   "data_collections":[{"data_collection":"APP.CUSTOMERS","event_count":2}]}
]
----

[source,json]
----
{"id":"example-transaction","total_order":1,"data_collection_order":1}
----

`total_order` 是已发出的事务数据事件顺序，`data_collection_order` 是该表在事务内的事件顺序，均从 1 开始。
计数反映捕获范围和事件处理路径，不等于数据库原始事务修改的所有行数，也不包含 tombstone 作为新的行变更。
达梦 BEGIN 的时间来自所处理的日志行，END 使用 Connector 处理时间；不能将两者差直接当作数据库事务执行时长。
事务元数据提供下游重组依据，但不会让多个业务 Topic 的消息自动原子可见。

== Connector 参数参考

参数写在 REST 请求的 `config` 中。下表默认值取自当前分支，容量单位为字节、时间单位以参数名为准。
空值或无默认值不等于必填；仅明确标为必填的项目必须配置。
Connector 参数、Worker 参数和数据库参数是三层不同配置，例如 `CONNECT_MAX_QUEUE_SIZE` 只生成 Worker 属性，不会替任务设置 `max.queue.size`。
本节覆盖当前公开配置描述中的字段，以及实际读取但由公共服务或 history/Topic 组件另外定义的配置；内部调试开关不作为受支持的生产接口。

[id="dameng-recovery"]
== 恢复、升级与主备切换

=== 普通重启与升级

保留 Connector 名称、`topic.prefix`、offset、独占的完整 schema history 和所需归档，从确认位置重放。
`source.lsn` 可能被长事务固定；本地临时缓存不参与重启恢复。缺档、history 缺失或身份不匹配时停止，`no_data` 不会跳过故障位置。

升级前保存 REST 配置、Worker 支持的 `GET /connectors/{name}/offsets` 结果和旧镜像。
缺失 `compatibility_signature` 或 `capture_scope` 的旧 offset 不能手工补造；通常用新 Connector 名称、`topic.prefix`、history Topic 和显式 `snapshot.mode=initial` 建立基线。
回滚镜像前也须确认旧插件能读取新 offset/history 格式。

=== 显式放弃积压并重建基线

仅在接受历史丢失时，在完整 REST 配置中设置新的 nonce：

[source,json]
----
{
  "recovery.restart.nonce": "incident-20261105-01",
  "recovery.incremental.snapshot.auto.start": "false"
}
----

新 nonce 跳过旧位置到当前基线的历史，包括更新、删除和旧主键；即使 `snapshot.mode=initial`，也不扫描存量行。
需要补数时稍后发送增量快照信号，或将 auto.start 设为 true，在新基线创建时安排全部捕获业务表的补数；要求信号表和目标表主键。
补数只读当前行，旧删除和旧主键仍须对账清理。

[cols="2,5",options="header"]
|===
|配置变化 |行为
|新的非空 nonce |创建新世代。最多 128 个不含空白的可打印 ASCII 字符。
|同值、移除或留空 |恢复当前世代，不再重选位置。
|重用更早的 nonce |拒绝。
|仅修改 auto.start |不触发新恢复或另一次补数。
|`snapshot.mode=initial_only` |不能与恢复 nonce 组合。
|===

建立基线仍需共享锁，等待已写捕获表的事务结束，受 `snapshot.max.duration.ms` 限制。
nonce、结构、offset 和可选补数计划先写入一条 history 记录，再允许确认新位置；崩溃后复用已持久化基线。
完整基线须能放入单条 Kafka 消息，受 producer、Topic 和 Broker 大小限制。
JMX 的 `RecoveryNonce`、`RecoveryBaselineLsn` 可确认当前世代。

[id="dameng-primary-standby-recovery"]
=== 无 VIP 主备恢复

配置 `database.failover.hosts=dm-a.example.com:5236,dm-b.example.com:5236`，成员须为同一物理数据库家族、`N_EP=1`，保持唯一 OPEN PRIMARY。
驱动固定 `loginMode=1`、`loginStatus=4`、`rwSeparate=0`、`autoReconnect=0`、`switchTimes=1`、`switchInterval=200`，禁止冲突覆盖。
重连由 Connector 按 `errors.max.retries` 管理，未确认事件可能重放。

切换步骤：

. 确认备库已应用所需 redo，两端归档连续、地址可达。
. DBA 执行 switchover；主库故障时先隔离旧主，再执行非强制 takeover。
. 确认唯一 PRIMARY/OPEN 和实时归档健康，保留配置、offset/history，观察 Task 与 `OldestReplayLsn` 恢复。

Connector 校验 PERMANENT_MAGIC、SYS.SYSOPENHISTORY 锚点、来源主库链和已应用 LSN。
open history 最多 128 条；锚点丢失、时间戳排序歧义、应用 LSN 倒退或归档分叉均停止。高当前 LSN 不能代替这些检查。
旧单地址 offset 没有主备锚点，不能仅添加 failover.hosts 升级，应新建身份/基线，或接受有损恢复。

[id="dameng-standby-capture"]
=== 备库采集

使用支持备库 LogMiner 的构建，在主库地址配置之外增加：

[source,json]
----
{
  "database.failover.hosts": "dm-a.example.com:5236,dm-b.example.com:5236",
  "database.standby.hosts": "dm-a.example.com:5236,dm-b.example.com:5236",
  "database.standby.replay.timeout.ms": "60000",
  "signal.data.collection": "CDC.DBZ_SIGNAL"
}
----

两组列表可相同，驱动分别选择主库和备库，两条连接使用相同账号。

[cols="2,5",options="header"]
|===
|连接 |职责
|主库（`loginMode=1`） |信号表创建、命令和水位 INSERT/DELETE、heartbeat.action.query、初始快照共享锁。
|备库（`loginMode=2`） |LogMiner、结构和对象编号读取、初始与增量快照查询。
|===

用户信号也必须写入主库。初始快照先锁主库、取主库 LSN、等备库追平，再读取备库，最后释放锁；因此仍影响主库写入。
增量快照在主库提交低水位，等备库应用后读取块，再提交高水位，避免补回备库尚未删除的旧行。

挖掘上界为 `min(归档上界, V$RAPPLY_SYS.SLSN, V$RAPPLY_PARALLEL_INFO.RPKG_LSN)`，并检查角色和来源身份。
等待超过 `database.standby.replay.timeout.ms`、角色改变或连接失败时，不确认未完成快照；读取失败不跳表。连接类错误按重试预算恢复，权限和 SQL 超时需处理原因。

切换后 Task 重选主备节点。没有 OPEN STANDBY 时停止等待，不回退到主库采集；两节点中备库升主后，须有另一个可用备库才能恢复。

=== 快照共享锁指标与日志

当前锁指标为 `SnapshotLockWaiting`、`SnapshotLocksHeld`、`LockedTableCount`、`SnapshotLockWaitDurationMillis`、`SnapshotMaxLockWaitDurationMillis`、`SnapshotLockHoldDurationMillis`。
持锁时间从第一把共享锁成功开始，包含后续锁等待、结构/行读取、队列等待和 rollback 执行。获取耗时覆盖整个 LOCK TABLE JDBC 调用，不是纯数据库阻塞时间，两种耗时不能相加。
成功 rollback 后当前值立即归零，最近结果通过 `LastSnapshotLockStatisticsAvailable`、`LastSnapshotLockedTableCount`、`LastSnapshotLockWaitDurationMillis`、`LastSnapshotMaxLockWaitDurationMillis`、`LastSnapshotLockHoldDurationMillis` 保留五分钟或直到下次快照。
之后 availability=false、结果值归零；Grafana 应据 availability 显示“无近期结果”，不是“持锁耗时为零”。Prometheus 独立保留已采样历史。
reset 清除完成结果，但保留尚未释放事务的活动锁状态；重启会清除内存中的最近结果。

日志在每次加锁前 INFO 打印表名，成功后打印耗时，事务 rollback 成功后打印释放表数、累计/最大获取耗时及持锁时长。
获取失败和 rollback 失败会 WARN；rollback 失败明确标记释放未确认，不发布成功完成结果，清理前保留最后观察的状态。
增量快照不使用此类贯穿全表快照的共享锁，因此不能用这些指标度量增量查询全部数据库锁行为。

[id="dameng-incremental-snapshot-monitoring"]
=== 增量快照进度与性能指标

使用 `context=snapshot` 下的 `IncrementalSnapshot*` 属性。初始与增量快照共用部分公共指标，应以下列独立属性区分阶段。

[cols="3,4,6",options="header"]
|===
|JMX 属性 |Prometheus 指标后缀 |定义与限制
|`IncrementalSnapshotRunning` |`running` |有未完成增量快照为 1，暂停时仍为 1；无未完成工作为 0。不是初始快照状态，也不是补数成功标志。
|`IncrementalSnapshotPaused` |`paused` |增量快照已暂停为 1；短暂停可能在抓取间隔之间发生。
|`IncrementalSnapshotPhase` |`phase{phase="..."}` |当前阶段的 info 风格样本，值为 1；阶段包括 idle、preparing、reading、waiting_close、emitting、paused、failed。阶段变化后旧标签在后续抓取中消失，不是永久累积的每阶段计数。
|`IncrementalSnapshotCurrentTable` |`current_table{table="schema.table"}` |当前表的 info 风格样本，值为 1；无当前表时不导出空表名。抓取可能漏过处理很快的小表。表标签不是每表累计行数；面板还按 running 过滤，失败后即使底层保留表名也会隐藏。
|`IncrementalSnapshotRemainingTableCount` |`remaining_tables` |尚未完成的增量快照表数，包含当前表；暂停保留，完成后为 0。不是剩余行数、完成百分比或 ETA。
|`IncrementalSnapshotRowsScanned` |`rows_scanned_total` |本 Task 生命周期内所有增量快照 JDBC 读到的累计行数，包括重读和随后被 CDC 去重的行。
|`IncrementalSnapshotRowsEnqueued` |`rows_enqueued_total` |本 Task 生命周期内增量快照行事件成功 dispatch 入队的累计条数；不含流式 DML，不代表 Kafka ack 或下游消费。
|`IncrementalSnapshotWindowsCompleted` |`windows_completed_total` |本 Task 生命周期内成功完成发送的窗口数；末块可不足 chunk.size，不能以块数乘块大小替代准确行数。
|`IncrementalSnapshotLastQueryDurationMillis` |`last_query_duration_seconds` |最近完成读块的耗时，含 JDBC 查询、取数、类型转换与构建去重缓存；进行中的查询不提前更新。
|`IncrementalSnapshotCurrentCloseWaitDurationMillis` |`current_close_wait_duration_seconds` |当前 CLOSE 写入提交返回后，等待对应 CLOSE 被处理的实时经过时间；只要已写 CLOSE 仍未处理就继续计时，暂停期间也可能增长；Grafana 仅在 waiting_close 显示是 UI 策略。
|`IncrementalSnapshotLastCloseWaitDurationMillis` |`last_close_wait_duration_seconds` |最近完成的 CLOSE 确认等待，含归档可见性、主备回放、挖掘与分发等待；不是纯 LogMiner 数据库耗时。
|`IncrementalSnapshotLastEmitDurationMillis` |`last_emit_duration_seconds` |最近完成本块缓存发送耗时，含转换、分发及队列等待；不含 Kafka 确认，进行中的发送不提前更新。
|===

表中 Prometheus 后缀加 `dameng_incremental_snapshot_`，毫秒转换为秒。counter 累计整个 Task 生命周期，重启归零；读取数含重读和去重，入队数不等于 Kafka 确认数。
`dameng:incremental_snapshot_scan_rate_rows` 和 `dameng:incremental_snapshot_enqueue_rate_rows` 使用两分钟 rate，表示行/秒。短阶段可能在抓取间隔中被漏过，剩余表数不能换算为剩余行数或 ETA。

按当前阶段排查：

* preparing：主库信号写入、提交和备库回放屏障。
* reading：主键索引、分块 SQL、JDBC 取数与类型转换。
* waiting_close：归档延迟、备库回放、LogMiner 和分发等待。
* emitting：事件队列、Worker 与下游发送压力。

增大 `incremental.snapshot.chunk.size` 可摊薄水位成本，同时增加去重缓存和单块停顿，应结合行宽与堆预算验证。

=== Prometheus 与 Grafana

部署资源位于 `debezium-connector-dameng/docker/monitoring/`。默认镜像内置 Agent 1.4.0 和 `jmx-exporter.yaml`，通过 `KAFKA_OPTS` 启用 `9404/metrics`，运行时无需另挂载 JAR。
Compose 发布 9404 端口后可检查：

[source,shell]
----
curl -fsS http://localhost:9404/metrics
----

显式设置 `KAFKA_OPTS` 会覆盖镜像默认值，增加 JVM 参数时保留一份：

[source,yaml]
----
environment:
  KAFKA_OPTS: "-javaagent:/opt/jmx/jmx_prometheus_javaagent-1.4.0.jar=9404:/opt/jmx/jmx-exporter.yaml -Duser.timezone=UTC"
----

设为空字符串可关闭 Agent。自定义 Exporter 规则可只读覆盖 `/opt/jmx/jmx-exporter.yaml`；旧 bind mount 会覆盖镜像内置版本，迁移时应核对。
修改 javaagent 启动参数需重建 Worker 容器。

Prometheus 示例，目标地址须从 Prometheus 可达：

[source,yaml]
----
scrape_configs:
  - job_name: dameng-connect
    scrape_interval: 15s
    static_configs:
      - targets: ['dameng-connect:9404']
rule_files:
  - /etc/prometheus/dameng/prometheus-rules.yaml
----

挂载同目录的 `prometheus-rules.yaml`，将 `dameng-cdc-dashboard.json` 导入 Grafana 并选择 Prometheus 数据源。
自动加载可使用 `grafana-provider.yaml`，面板 UID 为 `dameng-cdc-overview`。
「源标识」对应 `topic.prefix`，「Connect 任务」对应 REST 名称，应选中同一任务；JVM 指标属于整个 Worker。
UI 修改面板后须导出回源码，否则 provisioning 加载可能覆盖修改。

==== Kubernetes / Prometheus Operator

Pod 声明 `metrics:9404` 容器端口，按实际标签和命名空间修改样例后应用：

[source,shell]
----
kubectl apply -n debezium -f debezium-connector-dameng/docker/monitoring/kubernetes/pod-monitor.yaml
kubectl apply -n debezium -f debezium-connector-dameng/docker/monitoring/kubernetes/prometheus-rule.yaml
----

PodMonitor 的 selector/namespaceSelector 选择 Connect Pod；Prometheus 的 podMonitorSelector/podMonitorNamespaceSelector 选择 PodMonitor，ruleSelector/ruleNamespaceSelector 选择 PrometheusRule。
一个 Prometheus 只部署一份共享规则，各命名空间可分别部署 PodMonitor，避免相同规则重复写入。

没有原始指标时查端口、Pod 标签和 Prometheus target 的 `up`；有原始指标但无积压/速率时，查 **Status → Rules** 中是否加载 `dameng-cdc`、Operator 规则选择器及 `rule_evaluation_failures_total`。

==== 指标判读

* `LatestArchivedLsn - ScannedUpperLsn` 是扫描积压，`ScannedUpperLsn - OldestReplayLsn` 是重放跨度，均不是时间延迟。
* LSN 是 gauge，不用 counter 的 rate；面板的两分钟窗口至少需要两个抓取样本。抓取间隔过长时须同步调整窗口。
* 入队、dispatch 和 Producer 等待可能重叠，不能相加；队列空也可能是源空闲或挖掘慢。
* Producer buffer wait 表示分配缓冲等待，batch-size、record-size、records-per-request 是滚动统计，空闲缺值不当作零。
* 增量快照完成后面板隐藏旧阶段与最近耗时；累计卡片仍为 Task 总量，无数据不等于零。

新增埋点需同步 Connector JAR、Exporter、Prometheus rules 和面板。只改面板不能从旧插件取得新指标。
规则检查在 monitoring 目录执行：

[source,shell]
----
docker run --rm --entrypoint /bin/promtool -v "$PWD:/rules:ro" -w /rules \
  prom/prometheus:v3.5.0 test rules prometheus-rules.test.yaml
----

[id="dameng-faq"]
== 常见问题与故障处理

[cols="3,4,5",options="header"]
|===
|现象 |优先核查 |处理原则
|插件列表没有达梦 |plugin.path、解压层级、驱动/依赖、所有 Worker 是否更新 |先让完整类名出现在 connector-plugins，再创建任务。
|Included connector type 不匹配 request type |validate URL 是否写了 dameng 简称；POST/PUT 对象层级 |使用完整类名，POST 包含 name/config，PUT config 只交配置对象。
|Task RUNNING 但没有已有数据 |snapshot.mode、是否已有 offset、是否观察正确 Topic |默认 no_data 不扫描存量；需要时显式 initial 或增量快照，不删除 offset 试错。
|include 中的表没消息 |启动表清单/WARN、账号可见性和 SELECT、正则及大小写、事务是否提交 |先用同一 CDC 账号查表及元数据。不可见表不会因写在 include 中就自动获得权限。
|ARCH_LSN 很大，source.lsn 不前进 |ScannedUpperLsn、OldestReplayLsn、OpenTransactions |长事务可能固定安全起点；分别判断扫描积压和恢复跨度，不把两个 LSN 直接当处理速度。
|数据库有变化但 LatestArchivedLsn 未变 |归档策略、实际归档文件、磁盘空间 |只有已归档日志可挖；心跳和扩大窗口不会强制保证归档完成。
|持续追不上归档 |前进/重建/dispatch 时间、入队等待、producer buffer wait |按瓶颈调窗口、fetch、batch/压缩/资源；不要只增加 max.queue.size。
|持锁久或快照超时 |加锁日志、持锁指标、活跃写事务、快照数据量、下游队列 |结束不必要的长事务或调整维护窗口/预算。no_data 仍有结构锁；增量快照避免全程共享锁但需先建立结构基线。
|旧 LSN 归档缺失 |最老 replay LSN 到当前的完整归档范围 |补回正确来源的归档后恢复，或采用新身份初始快照；接受历史损失时才显式 nonce。重复 restart 和 no_data 不会修复。
|不支持 DDL，重启后再次失败 |错误 LSN、原始 SQL、对象身份和兼容参数 |处理历史语句或重建基线；接受风险时按 <<dameng-ddl,DDL 策略>> 显式忽略，不用当前表定义替换旧结构。
|capture_scope differs / 范围调整被拒绝 |旧范围描述、初始快照状态、数据库选择、信号表、table.ignore.builtin |普通表扩缩按范围调整机制处理；快照未完成或不支持的身份变更不能直接恢复。保留原配置排查，不填造签名或删除 history。
|compatibility_signature 不匹配/缺失 |旧插件 offset、模式/词法/大小写参数、主备参数一致性 |不要填造签名。只有确认临时设置期间没生成受影响历史，才可还原设置恢复，否则新基线。
|内存/事务数/单 SQL 上限或磁盘失败 |具体错误字段、SQL 连续片段、并发事务、落盘可用容量/权限 |调整对应资源或负载后重启；队列、事务缓存、单 SQL 是不同预算。不能跳过超限事务。
|主备切换后停止 |唯一 OPEN PRIMARY、身份锚点、应用 LSN、归档连续性 |由 DBA 修复主备状态并保留 history/offset；高当前 LSN 不足以证明旧确认数据已复制。
|备库 -710 |实际构建、STANDBY 角色及失败的 SQL |旧 8.1.2.128 构建的 JDBC LogMiner 注册归档受角色限制；8.1.3.162 备库采集需配置 database.standby.hosts，信号 DDL/DML 路由到主库。业务 SQL 或水位误写备库也会报此错误，不能通过放开任意备库写入解决。
|Kafka 2.0 history 创建失败 |history Topic 是否预建、单分区和保留策略 |按部署章节预创建，检查认证与权限；延长 timeout 不修复协议不兼容。
|Grafana 无数据 |Task 是否运行、Agent 是否加载、Exporter 是否有对应规则、新版 JAR、标签筛选 |先 curl metrics，再查 Prometheus target 和 Grafana；缺 series 不当成数值零。
|===

连接类 IOException、SQLState 08、可恢复连接错误及主备无可用主库的特定错误按 errors.max.retries 重试。
快照预算、SQL timeout、history 存储、落盘损坏、未知 DDL 和缺档等不是靠重连能修复的错误，应先处理原因。
首次排查保存版本、配置键名、脱敏日志、LSN 和失败语句；不要把凭据、业务行或 history 全文直接公开。

多个 Worker 只提高调度容错，不增加单个 Connector 的 Task 数。扩缩表见 <<dameng-capture-scope-changes,范围调整>>，升级与回滚见 <<dameng-recovery,恢复>>。
REST 访问由部署层保护；凭据使用配置提供器，日志、临时文件、offset 和 history 按源数据权限保护。

== 构建、测试与发布

使用 JDK 21 或更高版本和根目录 `./mvnw`。Java 17 是 Connector 字节码目标，不是构建 JDK 要求。
改 Java 代码后先格式化；`-am` 包含本地依赖模块：

[source,shell]
----
./mvnw -pl debezium-connector-dameng -am process-sources
./mvnw -pl debezium-connector-dameng -am test
./mvnw -pl debezium-connector-dameng -am verify -Pdameng-tests
----

Surefire 在 test 阶段执行单元测试，Failsafe 在 integration-test 执行集成测试、verify 检查结果。达梦默认跳过 IT，须选择测试 profile。

[cols="3,5",options="header"]
|===
|Profile |范围
|`dameng-tests` |普通数据库与嵌入式引擎回归。
|`dameng-probes` |手动能力诊断，只选择 `*ProbeIT`。
|`dameng-performance-tests,assembly` |`*BenchmarkIT` / `*PerformanceIT`，须满足各自启用条件；生成器场景使用 `-Ddameng.perf.enabled=true`。
|`dameng-connect-tests,assembly` |插件打包和独立 Kafka Connect Worker 回归。
|`dameng-all-tests` |普通、诊断和性能类，排除独立 Connect；不绕过启用条件。
|===

单元测试用 `-Dtest=类名`，集成测试用 `-Dit.test=类名`。例如：

[source,shell]
----
./mvnw -pl debezium-connector-dameng -am verify -Pdameng-tests \
  -Dit.test=DamengConnectorIT -Dfailsafe.failIfNoSpecifiedTests=false
----

嵌套套件与其他类的 `#方法` 筛选应分次执行，混合到一个 it.test 值可能漏跑嵌套套件。核对 XML 中实际执行的类与数量。

PostgreSQL 兼容模式的专用回归覆盖快照、引用名大小写、归档 DDL、默认值、CRUD 和重启恢复。
测试只配置自己创建的容器，不修改外部数据库：

[source,shell]
----
./mvnw -pl debezium-connector-dameng -am verify -Pdameng-tests \
  -Dit.test=DamengPostgresCompatibilityIT -Dfailsafe.failIfNoSpecifiedTests=false \
  -Ddameng.compatible.mode=7
----

共享的 `DamengConnectorIT`、`DamengCaseSensitivityIT` 和 `DamengDatatypesIT` 也可通过 `-Ddameng.compatible.mode=7` 验证模式 7。
报告位于模块 `target/surefire-reports/`、`target/failsafe-reports/`，不同调用会残留历史 XML；同一工作区串行运行。
覆盖率使用 `clean verify -Pdameng-tests,dameng-coverage` 收集新数据，95% 行覆盖率门槛不替代行为验收。
