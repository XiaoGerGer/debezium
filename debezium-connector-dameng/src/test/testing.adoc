The floating point tests expose existing discrepancies: high-precision stored values become rounded streamed values and some tiny nonzero values become zero. The raw snapshot Struct preserves negative zero in all five declarations tested; its subsequent JSON decoding does not preserve the sign. Positive and negative zero are treated as equal by numeric consistency assertions. The earlier direct LogMiner probe located ordinary fractional rounding in SQL_REDO/MINE_VALUE before connector conversion. The JSON round-trip discrepancy is a separate issue in the current Kafka conversion path, not evidence that DM LogMiner lost the snapshot value. The exact-value engine and floating boundary assertions remain available with `-Ddameng.datatype.floating.diagnostics=true`; they are skipped in the routine database suite while the DM LogMiner precision limitation is unresolved. NaN and other database-rejected inputs are absent from the current CDC consistency catalog. An explicit diagnostic run still fails on any stored-value discrepancy; a routine suite result does not establish lossless floating point CDC. The earlier successful coverage/build results below predate these additional semantic assertions.

The REAL upper-bound fixture follows the https://eco.dameng.com/document/dm/zh-cn/pm/dm_sql-introduction.html[official DM SQL type specification]: its documented range ends at `3.4E38`, below Java's `Float.MAX_VALUE`. The local JDBC driver's `setFloat` rejects the latter as overflow. Such a rejected input is not a connector data-loss result; the regression uses the float representation of the documented bound instead.
The floating boundary catalog no longer inserts `3.5E38` or `1E309` as rejection-only examples because they exceed the documented REAL and DOUBLE ranges.

To retest the unresolved floating precision limitation, run the strict assertions explicitly. A nonzero exit indicates that the database still returns a different stored value through LogMiner.

=== Datatype boundary and compatibility mode matrix

Compatibility strategy unit tests are in `io.debezium.connector.dameng.compatibility`, matching the production package.
`DamengCompatibilityTest` covers open mode identifiers, registry conflicts, immutable environment parameters and native DDL rules.
`DamengConnectionIT` and `DamengConnectorIT` retain the database and task integration checks in the main connector test package.


`DamengDatatypeCases` supplies the same inputs to `DamengDatatypesIT` (complete embedded engine) and `DamengDatatypeProbeIT` (JDBC/archived-redo components).
The catalog covers accepted integer bounds and their neighbors, zero, BIT coercion, every DECIMAL precision from 1 to 38 with distinct scale endpoints and midpoint,
decimal aliases and handling modes, accepted unconstrained NUMBER exponent values, floating declarations and IEEE finite boundaries, all documented TIME precisions 0 through 6,
all documented TIMESTAMP precisions 0 through 9, BCE/early/future dates and the calendar transition, fractional time zones and offset bounds, character/byte length boundaries,
empty strings, embedded NUL, Unicode and supplementary characters, binary padding/length and all four binary handling modes.
Declared VARCHAR/VARBINARY maxima use `USING LONG ROW` to distinguish the declared length limit from the page's shorter row limit.
The CDC consistency catalog contains only inputs accepted by the tested database build; it does not treat database rejection as a connector result.
INTERVAL coverage includes all thirteen qualifiers, every leading precision 1 through 9, and the full cross product with fractional precision 0 through 6 for the four qualifiers ending in SECOND, plus default declarations (346 cases).
Each declaration exercises the positive and negative maximum, zero, the smallest positive and negative unit, and NULL.
Independent interval expectations use the JDBC driver's binary-backed component getters, not the production SQL literal decoder or the common interval formatter.
External LOB streaming and arbitrary user-defined complex types remain outside this catalog.

Each accepted boundary is read independently from JDBC at the relevant operation, then compared with snapshot, committed INSERT, value-to-NULL UPDATE,
NULL-to-value UPDATE and DELETE before/after images. The complete engine also checks event keys.
Expected temporal values use JDBC's stored textual calendar representation and the declared precision; decimal and binary settings use standard Java representations.
Expected values never come from the connector converter or from a later current-row query used to reconstruct historical events.
Floating assertions compare exact bits. Fixed decimals check scale as well as value.
Raw Connect rows and schema-enabled JSON round trips are checked independently.
Checks accumulate until the finite workload is consumed, so a snapshot JSON assertion does not suppress the streaming assertions.
Fatal engine decoding still stops that test instance; the component layer continues checking other independently captured events.
Ancient and future non-zone temporal boundaries have separate test instances so a fatal year-format problem does not hide the other boundaries.

`dameng.compatible.mode` is a test-fixture property, defaulting to `0`; it is not a production connector configuration.
Before creating test tables, the fixture changes only its own disposable container, restarts it and verifies the system, session and file values.
An external `dameng.hostname` is read and checked against the requested mode; it is never reconfigured or restarted.
The fixture records server build, JDBC version, driver, charset, selected parameters and a numbered case catalog.
Production still rejects nonzero modes. The component tests invoke the real connection, archived LogMiner, DML/DDL parsers and converters directly;
they do not mock the mode guard. Their success is component evidence, not full Connector support.
The complete-engine layer retains the startup failure for nonzero modes until compatibility is implemented.

=== Large transaction regression

`DamengLargeTransactionIT` is an independent real-database suite for finite large-transaction correctness checks. == Operational safeguards and regression scope

`LogMinerTransactionBufferTest` checks the production buffer's resident transaction metadata, single-SQL payload size, memory spill threshold and disk quota. Cumulative input bytes and rows are telemetry only. Regression cases exceed the former 512 MiB and 1,000,000-row limits, verify forced spilling and exact-limit SQL continuation assembly, and reject all publication/replay-position APIs after a resource failure. `DamengRuntimeSafetyIT` verifies delivery with the retired limits set to 1 and forced spilling, and verifies that a single-SQL resource failure does not publish partial results.

`DamengConnectorConfigTest` covers finite positive socket and initial-snapshot timeouts, the driver's `socketTimeout` mapping, rejection of the ambiguous raw `database.socketTimeout` input, nonnegative statement timeouts, and rejection of unsupported parallel snapshot connections. Real tests must establish that JDBC timeout and connection abort release locks on the deployed DM version, including a snapshot blocked by downstream backpressure. Unit mocks alone cannot establish server-side session termination.

Offsets now require a `capture_scope` signature of database/schema/table include and exclude expressions, `table.ignore.builtin`, and `signal.data.collection`. Older offsets lacking the signature and changes to any signed expression are rejected. This applies to narrowing filters and equivalent-expression rewrites as well as expanding filters. Recovery tests must keep the exact signed values or use a new identity, fresh history and an initial snapshot. Column filters and `snapshot.include.collection.list` do not change the table coverage signature.

Resource limits do not remove history reconstruction required to validate cross-window rollback. A resource failure keeps the replay position unchanged and can recur after restart until an operator addresses the actual memory, single-SQL or disk limit with sufficient resources and retained archives. `log.mining.buffer.max.bytes` and `log.mining.buffer.max.records` are accepted only for compatibility and ignored with a warning; they do not configure the independent `log.mining.buffer.max.sql.bytes` and `log.mining.buffer.max.transactions` limits. Archive deletion, prolonged network loss and driver/server failure combinations remain separate fault-injection requirements.
