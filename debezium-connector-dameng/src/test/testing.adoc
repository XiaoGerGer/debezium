The floating point tests expose existing discrepancies: high-precision stored values become rounded streamed values and some tiny nonzero values become zero. The raw snapshot Struct preserves negative zero in all five declarations tested; its subsequent JSON decoding does not preserve the sign. Positive and negative zero are treated as equal by numeric consistency assertions. The earlier direct LogMiner probe located ordinary fractional rounding in SQL_REDO/MINE_VALUE before connector conversion. The JSON round-trip discrepancy is a separate issue in the current Kafka conversion path, not evidence that DM LogMiner lost the snapshot value. The exact-value engine and floating boundary assertions remain available with `-Ddameng.datatype.floating.diagnostics=true`; they are skipped in the routine database suite while the DM LogMiner precision limitation is unresolved. NaN and other database-rejected inputs are absent from the current CDC consistency catalog. An explicit diagnostic run still fails on any stored-value discrepancy; a routine suite result does not establish lossless floating point CDC. The earlier successful coverage/build results below predate these additional semantic assertions.

The REAL upper-bound fixture follows the https://eco.dameng.com/document/dm/zh-cn/pm/dm_sql-introduction.html[official DM SQL type specification]: its documented range ends at `3.4E38`, below Java's `Float.MAX_VALUE`. The local JDBC driver's `setFloat` rejects the latter as overflow. Such a rejected input is not a connector data-loss result; the regression uses the float representation of the documented bound instead.
The floating boundary catalog no longer inserts `3.5E38` or `1E309` as rejection-only examples because they exceed the documented REAL and DOUBLE ranges.

To retest the unresolved floating precision limitation, run the strict assertions explicitly. A nonzero exit indicates that the database still returns a different stored value through LogMiner.

=== Large transaction regression

`DamengLargeTransactionIT` is an independent real-database suite for finite large-transaction correctness checks. It covers bounded queue backpressure, an open transaction observed alongside other commits, full and savepoint rollback, and restart from a durable offset in the middle of a transaction. The class reads its limits from JVM system properties; defaults are 10,000 rows, a 512-byte payload, a 300-second timeout, and a 1,000-LSN mining batch. No throughput, memory ceiling, or maximum supported transaction size is implied.

The suite configures a 64 KiB task-wide transaction cache threshold and a test-owned temporary directory to force spilling. The savepoint case verifies that a spilled provisional suffix is replaced by the final rollback view and that the retained UPDATE before image is correct. Restart reconstructs from archives; temporary files are not reused as durable state.

`LogMinerSpillStoreTest` compares the optimized codec byte-for-byte with the original `DataOutputStream` format, including all UTF-16 code units and SQL longer than 64 KiB.
It checks alternating large and small records, independent readers, null/empty values, malformed frames with valid checksums, and truncation after opening a reader.

== Operational safeguards and regression scope

`LogMinerTransactionBufferTest` checks the production buffer's resident transaction metadata, single-SQL payload size, memory spill threshold and disk quota. === Non-table object DDL classification and recovery regression

dependent objects. PROFILE CASCADE only changes user/profile associations and

query of today's dictionary to reconstruct their historical scope.

boundaries. This is not a complete SPL validator or an implementation of

behavior is verified across the supported version matrix. TYPE/CLASS CASCADE, embedded CREATE SCHEMA objects, implicit
auxiliary-table changes, and unsupported table-column types remain outside

The summarizer joins table, non-table, query, function and datatype syntax, catalog calls, isolated SQL, direct SQL, and mapped statement
family evidence by original URL and ordinal, then writes one row per fragment to
`target/official-sql-coverage.jsonl`, a review-friendly CSV to
`target/official-sql-coverage.csv`, one row per extracted or classified attempt
to `target/official-sql-attempts.csv`, and counts to
`target/official-sql-coverage-summary.json`.
All retained corpus identities are indexed; removed duplicates are no longer required by the ledger. The current meaning totals,
parent operation families and outstanding review categories are generated in
`target/official-sql-meanings-summary.json`; execution and strict support counts
are generated independently in `target/official-sql-coverage-summary.json`.
These totals can decrease when an incorrect classification or overly broad
completion claim is corrected. The counts are intentionally not duplicated as
a fixed baseline here: semantic grouping, actual JDBC outcomes and supported
CDC behavior answer different questions.
The previous 7,880-complete count is retired. It included routine signatures
classified as non-SQL, partial scripts, fixture substitutions, and no-redo
observations without a mined positive control.

The current outputs deliberately separate three questions:

* `sourceMeaning.complete` means all text has a defensible meaning or explicit
  non-SQL classification. A grammar production can meet this condition while
  still requiring instantiation and database execution.
* `fullSourceResultRecorded` means every original executable statement has an
  actual result, including rejection. It does not mean CDC is supported.
* `reviewComplete` is the conservative supported-result gate. It requires full
  source coverage, matching original source fingerprints, no unvalidated
  rewriting, and the relevant database/redo/Connector evidence. A source
  rejection, unsupported DDL, empty-table DML, unresolved template, or missing
  positive control leaves this false. Unknown routine effects, physical table
  restoration and materialized-view refresh need dedicated data/CDC assertions;
  their absence of mined DML alone cannot satisfy this gate.

`validatedAttemptStatusCounts` separates executed JDBC outcomes from extraction,
isolation and setup results within validated reports. Use
`validatedJdbcExecutedAttempts` when counting statements actually submitted to
JDBC; `validatedRunAttempts` also includes deferred and non-SQL segments.
External tool runs have separate `utility-accepted`/`utility-rejected` process
outcomes and `validatedUtilityExecutedAttempts`. Their command argument arrays
and execution channel are preserved without inventing an `executedSql` or
counting a DEXP/DMFLDR process as a JDBC submission. A successful utility
representative still does not complete every option of the original manual.

Every original statement occurrence is compared with its executed source text.
Repeated runs cannot substitute for two occurrences within the same script.
Literal values and quoted identifier case are preserved when comparing SQL;
backslash-containing SQL stays strict until execution-specific lexical settings
are available. A stronger validated repeat may supersede a weaker success for
identical SQL on the same database version, but cannot erase an earlier failure
or a result from a different fixture. Reports retain the evidence filename,
database version, executing account and relevant parameter context,
original-source verification, rewrite status, and validation flags. A passing
execution under ENABLE_DDL_ANY_PRIV=1 does not supersede a refusal under its
default value 0. Legacy evidence without these guarantees remains visible and unverified.

The non-SQL classifier accepts confirmed complete host/configuration/XML/OS artifacts,
strict output-only execution plans and error messages, and explanatory text
only when its rules exclude executable SQL. The permission appendix names are
retained as GRANT/REVOKE operands requiring instantiation, not non-SQL completion. SQL signatures,
scalar/type grammar, and bare SQL words stay in the SQL inventory. A separate
`classify-official-client-commands.py` recognizes the documented DISQL command
arguments, including all 45 SET properties. Only complete client-only forms
can resolve a fragment as non-SQL. AUTOCOMMIT, EXIT, HOST and script execution
retain transaction or indirect SQL effects for review.
Exact reviewed tool actions override generic shell/configuration exclusions.
ASM disk/file creation, CP/MV, IMPORT/EXPORT, IOTEST, password changes and login
retain their execution channel, storage/session effect and isolated-fixture
requirements. An operation is not harmless merely because it is not JDBC SQL.
DMRMAN BACKUP, RESTORE, RECOVER, MERGE, REPAIR, REMOVE and script inputs retain
their distinct effects. CONFIGURE display forms are separated from configuration
changes. Unreviewed database utility invocations, including import, bulk load,
database initialization and DISQL script execution, remain pending instead of
being completed by a generic utility or shell exclusion.
Whole-source SHA checks prevent an added SQL statement from inheriting an older
non-SQL classification. Returned SQL text and error echoes retain their source
role instead of becoming additional submitted SQL inputs.
DMRMAN SHOW transcripts retain one actual metadata-read input, its separate
echo and copied output; understanding that transcript does not prove a current
tool execution. DISQL VERIFY `original/new` lines and audit-record SQL_TEXT
columns likewise retain output roles. Package definitions, anonymous blocks
and their nested statements stay together. A collection's DELETE method is
not a table DELETE. Known cursor SQL and bindings can be extracted without
pretending that omitted host code, external scripts, debugger targets or
scheduled routine bodies are known.
Local JSON DOM PUT/REMOVE, array-element deletion, native hash-update functions
and client wallet changes retain their actual target instead of becoming table
DML. Conversely, DBMS_METADATA examples can INSERT metadata strings into user
tables and COMMIT, CREATE_WRAPPED creates the wrapped object, and queue dequeue
can consume messages. Scheduler ENABLE can start a known procedure's INSERT and
COMMIT asynchronously; an unknown action remains pending. Prepared-but-unexecuted
SQL, bound strings, copied plan nodes and DDL returned by TABLEDEF are separate
roles. An execution-plan transcript can still contain subsequent DROP INDEX
cleanup inputs. Foreign MySQL/Oracle configuration examples retain their dialect
and do not establish Dameng compatibility-mode support.
Mixed client fragments expose SQL candidates only at unambiguous statement
boundaries; the classifier report retains the current candidate and fragment counts. Each candidate retains start/end offsets and
`executionVerified=false`; output, client commands and unresolved source remain
separate segments. Extraction does not complete or execute those examples.

The optional `--require-all-fragments-resolved` gate still fails while source
records are unresolved. Successful audit execution is not evidence that all
vendor SQL or all Kafka event values are supported. The reports distinguish
JDBC syntax acceptance, actual LogMiner redo and DDL schema planning;
end-to-end DML assertions remain necessary for data correctness.
An interrupted connection records an uncertain outcome, and an unmet prerequisite
records that no SQL was submitted. Neither becomes a syntax rejection. Production
archive-loading failures remain distinct from parser failures; a later raw SQL
LogMiner diagnostic cannot satisfy a supported-family or source-completion gate.
An exception handler may commit successful array-DML rows before raising.
The ledger retains the JDBC rejection alongside independent committed rows
and end-to-end CDC assertions; it does not equate an error with rollback.
Error-code and source-spelling adaptations retain their own rewrite reason
and original SQL. A test client's explicit commit is recorded separately from
the anonymous block when the source itself contains no COMMIT.

=== Semantic grouping for representative CDC tests

`review-official-sql-meanings.py` reads each original fragment, retaining every
classification's original text and offsets, source form, confidence and reason.
It identifies operation/object families, grammar productions, routine signatures
and embedded SQL. Each entry also records the specific remaining work, such as
host extraction, compound-program boundaries, grammar instantiation or missing
object context. No semantic classification creates a database-test result.

`group-official-sql-semantics.py` joins those meanings with the execution ledger.
`target/official-sql-semantic-groups.jsonl` indexes the current retained identities;
`target/official-sql-semantic-summary.json` includes the parent operation families
and finer syntax groups. The hierarchy groups queries under SELECT, table DDL
under CREATE TABLE/ALTER TABLE, and object DDL under CREATE ROLE, CREATE USER,
ALTER SYSTEM and similar concrete families. Clauses and types inherit their
enclosing operation without being discarded as non-SQL. CALL is a parent
category; each concrete routine and overload retains its own identity and
requires its own effect assessment. Unknown call-shaped output fields do not
become confirmed database calls.

Ordinary SELECT and read-only WITH SELECT can share a CDC no-row-redo
representative. SELECT NEXTVAL, FOR UPDATE, SELECT INTO and queries calling
routines remain separate. WITH UPDATE and WITH DELETE are DML. A family
representative proves only its sampled behavior; CREATE TABLE success cannot
prove CTAS, LIKE, partitioning or every optional clause. The family matrix CSV
and per-fragment pending JSONL expose missing variants and their next actions.
The family CSV also separates validated JDBC acceptance, database rejection and
Connector rejection counts, with both passing and failing sample SQL. A passing
REVOKE representative does not erase a failing REVOKE CASCADE variant. Source
meaning and execution grouping share one recognizer so JAVA CLASS, PARTITION
GROUP, MATERIALIZED VIEW LOG and quoted literals cannot silently use different
object identities in the two reports. Queries preserve all routine callees and
additional locking, sequence and SELECT INTO effects; a mixed query cannot
borrow a call-free representative.

Source context also distinguishes string `INSERT(...)` functions from row
INSERT, analytic `PARTITION BY` from table partition DDL, and MERGE PARTITIONS
from MERGE INTO DML. A trigger's event verbs are separate from its body SQL,
which runs when the trigger fires. A package initializer can execute on first
access; a declared cursor does not execute until opened. Known same-page
procedure bodies retain their own fingerprinted context instead of being
treated as opaque calls or independent top-level DML.

Driver operations retain their execution role: statement inspection and
preparation do not execute SQL, and a SQL-looking argument passed to an already
prepared statement may be a bound value. Unknown callbacks, ORM-generated SQL,
external START scripts and import dump contents remain explicit pending work.
Original foreign-dialect examples, malformed terminators and contradictory
copied results remain visible alongside any separate adaptations.

The final source-context review leaves no unread meaning-review entries.
Entries that remain semantically partial have exact-source reviews with an
explicit reason, such as absent external scripts, unresolved generated SQL,
unknown callbacks, omitted code or defects in the published example. These
are reviewed-but-partial sources, not successful executions. A missing fixture
with known operation families remains distinguishable from an unknown SQL
producer. Full source URLs take precedence over page basenames: for example,
`app-dev/index.html` and `sql-dev/index.html` retain separate source identities
and cannot borrow each other's review.
