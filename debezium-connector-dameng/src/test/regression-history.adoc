== 官方 SQL 审计与非表 DDL 验证补充

2026-10-29 在 8.1.3.162 原生模式的官方语料实测中，`STAT ... ON` 的表、索引和 hint 形式均生成 DDL redo，审计时的解析器拒绝了这三种样本。当前已为独立 STAT 语句增加非表分类；这不放开表定义中未实现的 STORAGE/STAT 子句。
`REVOKE ... CASCADE` 的表、列、视图、过程/函数/包、序列、域、同义词和目录授权回收也生成 DDL redo；审计时有 13 个样本因尾部语法被拒绝，后续 CLASS、TYPE 专项又验证了两条同类回收语句。非表 DDL 分类现已接受权限词汇及 `REVOKE ... CASCADE`，这些旧审计数字保留为当时的结果。
同一历史审计源码还拒绝了 CLASS/TYPE 的创建、定义体、编译和删除共十条实际 DDL，以及 ROWID、LONG、BFILE 列的三条建表 DDL。当前为 SQL 程序对象增加的分类不能反推这十条历史样本已经通过重测；特殊列类型映射也未因此扩展。LIBRARY 语句和 JSON 类型声明在该次数据库测试中被数据库拒绝，尚不能据此判断 Connector 支持情况。
默认配置下，未识别的对象类型即使不修改采集表的列结构，也仍可能使任务在相应日志位置停止。
同版本的 `RESTORE TABLE` 实测还发现：目标数据已被备份数据替换，但恢复语句的 LSN 区间没有目标表的 DML redo，独立 marker INSERT 可以正常挖掘。不能依赖 LogMiner CDC 将这类表恢复产生的数据变化同步到下游；解析器未报错不代表恢复数据已被采集。
物化视图专项的 15 个代表语句中，13 个被该数据库版本接受，`COMPILE` 和 `DROP MATERIALIZED VIEW LOG IF EXISTS` 被数据库拒绝。FAST 和完全刷新会产生后台表 DML；当时的分析器拒绝其中 13 条 MATERIALIZED/REFRESH DDL 记录。另三条内部表 TRUNCATE 仅在空历史模型探针中规划失败。后续默认过滤和语句分类用于跳过物化视图内部数据，不代表支持物化视图 CDC；旧审计结果保留为当时的证据。
单实例状态专项验证了 34 条角色、状态、参数和本地归档代表语句，其中 27 条接受、7 条因状态前提被拒绝。新增第二个 LOCAL 归档目的地后，当前生产挖掘连接会重复注册同一日志的副本，报 `-2848 cannot add duplicate logfile`。限定原归档目录的独立 SQL LogMiner 诊断成功，不能据此认为 Connector 已支持多 LOCAL 归档；该问题尚未修复。
`FORALL` 专项通过完整引擎验证了异常处理器提交后再抛错的情形：两个官网示例虽返回 JDBC 错误，已提交的 2 行和 3 行更新仍全部发出 CDC。另一个官网示例绑定错误码 `-25000`，该版本实际返回 `-24381`，因未进入预期处理分支而全部回滚，CDC 为 0；单独适配错误码的代表样本提交及发出 3 行更新。不能仅根据客户端收到错误判断事务全部回滚；原样示例和适配样本的证据分别保留。
可回归测试和逐条证据索引见模块 `src/test/testing.adoc` 的官方 SQL 语料章节。历史审计结果不代表所有缺口均已修复。

== CASE_SENSITIVE=0 标识符适配

`CASE_SENSITIVE` 是建库属性，不是 Connector 参数，也不能通过修改正在运行的任务把数据库切换为模式 0。
Task 自动查询 `SF_GET_CASE_SENSITIVE_FLAG()`，结果仍进入 offset 的 compatibility_signature；重启不能把不同建库属性的历史位置混用。

8.1.3.162 实测：模式 0 的 JDBC 元数据保留不少原始拼写，例如 Dbz_Mixed、Id，而非引号关键词 VaLuE 被保存为 VALUE；LogMiner 的 DDL 保留提交语句的原始拼写。
因此模式 0 对 schema、表、列、主键列和约束统一使用大写作为 Connector 内部及消息中的标识符，历史 DDL 与 JDBC 使用同一规则。默认 Topic 中的 schema/table 部分和消息字段名也相应大写，topic.prefix 本身不变；`'AbC'` 等数据和默认值不改变大小写。
例如物理表 `"Dbz_App"."Dbz_Case"`、列 `"VaLuE"` 对应 `prefix.DBZ_APP.DBZ_CASE` 与字段 `VALUE`。

模式 0 的 include/exclude、列配置、增量快照 data-collections 和下游映射应使用这套规范名称；即使正则显式关闭忽略大小写，也按规范名称匹配。
`signal.data.collection` 的具体表名会自动规范化，已有混合大小写信号表可复用；自动创建时也按统一身份识别，防止水位写进去了却没有被信号处理器认出。
模式 1 的双引号名称保留大小写，非引号名称按现有规则转大写；模式 0 的新命名约定不会改变模式 1 的 Topic 或字段。
本次也修正了信号表的两段名称解析：达梦统一按 schema.table 处理，不采用公共框架的 catalog.table 默认值。此前登录用户与配置 schema 不同且信号表不存在时，自动建表可能落在登录用户 schema；现在按指定 schema 建表，重启复用同一张表。
建库属性与主备读写路由是两个独立能力。物理备库采集及主库信号写入已在 link:../../../documentation/modules/ROOT/pages/connectors/dameng.adoc#dameng-standby-capture[备库采集与主库信号写入] 实现；本节的 CASE_SENSITIVE 回归不代表其与所有主备、字段和兼容模式组合均已覆盖。

=== 按失败阶段归类

预期值独立读取数据库实际存储结果，浮点比较实际二进制位，不是要求数据库存储后仍等于原始十进制输入文本。

=== B：标准 JSON 解码的特殊值差异

5 项聚焦负零用例为 REAL、FLOAT(24)、FLOAT、FLOAT(53)、DOUBLE 的 `-0.0`；2 项 NaN 用例为 REAL 和 DOUBLE。
负零经过编码的 JSON 包含 `-0.0`，但标准 JsonConverter 解码后成为 `+0.0`；NaN 编码为字符串 `"NaN"`，同一转换器解码成数值 0。
当轮原始 Connector 特殊浮点 CRUD 回归另有 8 项，在当轮 XML 中均通过；当前仅保留 REAL、FLOAT(24)、FLOAT(53)、DOUBLE 四种类型的实际存储零值回归，已移除当前数据库拒绝的 NaN 写入输入。
`DamengJsonConverterProbeIT` 独立验证标准转换器的现有行为；诊断测试通过不等于无损往返通过。

负零与正零虽然按通常数值比较相等，但符号位、倒数和部分科学计算语义不同；NaN 变成 0 会把“非数值”误作真实零值。
这是可以单独评估修复的转换/消费协议问题：在 Kafka 依赖版本保持不变的条件下，验证自定义 Converter 或下游显式解码协议，并检查 schema、存量消息和消费者兼容性。
本次未实现或验证替代 Converter，不能宣称换一种格式就已解决。

=== D：LOCAL TIME ZONE 的当前策略与历史验证

旧版 CREATE/INSERT 已成功，但 snapshot 在 `DamengValueConverters.schemaBuilder()` 主动拒绝 LTZ，底层原因为 `Unsupported Dameng TIMESTAMP WITH LOCAL TIME ZONE`。这是实现修改前的历史结果。
历史跨会话诊断发现：快照随读取会话时区变化，而日志文本没有携带足够的原始写入时区信息，无法唯一恢复 instant。
2026-10-26 在官方 8.1.3.162 pack1 构建 `03134284194-20240703-234060-20108` 上重新验证：两个写入会话分别设置 `+05:45` 和 `-12:59`，写入同一无偏移字面量 `2000-02-29 12:34:56.123456`。
UTC 读取会话分别得到 `2000-02-29 06:49:56.123456` 与 `2000-03-01 01:33:56.123456`，即两个不同 instant；对应归档 `SQL_REDO` 均为同一个 `TIMESTAMP'2000-02-29 12:34:56.123456'`。
挖掘会话设为 UTC 或 `+08:00` 时，两条 redo 的表达式都保持相同；另一组测试也确认同一行的 JDBC 读值会随读取会话时区变化。
在线字典模式下，`DBMS_LOGMNR.MINE_VALUE(REDO_VALUE, 'schema.table.VALUE')` 对这两条历史 INSERT 也都返回 `2000-02-29 12:34:56.123456`；挖掘会话设为 UTC 或 `+08:00` 结果相同。因此在已验证的 `SQL_REDO` 和 `MINE_VALUE` 路径中，都没有得到可区分这两个 instant 的列值。
后续对照加入第三条：在 `-12:59` 写入会话用 `2000-02-28 17:50:56.123456` 表示第一条的同一个 UTC 时间点。归档 `SQL_REDO` 和 `MINE_VALUE` 仍返回这个不同的本地时间文本，说明已测输出不是统一的 UTC 时间。第四条在 `+05:45` 会话写入带显式 `-12:59` 偏移的 `2000-02-29 12:34:56.123456`；挖掘结果为 `2000-03-01 07:18:56.123456`，说明输出也不是简单复制 INSERT 原文，而是呈现写入会话的本地时间。
`MINE_VALUE` 的 JDBC 元数据为 `VARCHAR`，`getObject()` 返回 `String`。将该字符串再读成 `Timestamp` 只会引入客户端时区解释，不会恢复写入时区。上述实验确定的是公开 LogMiner 查询的时间基准，未直接解码归档文件的原始二进制编码；不能断言物理 redo 内部一定按写入会话时区存储。
`DamengDatatypeProbeIT.shouldExposeAmbiguousLocalTimezoneRedoAcrossWriterSessions` 将这种歧义作为回归断言。结论限于本构建已测的归档 `SQL_REDO` 和在线字典 `MINE_VALUE` 路径，不排除未来数据库版本或其他接口提供可恢复的原始时间点。
当前实现按用户选择接受这种语义损失：只对 `TIMESTAMP WITH LOCAL TIME ZONE` 将流式本地时间文本当作 UTC，并将 Connector 的 JDBC 会话设为 UTC 以固定 snapshot 读取基准。输出是带 `Z` 的 `io.debezium.time.ZonedTimestamp` 字符串，不声明流式输出是真实 instant。普通 `TIMESTAMP` 和 `TIMESTAMP WITH TIME ZONE` 维持原有映射。
在官方 8.1.3.162 pack1 上，完整引擎定向测试覆盖同表三种时间类型的 snapshot、INSERT、UPDATE、DELETE：`+05:45` 写入的 LTZ 在快照为 `2000-02-29T06:49:56.123456Z`，流式为 `2000-02-29T12:34:56.123456Z`；另外两列未被套用 LTZ 规则。下游恢复需要每条写入对应的会话时区，任务配置一个固定默认时区不能保证所有历史记录正确。

若未来要求无损支持，仍需验证能取得每条历史记录原始 instant 或写入会话时区的数据库接口，并覆盖不同写入会话、显式偏移、夏令时及重启回放。

=== E/F/G/H：数据库未接受测试声明或输入

E 的 18 项等于 3 种类型名称 × 3 种 decimal.handling.mode × 正负两个值。
配置仅影响 Connector 的表示方式，无法改变启动前的 INSERT 结果；本轮 SQL 科学计数值被拒绝，错误根因为 `Data overflow`。
历史分路径诊断还记录 JDBC setBigDecimal 拒绝同样数值，但本次没有重新执行该诊断。
不能把官网数值表达式的计算范围直接等同于该旧构建的列存储范围。

F 的 15 项等于每种精度下 4 个普通 TIMESTAMP 输入独立用例、1 个带时区用例，共 3 组。
四个输入含公元 1 年、1969 年末、闰日及 9999 年；这次全部在建表阶段失败，尚不能判断对应日期/小数秒转换的结果。
升级后即使接受声明，还要检查 Connector 纳秒时间戳的 INT64 可表示范围；当前测试用独立 BigInteger 期望值防止溢出被误判为通过。

G 的输入是 `梦` 重复 8 次、重复 7 次，以及 `😀` 重复 8 次。
报告中的 emoji `length=16` 来自 Java UTF-16 长度，实际是 8 个 Unicode 码点，不是写入了 16 个 emoji。
现有字符集和长度参数下 JDBC 报 `Param incompatible`；历史 SQL 字面量路径也记录列超长。
目前不能仅凭这些信息断言是驱动、服务器实现还是某个参数单独负责，应在升级后重测两条写入路径及显式 CHAR/BYTE 语义。

H 的建表语句使用 `VALUE ROWID`，与查询或日志 WHERE 中的 ROWID 行定位语义不同。
不能通过删除这项失败就把普通 ROWID 类型列标成支持，也不能据此否定无主键表采集。

37 项都尚未进入这些值的 CDC 验收。升级后需先确认原声明/输入被接受，再检查 snapshot、归档 CRUD、before/after、JSON 及相关重启/历史结构回放。
缩小输入、截短中文或把精度改成 6 会变成另一个用例，不能算修复原来的边界。
